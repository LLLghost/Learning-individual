# Исполнители практики новой редакции

45 гостевых сценариев находятся в `author_catalog.py`; его результат —
`catalog.json`. Ещё одна работа, восстановление ВМ, выполняется отдельным
`proxmox_backup.py` на учебном хосте. Сборка делает два самостоятельных скачиваемых
файла и показывает их SHA-256 в уроках. Скрипт из изменяемой ветки не запускается
через pipe в root-shell.

**Код сценария и протокол его исполнения — разные доказательства.**
Свежая авторская приёмка Proxmox за 2026-10-28:
`quality/live-labs/2026-10-28/README.md`; 45 гостевых сценариев и native backup
прошли по два варианта. `quality/practice-readiness.json` связан с текущими SHA.
Прежние WSL-проверки сохранены отдельно и не заменяют живой прогон.

## Гостевой цикл

Использовать выделенную Debian 12/13 ВМ, Python 3.11+, непривилегированного
пользователя `course` с sudo. На рабочем компьютере и хосте Proxmox гостевой
исполнитель не используется. Он отказывается от работы при наличии `/etc/pve`.

1. Скачать `course-practice.py`, сверить опубликованный SHA-256, прочитать код.
2. Внутри выделенного гостя однократно выполнить
   `sudo python3 course-practice.py enroll --disposable-guest`.
3. В уроке нажать «Начать новую попытку». Скопировать команды именно этой попытки.
4. Выполнить `prepare`, решить задачу, затем выполнить `check --output <новое-имя>.json`.
5. Загрузить отчёт в урок. После изменений повторить check с новым именем отчёта.
6. Сохранить нужные наблюдения и выполнить `restore`. Затем подготовить другой
   вариант через `--variant 1`. Активная попытка не перезаписывается подготовкой.

`status` показывает идентификатор попытки, вариант, пользователя и рабочую папку.
`WORK=/var/lib/mayak-practice/<lesson>/work`; `NS=mk` и первые 10 символов attempt.
Выполнение собственных `solution.py`, `solution.sh` и `measure.py` производится
от имени ученика через runuser, а не root. Предоставленный `solve` служит авторской
проверкой сценария. Наличие solve не доказывает самостоятельное решение учеником.

Исполнитель требует необходимые инструменты до создания ресурсов. Основные
пакеты Debian: `python3`, `sudo`, `iproute2`, `iputils-ping`, `curl`, `util-linux`,
`e2fsprogs`, `git`, `openssl`, `pciutils`. Дополнительные работы требуют
`nftables`, `dnsutils`, `dnsmasq-base`, `lvm2`, `mdadm`, `ansible-core`,
`numactl`, `nfs-kernel-server`, `nfs-common`, `dmsetup` и подходящего ядра.
ZFS требует отдельно установленного и работающего OpenZFS; название пакета и
доступность зависят от подключённых компонентов репозитория и ядра.

Docker и kind устанавливаются отдельно по официальным инструкциям.
Контейнерные сценарии используют заранее загруженный `python:3.11-slim`,
фиксируют его локальный image ID и не скачивают другой образ во время опыта.
Для гарантии локальной публикации использовать Docker 28 или новее; ограничения
старых версий объясняются в уроке. Kubernetes создаётся как отдельный kind-кластер
попытки, текущий kube-context не используется. Нужны заранее загруженные образы
Python и `kindest/node@sha256:...`; последний передаётся при подготовке:

```sh
sudo MAYAK_KIND_NODE_IMAGE='kindest/node@sha256:<проверенный-digest>' \
  python3 course-practice.py prepare kubernetes --attempt <id-из-урока>
```

NUMA-опыт требует двух видимых узлов; UEFI-опыт — загрузки через OVMF. Программный
DM multipath использует два loop-пути к одному образу: он проверяет переключение
в блочном слое, но **не независимость физических HBA, сетей и питания**. NFS
проверяется между клиентским mount и серверным экспортом внутри одной ВМ;
независимый отказ сервера требует отдельного стендового прогона.

## Резервное восстановление Proxmox

`proxmox-backup.py` запускается root на разрешённом учебном хосте Proxmox VE 8/9.
Нужна исходная Linux-ВМ с Python 3 и работающим QEMU guest agent.
Выполнить `prepare --source-vmid <VMID> --storage <storage> --attempt <id>`.
Скрипт создаёт отдельный полный клон, отключает его NIC, записывает контрольную
заметку и включает проверочную HTTP-службу. Исходная ВМ не изменяется.

Подготовка печатает точные команды vzdump и qmrestore в новый VMID. Ученик
выполняет их, запускает восстановленную ВМ и вызывает `check`. Проверяется
HTTP-ответ внутри восстановленного гостя через guest agent. `restore` удаляет
только две ВМ с совпавшей меткой владения; источник и архивы сохраняются.
Ошибку владения нельзя обходить с помощью force. Полный живой цикл проверен
дважды в протоколах за 2026-10-27. Offline-клон Debian может ждать сеть около
120 секунд; guest agent ожидается ограниченное время, до 180 секунд.

## Проверки разработчика

```sh
python scripts/practice/author_catalog.py
node scripts/practice/test-report.mjs
sudo python3 scripts/practice/test_cli.py <непривилегированный-пользователь>
sudo python3 scripts/practice/test_runner.py --all --user <пользователь> \
  --output work/practice-evidence/all-recipes.json
```

Последний прогон создаёт временные каталоги, отдельные namespaces, loop-mounts
и временные systemd units. Он не записывает enrollment-маркер в `/etc` тестовой
системы. Отсутствующие инструменты и возможности обозначаются `unavailable`,
а не успешными проверками. Перед запуском новых сценариев перечитать их код.

Вывод каждой фазы ограничен 1 MiB на поток и временем; при превышении результат
отклоняется, а группа процессов завершается.

Отчёт привязан к попытке, варианту, гостю и SHA-256 исполнителя. В новой практике
принадлежность определяется случайным ID из браузера, а не предположением о
совпадении часов гостя и браузера. При заметном расхождении показано предупреждение. Контрольная сумма
обнаруживает случайное изменение файла, но не является подписью или защитой от
владельца root-доступа. Статический сайт показывает последнее принятое наблюдение;
он не узнаёт об изменении ВМ без новой проверки и загрузки отчёта.
