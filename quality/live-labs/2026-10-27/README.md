# Свежая авторская приёмка Proxmox: 27 октября 2026

**45 гостевых сценариев + восстановление ВМ + 9 прежних работ; по два цикла.**
В Chromium приняты 110 настоящих отчётов. Это проверка реализаций с эталонными
решениями автора, а не самостоятельное прохождение начинающим.

## Среда и воспроизводимость

- Proxmox VE 9.1.1, узел pxe; управляющая сеть не менялась.
- VM9100: новая Debian 12 из официального generic-образа, Linux 6.1.0-54-amd64,
  OVMF, 4 vCPU, 6 GiB, два виртуальных NUMA-узла. Конфигурация: `vm-config.txt`.
- Образ Debian проверен по SHA-512 из официального HTTPS-источника.
  Kind 0.30.0 и kubectl 1.34.0 проверены по опубликованным SHA-256.
  Docker 29.9.2, ZFS 2.1.11; версии — `environment.txt`.
  Python image digest: `sha256:ae952e0a57138a4317b9b61caaa19a8217c2f356803f8d7e63aad08769950937`.
  Kind node digest: `sha256:7416a61b42b1662ca6ca89f02028ac133a309a2a30ba309614e8ec94d976dc5a`.
- VM9101 — отдельный небольшой источник для backup: Debian 12, Python, guest agent,
  cloud-init отключён после подготовки. См. `backup-source-config.txt`.
- Исходные ВМ сохранены. Снимки: `mayak-tested-clean` у 9100,
  `mayak-backup-clean` у 9101. Временные клоны и восстановленные VM100/101 удалены
  штатным restore с проверкой метки владения. Архивы vzdump сохранены на стенде.
- Учебная сеть: mayakbr0, 172.30.253.0/24; NAT через vmbr0. Основной гость .2,
  источник backup .3. Первоначальный DHCP в LAN не выдал адрес.
- Пароли и закрытые SSH-ключи в протоколы не входят.

## Что реально проверено

`guest-cycles.json`: CLI опубликованного исполнителя, enroll только выделенного
гостя. В каждой работе: prepare → отказ check до решения → эталонное решение →
успешный check с отчётом → restore → повторный restore. Затем другой вариант.
Ввод собственных программ выполняется непривилегированным course через runuser,
системные изменения — разрешённым исполнителем через root/sudo.

В process, systemd и container-network после успеха отдельно остановлены реальный
процесс, служба или контейнер: все шесть новых check отказали. Импорт отказа снял
подтверждение; более старый успешный отчёт не восстановил его.

`browser-reports.json`: 92 отчёта нового исполнителя в настоящем интерфейсе.
Начальные ID выданы кнопкой браузера до стендового запуска. Для импорта в чистый
профиль восстановлены соответствующие ID/варианты; условия не менялись ради зачёта.
Проверены новый отказ, новая попытка и импорт прежней попытки как истории.

`legacy-cycles.json` и `legacy-browser.json`: подготовка реальных systemd, сетевых
namespaces, пустого диска, LVM, RAID1, ZFS, сертификатов и chrony. Сбор фактов
настоящим course_lab.py; 18 положительных и 18 отрицательных отчётов в кабинете.
У сетевых работ отдельные стеки Linux внутри ВМ, управляющий интерфейс не трогался.
Для отрицательной проверки L31A отчёт дополнительно пересобран с заведомо
отличающимся от измеренного значением поправки (`harness/negative-time.sh`).

`backup-acceptance.json`: полный независимый клон → отказ до восстановления →
vzdump → qmrestore в другой VMID → HTTP-ответ контрольной заметки через guest
agent → удаление обеих временных ВМ → идемпотентный повтор restore. Два варианта,
суммы реальных архивов включены в протокол. Это не просто проверка наличия архива.

В конце гостевых циклов проверено отсутствие оставшихся namespaces, контейнеров,
loop-устройств и монтирований практики; вывод аудита был пуст.

## Найденные и исправленные дефекты

1. Первый прогон: 43/45, см. `guest-first-run.json`. VLAN-проверка одним пакетом
   давала перемежающийся отказ после отрицательной пробы ARP. Теперь отправляются
   три пакета; неверное состояние по-прежнему отклоняется.
2. Ansible отказывался от ASCII-локали C. Исполнитель задаёт C.UTF-8;
   повторный настоящий запуск обоих вариантов успешен.
3. Старый успешный отчёт мог заменить более свежий отказ той же попытки.
   Интерфейс сохраняет его только в историю. При переводе часов назад предлагается
   новая попытка; часы и контрольная сумма не объявляются удалённой аттестацией.
4. Offline-клон Debian ожидал networkd-wait-online: guest agent становился доступен
   примерно после 128 секунд при прежнем пределе 90. Предел увеличен до 180;
   исходные отказы — `backup-first-run.json`. Полный последующий цикл проверен
   на отдельном минимальном источнике.
5. verify:live по умолчанию читал сентябрьские отчёты. Теперь он берёт каталог
   принятой текущей версии, оба варианта и проверяет SHA сборщика. Исторический
   каталог можно проверить только явно, с соответствующей пометкой.

## Файлы и повторная проверка

`summary.json` содержит сводку и SHA файлов (LF для текста, исходные байты для tgz).
`release-checks.json` — запись выполненных команд и кодов завершения, не сырой лог.
`guest-reports.tgz` и
`legacy-reports.tgz` — первичные отчёты; `legacy/` — положительные варианты для
`npm run verify:live`. `harness/` сохраняет использованные сценарии и импорт.
Они рассчитаны на эти одноразовые ресурсы и не предназначены для запуска на
рабочем компьютере или непосредственно на хосте вместо гостя.

Команды проекта: `npm run validate:release`; отдельно `npm run verify:live`.
Префикс публикации дополнительно проверяется через BASE_PATH=/Learning-individual.

## Границы доказательства

NUMA, PCIe и UEFI здесь виртуальные. ECC, BMC, питание и реальные прошивки этим
прогоном не аттестованы. NFS проверен внутри одного гостя; multipath — два
программных пути, не независимые HBA/сети. Статический сайт не наблюдает ВМ:
после изменения нужен новый check и импорт. Приёмка программы не доказывает
понятность урока, перенос навыка после перерыва или удобство для человека.
