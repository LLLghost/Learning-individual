# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Учебник по серверной инфраструктуре: один исходный файл `public/course.html` (~2 МБ, ~120 000 слов на русском) и генератор без зависимостей, который режет его на статический многостраничный сайт в `build/` (48 маршрутов). Всё остальное — навигация, поиск, тренажёры, учебный кабинет, CSS и JS — вычисляется из этого файла при сборке.

**Язык проекта — русский.** Текст учебника, интерфейс, сообщения и комментарии в коде — по-русски. Комментарии объясняют «почему так», а не «что делает строка»; такой стиль выдержан во всех скриптах, следуйте ему.

## Команды

```bash
node scripts/build-static.mjs          # сборка в build/ (pnpm build)
node scripts/validate-site.mjs         # проверка собранного сайта (pnpm validate)
BASE_PATH=/Learning-individual node scripts/build-static.mjs   # для GitHub Pages в подкаталоге
node --check build/assets/site.js      # синтаксис сгенерированного клиентского JS
python3 -m http.server 4175 --directory build   # посмотреть результат
```

Скрипт стенда проверяется на подставном хосте — зависимостей не требует, идёт в
той же работе, что сборка и проверка:

```bash
bash scripts/stand/selftest.sh          # подставные qm и pvesm, 47 утверждений
```

Сборка и проверка используют только стандартную библиотеку Node — `pnpm install` для них не нужен. **Всегда прогоняйте проверку в обоих режимах**: без `BASE_PATH` и с ним, потому что ошибки в ссылках проявляются только во втором.

Инструменты правки исходника (оба физически не могут повредить разметку и ответы — они не отдают то, что нельзя менять):

```bash
node scripts/text-nodes.mjs list [--latin] [--from N] [--limit N]  # текстовые узлы прозы
node scripts/text-nodes.mjs apply patch.json                       # вернуть правки по индексу
node scripts/text-nodes.mjs synctoc                                # пересобрать оглавление
node scripts/study-strings.mjs list [--latin]                      # видимые строки банка заданий
node scripts/study-strings.mjs apply patch.json
```

### Браузерный обход

```bash
npm install --no-save playwright && npx playwright install chromium
node scripts/smoke-browser.mjs     # 48 маршрутов и три действия
```

Валидатор читает разметку и не видит того, что ломается только при исполнении: упавший обработчик, не найденный элемент, ошибка в клиентском коде. Обход поднимает свой сервер на стандартной библиотеке, проходит все маршруты и падает на первой же ошибке в консоли, а затем проверяет три живых действия — мини-тренажёр засчитывает ответ и показывает разбор, поиск находит слово, вид модуля собирает задания и работу. Каждое из трёх ломалось молча и правилами разметки не ловится.

В рабочем процессе это **отдельная работа** `smoke`: сборка и публикация по-прежнему обходятся одной стандартной библиотекой, браузер ставится только в ней. Публикация ждёт обеих работ. Обход идёт по сайту, собранному **без** `BASE_PATH`: локальный сервер отдаёт его из корня.

### Внешние ссылки проверяются отдельно

```bash
node scripts/check-links.mjs      # нужна сеть, в обычный прогон не входит
```

Мёртвая ссылка — невыполненное обещание: читателя отправили к первоисточнику, а его нет, и по самой книге этого не видно. Проверка разделяет три случая: **мёртвые** (правим), **переезды** (обновляем адрес — за редиректом обычно стоит исчезнувшая страница: вики mdraid уехала в архив kernel.org, страница вики EDK II свелась к корню репозитория) и **закрытые** 403/429 (защита от роботов у Red Hat, Ansible, PCI-SIG — проверяются руками). Заголовок `user-agent` обязан быть из однобайтовых символов: кириллица в нём роняет запрос до сети, и все ссылки разом выглядят мёртвыми.

### Тестов нет — есть `validate-site.mjs`

Отдельного тестового прогона в проекте нет: `scripts/validate-site.mjs` (~670 строк) и есть спецификация. Выбрать одну проверку нельзя, но убедиться, что она работает, можно и нужно так: **сломать вход и увидеть именно её сообщение**, потом восстановить. Так проверялось каждое добавленное правило; добавляя новое, делайте так же.

## Архитектура

### Один источник, всё остальное производно

`build-static.mjs` не разбирает HTML деревом. Он находит границы по идентификаторам: `marker('b07')` ищет `id="b07"` и отступает назад до `<`. Регионы идут в исходнике подряд и режутся срезами:

```
title … start-part → уроки start01–start05 → b00 … b33 → b33-s044 (приложения)
  → selftest → study-app → assessment → labs (lab00–lab36) → assessment-reference
```

Отсюда следует главное: **порядок блоков в `course.html` — часть контракта.** Перестановка региона ломает срезы молча, потому что сборка всё равно пройдёт.

Массив `pages` — реестр «что попало на страницы». Из него строится `idToUrl`, а `rewriteLinks` превращает внутрикнижную ссылку `href="#b07-s003"` в `href="/chapters/07/#b07-s003"`. Раздел, не попавший в `pages`, теряет все ведущие к нему якоря.

### Двойная нумерация

Главы `bNN` (00–33) и академические модули `UNN`/`id="chNN"` (00–36, всего 37) — **разные шкалы**. Работы практикума `LNN` и задания кабинета нумеруются по модулям, не по главам: L16 (ZFS) относится к главе 15, L26 (Kubernetes) — к главе 23. Соответствие нигде не записано руками: `moduleChapter` вычисляется по тому, внутри какой главы физически лежит заголовок модуля, а валидатор проверяет, что все ссылки «Теория» этому соответствуют.

Вводные уроки `/start/01–05` намеренно живут **вне** нумерации глав: своя шкала, свой раздел, свой боковой список. Так их можно было добавить, не сдвинув ни одного идентификатора из 34 глав и банка проверок.

### CSS и клиентский JS живут внутри генератора

Стили и весь браузерный код — шаблонные строки в `build-static.mjs`, попадающие в `build/assets/site.css` и `site.js`. Отдельных файлов стилей нет: правка оформления или поведения сайта — это правка генератора. Сборка клиентский JS **не разбирает**, поэтому синтаксическая ошибка в нём проходит и сборку, и (частично) проверку — валидатор специально прогоняет код кабинета через `new Function`.

### Практика и проверка — одна страница

Работы практикума **не имеют своих страниц**: их текст лежит скрытыми секциями `<section data-lab-module="N">` на `/assessment/`, и вид модуля показывает нужную копией узла (`cloneNode`) — кабинет по-прежнему не собирает разметку из строк. Адрес работы — `/assessment/?module=N`. Раньше это были 37 отдельных страниц, и читатель ходил между практикой и проверкой сам.

Страница практики несёт только работу: вступление, кабинет и ничего после него. Вся справка — критерии освоения, границы автоматической проверки, требования к стенду, контракт сдачи — живёт в разделе `#how-checks-work` на `/about/`, и ссылка из кода кабинета на `#autopractice` подставляется с `BASE_PATH` (`studyScript`). Общее введение практикума (`id="labs"`) **не принадлежит нулевой работе**: вид модуля показывает секцию целиком, поэтому заголовок всего практикума уезжал бы в U00 — он нарезается отдельным срезом `labsIntro`.

### Автопроверка работ практикума

Работа готовится скриптом, читатель решает, скрипт собирает факты в `lab-report.json`, кабинет сверяет и выносит вердикт. В книге это три вещи: `<script type="application/json" id="lab-code-data">` (сам `course_lab.py`), `id="lab-data"` (ожидаемые значения **хешами** и вопрос о механизме) и вид модуля в коде кабинета.

Автопроверку имеют **все 74 работы** — обе в каждом модуле; число названо в книге прозой, и валидатор сверяет его с данными. 65 из них вида `dataset` (стенд не нужен), 9 требуют стенда и без метки `/etc/course-lab-stand` отказываются работать. Виды работ: `dataset` — стенд не нужен, скрипт выдаёт данные; `collect` — скрипт только собирает факты со стенда, ничего не ломая; `stand` — скрипт вносит инцидент по случайному зерну и умеет откат.

Добавить работу вида `dataset` — это три записи в `course_lab.py` (`DATASETS`, `CLAIMS`, `LABS`) и запись в `lab-data` с хешами ожидаемых значений; хеш считается той же функцией `labHash`, что и в кабинете (FNV-1a с солью, результат по основанию 36). Набор данных обязан отвечать тексту работы в книге: карточка автопроверки показывается под тем же номером.

Ожидаемое значение хешируется в той форме, в какой его увидит сверка: JSON не различает `52` и `52.0`, браузер приводит оба к `52`, а хеш, посчитанный от «52.0», верный ответ не принимал. Числовые ответы поэтому нормализуются по правилам JavaScript до хеширования.

Работа обязана отвечать **своей** половине модуля: три работы были написаны по тексту второй половины, а стояли под номером первой — карточка автопроверки показывается под тем же номером, что и работа в книге.

Проверять добавленную работу надо целиком, а не глазами: прогнать `init` и `collect` настоящим скриптом, затем прогнать получившийся `lab-report.json` через **ту самую** `labRows` со страницы кабинета — и отдельно испортить каждое поле ответа по очереди. Поле, порча которого не меняет вердикт, не проверяется ничем: в разметке это выглядит ровно так же, как работающая сверка.

### Работы привязаны к своему стенду

Метка `/etc/course-lab-stand` одна на всех и лежит по известному пути: сама по себе она отличает стенд только от машины, где её забыли завести. Поэтому у стенда есть номер. Его заводит `course-stand.sh` один раз (`/etc/course-stand-id`, шестнадцать шестнадцатеричных цифр), кладёт в каждого гостя той же меткой и пишет карточку `/root/course-stand.json`; карточка загружается в кабинете, и скачанный `course_lab.py` выпускается с этим номером в `STAND_ID`. Сверяет его одна функция `stand_guard` — та же, что проверяет наличие метки.

Номер **случайный, а не выведенный из хоста**: из `machine-id` он не дал бы ничего сверх случайного, зато стал бы отпечатком хоста и уезжал бы в файлах, которые читатель пересылает. Заведённый однажды, он переиспользуется: `destroy` и повторный `create` не должны обесценивать уже скачанные скрипты.

Обещать этим можно ровно одно: **работа, ломающая настройки машины, не запустится не на той машине по ошибке**. Подделку результата привязка не усложняет ни на сколько — проверку в своём файле сотрёт кто угодно, номер впишет руками. Так и написано в `#how-checks-work`, и расширять это обещание в текстах нельзя.

Номер попадает внутрь строки Python, поэтому кабинет проверяет его форму до подстановки, а не доверяет загруженному файлу. Ключ `server-infrastructure-stand-v1` внесён в `BACKUP_KEYS` — иначе перенос прогресса терял бы привязку молча.

**Сверка описана данными, а не кодом под каждую работу:** в `checks` перечислены операции из `LAB_OPS` (`hash`, `sameAsClaim`, `matchesClaim`, `offset`, `equals`, `isTrue`…). Добавить работу — значит добавить запись в `lab-data` и пробник в скрипт, а не написать ещё одну почти такую же функцию. Там, где верное значение зависит от стенда (серийный номер диска, размер тома), сверка **относительная**: заявленное сравнивается с измеренным, а не с зашитым ответом.

Сверка идёт в браузере, а не в скачанном скрипте: иначе ожидаемые значения уезжают к читателю вместе со скриптом. Хеш прячет ответ от чтения исходника, но не от перебора — это защита от подглядывания, а не от подделки, и обещать большее нельзя: файл отчёта лежит на машине читателя. Подделка при этом требует знать внесённый вариант и вид подтверждённой гипотезы, то есть почти всё решение.

**Страница кабинета собирается из перечисленных блоков, а не из сплошного среза:** `${studyData}${checkerData}${labCode}${labData}${studyScript}`. Новый блок данных надо назвать в генераторе явно, иначе он просто не доедет до страницы — сборка и разметка при этом останутся правильными.

### Три проверки, и каждая своя

Курс проверяет читателя трижды, и ярусы **не должны пересекаться**:

1. **Мини-тренажёр главы или урока** — сразу после чтения, два вопроса о главных утверждениях: прочитано и понято. Вопросы лежат в `chapter-quick-data` (34 главы) и `lesson-quick-data` (5 вводных уроков) в `course.html`; у главы это вопрос о её модели и вопрос о её «типичной ошибке мышления». Разметку обоих делает одна функция `quickTrainer`, ключ отметки в календаре — номер главы или `sN` для урока: шкалы разные и пересечься не должны.

   Каждый из двух — не вопрос, а **слот с пулом смежных вопросов** об одном утверждении (`[[вариант, вариант], [вариант, вариант]]`). Промах не показывает ни верный вариант, ни разбор: слот показывает следующий вопрос пула. Раньше неверный ответ подсвечивал верный и печатал разбор, и кнопка «Проверить ещё раз» не значила ничего — оставалось повторить увиденное. Показанный вариант выбирается по числу попыток, поэтому переживает перезагрузку и не требует своего ключа хранилища; у засчитанной записи номер варианта хранится рядом с отметкой.
2. **Задания модуля в кабинете** — позже и по расписанию повторения: применение механизма к незнакомой ситуации, второй ярус, расчёт, сценарий. Только этот ярус идёт в зачёт.
3. **Работа практикума** — на стенде, где готового решения нет.

Раньше первый ярус брал два первых задания модуля **прямо из банка кабинета** (`items.filter(module).slice(0, 2)`): читатель отвечал на оцениваемое задание заранее и вместе с разбором. В разметке это не видно — вопросы там настоящие, просто чужие. Валидатор сравнивает тексты вопросов обеих проверок и не пропускает совпадение.

`chapter-quick-data` лежит **после `</main>`**, рядом с `study-data`, то есть вне всех срезов регионов. Блок с типом (`type="application/json"`) не ломает `followingScript`: тот ищет ровно `<script>` без атрибутов.

### Лаборатория главы и работа практикума — разные ярусы

«Лаборатория» в главе закрепляет **нормальную настройку** механизма; развёрнутая работа `LNN` уводит за пределы готового решения. В шести поздних главах (24, 27–32) работа была написана копией лаборатории: читатель делал одно и то же дважды, и перекрытие по словам доходило до 58%. Лаборатория этих глав сокращена до подготовки и наблюдения, а измерения, отрицательные тесты и инциденты оставлены работе; в конце лаборатории стоит явная ссылка на неё.

### Что нового

`CHANGELOG.md` ведётся для читателя, а не для разработчика: что изменилось и ради чего, а не список коммитов. Генератор берёт **верхнюю запись** и печатает её на `/about/` вместе с датой сборки — вести список в двух местах никто не станет, поэтому источник один. Из разметки в пунктах поддерживается только `**жирный**`: полноценный разбор markdown стал бы ещё одним источником расхождений. Валидатор сверяет запись на странице с верхней записью файла — иначе в репозитории появляется новая запись, а на сайте остаётся прошлая, и читатель узнаёт об изменениях последним.

### Адрес сайта и метаданные

`SITE_URL` — полный адрес сайта (`https://владелец.github.io/репозиторий`), рабочий процесс собирает его сам и приводит имя владельца к нижнему регистру: адреса `github.io` регистрозависимы. Переменная нужна `canonical`, `og:url` и `sitemap.xml` — они требуют абсолютных адресов. **Без `SITE_URL` эти три вещи не выпускаются вовсе**: врать поисковику о том, где живёт страница, хуже, чем молчать. `robots.txt` пишется всегда, строка `Sitemap:` в нём — только когда адрес известен.

Описание главы берётся из её первого содержательного абзаца, а не из заголовка: описание, равное заголовку, даёт в выдаче две одинаковые строки вместо строки и пояснения. Валидатор ловит именно случай «все 34 главы описывают себя своим же названием».

### Схемы

Семь мест, где смысл по существу пространственный, нарисованы как SVG прямо в `course.html`: `<figure class="scheme">` с `<svg>` внутри и подписью `<figcaption>`. Раньше там стояли `<pre>` с символьной графикой — она разъезжалась при любом размере шрифта и ничего не говорила экранному диктору.

Правила, которые закреплены проверкой: у схемы обязаны быть `role="img"`, `<title>` и `<desc>` (диктор читает именно их), подпись, и **никакой** ширины на самом `<svg>` — размер задаёт `viewBox`, а колонка тянет картинку по себе. Идентификаторы внутри SVG общие для всего документа: наконечник стрелки у каждой схемы свой (`tip-io-path`, `tip-bmc`, …), иначе четыре схемы дают четыре одинаковых `id="tip"`. На узкой колонке схема не ужимается, а прокручивается вбок, как таблицы и листинги: при `width:100%` без `min-width` подписи внутри рисунка сжимались до шести пикселей.

Цвет берётся из `currentColor`, поэтому тёмная тема ничего не переключает; `style=` в разметке запрещён политикой безопасности, так что оформление идёт презентационными атрибутами и классами (`zone`, `dim`, `accent`, `num`). Подпись под схемой и серая строка внутри неё не должны говорить одно и то же — это выходит двумя одинаковыми строками подряд.

### Вся книга одной страницей

`/book/` — вся проза подряд: пять вводных уроков, 34 главы и приложения. Отсюда книгу печатают, сохраняют в PDF и кладут в читалку; постранично это значило бы сорок раз нажать «печать».

Страница собирается теми же срезами, что и главы, поэтому расходиться с книгой не может, но три вещи в ней сделаны иначе. Мини-тренажёр, свободное воспроизведение и карточки практикума **не попадают**: их рисует скрипт, и на бумаге они просто пусты. Ссылка на раздел, который на этой странице есть, остаётся местной — иначе печать даёт сноски, уводящие с листа на сайт; всё остальное (работы практикума, кабинет) по-прежнему ведёт на свою страницу. Рейла разделов нет: заголовков здесь восемьсот.

Страница **намеренно исключена** из индекса поиска и из офлайн-копии — это та же проза во второй раз: в индексе она удваивала каждую находку и сам файл (1,6 → 2,9 МБ), в кэше — его объём. Список исключений в валидаторе один на три правила (`DUPLICATE_ROUTES`).

На бумаге глава начинается с новой страницы, листинги и схемы не рвутся пополам, а у внешней ссылки печатается её адрес: на листе сама ссылка бесполезна, сноска с адресом — нет. Внутренние ссылки адреса не получают, иначе каждая из сотен перекрёстных ссылок тянула бы за собой строку.

### Работа без сети

`build/sw.js` собирается генератором (правьте генератор, не файл). Он отдаёт страницу из кэша и обновляет её в фоне, поэтому сайт открывается офлайн и мгновенно. Кнопка «Сохранить учебник для работы без сети» на `/route/` кладёт в кэш сразу все маршруты и индекс поиска, сообщая о ходе через `postMessage`. Имя кэша содержит хеш от исходника и собранных файлов: новая публикация обязана вытеснить старую копию, иначе читатель останется на ней навсегда. Политика безопасности несёт `worker-src 'self'` — без неё регистрация молча не проходит, и офлайна просто нет.

Индекс поиска лежит компактно: `{v, p:[[адрес, заголовок]], s:[[номер страницы, якорь, заголовок раздела, текст]]}`. Текст раздела **не режется** — поиск полнотекстовый, и обрезка стоила бы находок; экономия идёт на повторяющихся адресах и заголовках страниц. Валидатор разворачивает индекс обратно и проверяет правила на развёрнутом виде.

### Банк заданий

`<script type="application/json" id="study-data">` в `course.html`: 111 заданий (`items`) и 37 сценариев (`cases`), каждое привязано к модулю. Блок сериализован с разделителями `", "` и `": "`; `study-strings.mjs` воспроизводит это форматирование посимвольно и отказывается работать, если не смог. Правьте банк только через него — прямая правка легко ломает и форматирование, и ответы.

### Прогресс не ставится сам — это осознанное решение

Задание засчитывается, только когда верны **и ответ, и рассуждение** (второй ярус спрашивается всегда и до вердикта). Уровень уверенности заявляется до проверки и после результата не меняется. Даты в `server-infrastructure-timeline-v1` только добавляются. Всё, что читатель отмечает себе сам — темы в свободном воспроизведении, «разобрано» в журнале ошибок, работы практикума, — **ничего не засчитывает и в календарь не идёт**. Не добавляйте кнопку «отметить пройденным»: это прямо противоречит замыслу.

### Две шкалы: теория и практика на стенде

Автоматический результат — это **две разные шкалы**, и смешивать их нельзя. «Теория и тренажёры» считает модули, программные тесты и итоговый контроль. «Практика на стенде» считает только работы с полем `bench` в `lab-data` — те девять, чьи факты снимаются с настоящей машины; у них есть `chain` (цепочка: systemd, сеть, хранение, восстановление данных, доступ, время) и `proof` — фраза о том, что отчёт подтверждает, а что нет.

Вид работы (`kind`) доказательством не считается: `collect` тоже подтверждает лишь то, что перечислено в его сверке — L16B обещал восстановление данных, а проверял четыре факта из десяти. Поэтому метка стоит отдельным полем, которое видно в обзоре, а не выводится из вида.

Вердикт работы считает одна функция `labResult`; карточка, общая шкала и таблица прогресса берут его у неё. Считая каждая по-своему, они разошлись бы незаметно.

Критерии работы версионируются полем `criteria` (по умолчанию 1). Принятый отчёт помечается версией, по которой его проверили, и отчёт под прежним, более узким контрактом в практическую шкалу не идёт — он помечается и пересдаётся. Расширили сверку существующей работы — поднимите `criteria`.

Восстановление загрузки и комплексный инцидент целиком автоматической проверки пока не имеют; L36A/B — разбор подготовленных наблюдений, а не подтверждение восстановления. В книге это сказано прямо: засчитывать вместо стенда разбор данных нельзя.

Границу при этом описывайте честно и не расширяйте её в текстах: состояние лежит в браузере читателя, файл отчёта о работе — на его машине. Подделать результат можно, просто это требует почти всего решения; обещать невозможность подделки нельзя, и в README такое обещание уже стояло.

Состояние хранится в `localStorage` (10 ключей `server-infrastructure-*`). Любой новый ключ обязан попасть в `BACKUP_KEYS`, иначе перенос в другой браузер потеряет часть работы молча. Валидатор берёт ключи **из самого кода** — общего `site.js` и двух страниц со своим, кабинета и «Маршрута», — а не из списка рядом: список знал семь ключей из девяти и о десятом не сказал бы ничего. Один из ключей — `place-v1`, место чтения: адрес, заголовок, ближайший раздел и доля прочитанного. Пишется на страницах с прозой не чаще раза в секунду, читается только главной; адрес из хранилища перед подстановкой в ссылку проверяется, чтобы чужая запись не стала ссылкой куда угодно.

### Стенд главы 0 разворачивается скриптом

`scripts/stand/course-stand.sh` поднимает топологию главы 0 на хосте Proxmox VE: три моста без портов и адреса, шесть машин с адресами из плана главы. Правила у него те же, что у инжектора работ: **план по умолчанию** (аргумент `plan` ничего не меняет и работает даже не на Proxmox), каждое изменение идёт через одну функцию `run` — поэтому напечатанный план не может разойтись с тем, что произойдёт; занятые идентификаторы не перезаписываются; удаляются только машины со своей меткой; мост управления и чужие настройки хранилища не трогаются вовсе — скрипт называет команду и останавливается.

Адресный план лежит одной таблицей `STAND_NODES`, и валидатор сверяет её с таблицей главы 0 по составу адресов каждого узла: порядок в книге свой, он идёт от смысла интерфейса. Разъехавшись, скрипт и книга не ломают ни сборку, ни разметку — стенд поднимется, просто не тот, о котором написаны работы.

Проверять правки скрипта надо прогоном `selftest.sh`: он поднимает подставные `qm`, `pvesm` и `ip`, гоняет `plan` в десятке состояний хоста и утверждает результат. Половина того, что скрипт уже собрал, живого хоста не требовала вовсе — съехавшая нумерация слотов, пароль в напечатанной команде, диск cloud-init не в том слоте, — и ловится здесь. Главное его утверждение: **план не выполняет ни одной меняющей команды**; подставной `qm` пишет журнал вызовов, и обход функции `run` виден сразу. Чего он поймать не может, там же и сказано: `qm set`, молча принимающий несуществующий мост; облачное ядро, не видящее привод; cloud-init, уходящий в `apt` по мёртвой сети. Для этого есть `scripts/stand/task-local-proxmox.md` — задание сессии, запущенной рядом с настоящим Proxmox.

Прогон `plan` руками тоже остаётся: он выполняется где угодно и печатает каждую команду. Так нашлись пустой `import-from`, необъявленное имя в одном `local` под `set -u` и зашитое `eth0` в правиле трансляции — в гостях Proxmox внешний интерфейс называется иначе, и стенд остался бы без выхода в сеть.

У хоста может вообще не быть моста для внешней сети: управление живёт на обычном интерфейсе, и подключить к нему виртуальную машину нельзя. Перекладывать управляющий интерфейс в мост скрипт не смеет — это верный способ лишить человека доступа к его же хосту. Поэтому есть второй режим, `STAND_WAN_MODE=nat`: отдельный мост с адресом на хосте и трансляцией наружу, управляющий интерфейс не трогается вовсе. Топология стенда не меняется, меняется только то, как маршрутизатор виден снаружи.

Запуск на настоящем хосте дал ещё одно, и самое дорогое: **`qm set` принимает несуществующий мост молча**. Отказ всплывает только на `qm start`, когда машина уже создана и идентификатор занят. Поэтому имя моста управления не зашивается (`vmbr0` — частое, но не обязательное): оно берётся из маршрута по умолчанию хоста, проверяется до создания машин, а мосты стенда сверяются с `/sys/class/net` после перезагрузки сети. Прерванная сборка вдобавок говорит, что недоделанное убирается аргументом `destroy`.

Прочитанный план с настоящего хоста дал ещё три: `--vga serial0` гасит кнопку «Console» в веб-интерфейсе, и первый гипервизор выглядит сломанным; список `packages` в cloud-init выполняется один раз и без повторов, а пять узлов в этот момент ждут, пока router поднимет трансляцию, — поэтому пакеты ставит сценарий с ожиданием связи, а не `packages`; `import-from` появился в Proxmox VE 8, и на семёрке нужен внятный отказ, а не непонятая команда. Порядок запуска тоже часть контракта: router стартует первым, остальные — только когда он готов.

Сквозной прогон на Proxmox VE 9.1 добавил к этому главное: **штатный апгрейд cloud-init подрывает весь замысел с ожиданием связи**. Proxmox по умолчанию ставит `ciupgrade=1`, то есть `package_upgrade: true` в user-data, а модуль, который это исполняет, идёт в `cloud_final_modules` раньше `scripts-user` — раньше нашего `runcmd`. Гость, запущенный за пятнадцать секунд до того, как router поднял трансляцию, ушёл в `apt-get update` по неработающей сети и провисел в нём двадцать минут: apt не отваливается по таймауту сам, cloud-init не идёт дальше, машина «running», `qm agent ping` молчит, и ни в выводе `create`, ни в журнале хоста нет ни строки. Поэтому скрипт выключает апгрейд (`--ciupgrade 0`, параметр есть с Proxmox VE 8.2 — наличие спрашивается у `qm help set --verbose`), а у apt в сценарии гостя заданы таймауты и повторы.

Отсюда же второе: слепой паузы после запуска router не хватало и не могло хватать — трансляцию он поднимает после установки пакетов, то есть через две-три минуты. Ждём признак, а не время: агент router отвечает только после того, как трансляция готова, потому что ставится последней командой сценария. По той же причине агент не входит в общий список пакетов — иначе он отвечал бы с середины настройки, и оба признака готовности (`status` и ожидание router) стали бы ложными.

Третье, из того же прогона: `serial=` у диска попадает на страницу VPD 0x80, а udev строит имена в `/dev/disk/by-id` по странице 0x83, куда QEMU кладёт имя слота. Без `wwn=` учебные диски `storage` видны там как `scsi-0QEMU_QEMU_HARDDISK_drive-scsi1` — то есть именно как номер слота, от которого упражнение главы про устойчивые имена отучает; в `lsblk` серийник при этом виден, и расхождения не заметить. Буквы `sd*` на этом стенде переставляются при каждой перезагрузке — проверено, так что упражнение не умозрительное.

## Что сломается незаметно (и потому закреплено проверками)

Валидатор ловит именно те дефекты, которые не видны ни в сборке, ни в разметке. Прежде чем спорить с ним, прочитайте комментарий рядом с правилом — там записан случай, из-за которого оно появилось.

- **Изменили заголовок или добавили раздел** → `node scripts/text-nodes.mjs synctoc`, иначе оглавление разойдётся с текстом.
- **Добавили или убрали страницу** → в валидаторе зашито ожидаемое число маршрутов (48). Число маршрутов, число страниц в офлайн-копии и охват индекса поиска — три разные величины: `/book/` намеренно исключён из двух последних, и они равны 47. Сверяйте каждую со своим источником, а не одну с другой.
- **Списки markdown внутри `<p>`** (`- пункт` с новой строки) браузер схлопывает в одну строку; в разметке это незаметно.
- **Уровни заголовков** не перепрыгивают ступень, страница не кончается заголовком без текста, навигация по разделам совпадает с `h2` по составу и порядку.
- **Раскладка**: ширина страницы задана через `--page` (её же использует верхняя панель), ширина строки — через `width:min(100%,900px,var(--reading-measure))` (не `max-width`: иначе текст не замечает узкой колонки и уезжает под рейл), рейл разделов встаёт сбоку не раньше 1500px, `hyphens:manual` (автоперенос рвёт обычные слова ради плотности строки).
- **Приложение A**: разделы A.1–A.24, и у каждой команды, меняющей состояние, в её разделе стоит «Осторожно». Справочник читают наискось.
- **Позиция верного варианта**: добавляя задание, не ставьте верный ответ первым по привычке. Один раз так собрался весь банк — и все 74 задания, все вторые ярусы и все 148 шагов сценариев проходились выбором первого варианта. В разметке это не видно; распределение закреплено проверкой.
- **Недельный план** в предисловии — единственное место, где курс разложен по времени. Он уже расходился с книгой: таблица осталась на 28 позициях старой нумерации, когда модулей стало 37. Проверка требует, чтобы все 37 модулей стояли в плане ровно по разу.
- **Мост «глава → модуль»**: строка «Академическое продолжение этой главы: UNN» должна называть ровно те модули, которые физически лежат внутри главы. При двойной нумерации это единственная подсказка читателю, а расхождение в разметке невидимо.
- **Обращение**: книга говорит читателю «вы» — не только местоимениями. Команды («создай», «переходи дальше») и глаголы второго лица («пока не можешь ответить») проверяются тоже: формы множественного числа берутся из самой книги, поэтому «создай» ловится, если где-то есть «создайте». «Ты» допустимо только в прямой речи в кавычках — вопрос к ядру, чужая формулировка задачи.
- **Устоявшийся перевод**: если для слова в книге уже есть русский вариант (следующий узел, перечисление, оконечное устройство, райзер, экспандер, перехват, прошивка, плоскость управления), английский оригинал в прозе и в банке заданий считается ошибкой. Имена объектов и параметров (Endpoints, capture_output, firmware volume) — исключения, они перечислены рядом с правилом.
- **Работы практикума** делает один человек за одним стендом: «студент» и «учащийся» в описаниях работ L00–L36 запрещены (в экзаменационных рубриках ниже — нет).
- **Справочник терминов** (`public/reference-terms.json` плюс приложение C) обязан покрывать частые слова: латинское слово, встречающееся в прозе не реже десяти раз, должно иметь определение. Панель «Определение» — единственная помощь читателю, наткнувшемуся на незнакомое слово, а база успела отстать от текста: в ней были `pstore` и `Machine Check`, но не было VM, GiB, CPU и RTO. Проверка спрашивает **ту самую `defLookup` из `site.js`**, которой отвечает панель, а не разбирает термины сама: свой разбор засчитывал слово, встреченное частью составного термина, — «TCP» считался определённым через «TCP handshake», а панель на выделенное «TCP» отвечала «Определения нет». Так прошли мимо Linux, systemd, Python и Docker. Составные термины базы вычёркиваются из текста до подсчёта (иначе статья требовалась бы на каждое слово из «Secure Boot» и «Load average»), а подписи внешних ссылок прозой не считаются.
- **Политика безопасности**: страницы несут `Content-Security-Policy` в `<meta>` (заголовки GitHub Pages задать не даёт). Из-за этого атрибут `style="…"` и обработчик `onclick="…"` в разметке перестают работать — молча, без следа в разметке: выравнивание столбца просто пропадает. Выравнивание чисел в таблицах задаётся классом `num`. Хеши встроенных скриптов считаются по готовой странице (`sealPolicy` в генераторе, уже после подстановки `BASE_PATH`), поэтому политика не может разойтись с содержимым.
- **Скрипт, ищущий чужой элемент**: встроенный скрипт падает на первой же строке и уносит всё, что идёт ниже. Так на `/assessment/a1/` не работали все 40 вопросов: скрипт из `course.html` начинался с фильтра оглавления, которого на этой странице нет. Обращение к элементу с соседней страницы пишется через `?.`, иначе проверка не пропустит.
- **Две шкалы не сливаются**: работа вида `dataset` не может нести `bench`, у стендовой работы обязаны быть цепочка и фраза о границах, а числа «65 без стенда» и «9 со стендом» в прозе сверяются с данными. Слитый счёт выглядит в разметке ровно так же, как раздельный.
- **Скрипт стенда и глава 0**: адреса, имена узлов и мосты сверяются между `STAND_NODES` и таблицей главы; строка `curl` из книги обязана вести в существующий файл; в скрипте обязаны остаться план по умолчанию, отказ на занятых идентификаторах, пропуск машин без метки при удалении, неприкосновенный мост управления, ожидание связи в настройке гостя, рабочая графическая консоль, вычисление моста управления вместо зашитого имени, проверка всех мостов до запуска машин, выключенный апгрейд cloud-init, ожидание готовности router вызовом `wait_router` (а не паузой), агент последней командой настройки и WWN у учебных дисков. Вызов ищется именно вызовом: оставшаяся в файле функция выглядит в тексте скрипта так же, как работающая, а сборка при этом снова идёт по слепой паузе. Флаг ищется в команде, а не где угодно в файле: в комментарии рядом он назван тем же текстом, и проверка вхождения срабатывала на объяснении.
- **Автопроверка работ**: инжектор — единственное место в проекте, которое меняет чужую машину, поэтому у скрипта обязаны быть отказ без метки `/etc/course-lab-stand`, `restore`, `--dry-run` и неприкосновенная управляющая сеть; сбор фактов и вердикт разделены; ожидаемые значения в `lab-data` лежат только хешами; каждая работа ссылается только на существующие операции сверки и заведена в реестре `course_lab.py`; сверка по хешу требует самого хеша; текст работы лежит на той же странице; верные объяснения не стоят все на одном месте — тот же урок, что и с банком заданий. Результаты работ живут внутри ключа прогресса, поэтому переносятся вместе с ним; отдельный ключ пришлось бы вносить в `BACKUP_KEYS`.
- **Каркас главы**: вопрос до чтения стоит выше раздела N.1, свободное воспроизведение — до мини-тренажёра, темы воспроизведения начинаются неотмеченными, верный ответ тренажёра не печатается в разметку.
- **Вопросы мини-тренажёра не повторяют банк кабинета**: у каждой из 34 глав ровно два слота, в каждом пул от двух вопросов по четыре варианта с разбором, и ни один не совпадает по тексту с заданием банка. Верные ответы распределены по позициям — тот же урок, что и с банком.
- **Промах не открывает ответ**: подсветка верного варианта и разбор ставятся ровно в двух местах кода (верный ответ и восстановленная отметка), пул слота не бывает из одного вопроса, и все варианты пула доезжают до страницы — подмена идёт без сети. В разметке разница не видна: подсветку ставит класс, разбор берётся из `data`-атрибута, и оба места выглядят одинаково при любом исходе. Поведение закреплено ещё и обходом браузера: промах не должен ни подсветить, ни объяснить, но обязан сменить вопрос.
- **Одно написание — одна статья справочника**: индекс панели («Определение») занимает ключ первым совпадением и молча отбрасывает второе. «mac» отвечал статьёй Ethernet вместо «MAC-адрес», «плейбук» — статьёй YAML вместо Ansible, а Timeout и «Тайм-аут» были двумя статьями об одном понятии, из которых читатель видел одну. Ни в сборке, ни в разметке это не видно: панель просто отвечает не тем. Повтор написания внутри одной статьи безвреден и правилом не ловится.
- **Перенос прогресса один на весь курс** и живёт на `/route/#route-backup`: он собирает все восемь ключей. Своя кнопка экспорта в кабинете уносила один ключ из восьми — мини-тренажёры глав, календарь, заметки и настройки чтения оставались в старом браузере, хотя файл выглядел полноценной копией. Кабинет только ведёт на «Маршрут» (адрес подставляется в `studyScript`, как и `#autopractice`).
- **Единственное число повелительного наклонения** ловится двумя способами: по паре из самой книги («создайте» → «создай») и по списку `ORDERS` в валидаторе. Список нужен потому, что глагол, употреблённый на «ты» один-единственный раз, пары в книге не имеет: «привяжи API к loopback» в лаборатории 22.14 пережило две вычитки и правило.

## Публикация

`.github/workflows/pages.yml` собирает и публикует при push в `main`; `BASE_PATH` он выбирает сам по имени репозитория. Действия закреплены хешами коммитов, а не тегами (тег можно передвинуть); номер версии стоит комментарием рядом, хеш берётся через `git ls-remote --tags`. Каталог `build/` в Git не хранится.
