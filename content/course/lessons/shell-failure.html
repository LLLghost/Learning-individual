Обрабатывать отказ команды и ограничивать ожидание

Результат: Остановить слишком долгую команду и обработать её код завершения.

Объект: Страница заметок и выделенные ресурсы текущего опыта.

Разберёмся до действия

Код завершения — числовой результат процесса; 0 обычно обозначает успех по контракту программы. stdout и stderr передают данные независимо от кода. В Bash set -e имеет исключения и не заменяет явную обработку ожидаемых отказов. Pipefail меняет код конвейера, но не откатывает выполненные действия. GNU timeout ограничивает длительность и обычно возвращает 124 при срабатывании; специальные режимы и сигналы имеют другие коды. Повторы допустимы только при понятной идемпотентности и ограниченном числе попыток.

Среда и права: В учебном Linux-госте обычным пользователем; sudo требуется только для явно указанных изменений. Данные примера можно разбирать без стенда.

Разобранный пример

Команды примера; переменные WORK и NS задаются в инструкции практики ниже:

timeout 1 sleep 30
printf "код: %s\n" "$?"

Ожидаемый результат: В интерактивной оболочке без set -e после примерно секунды виден код 124. Неуспех здесь ожидается и является предметом опыта.

Сопоставь наблюдение с описанным механизмом. Вывод относится к проверенному объекту и условиям опыта.

При отклонении: При несовпадении результата сохрани фактический вывод, проверь предпосылки и остановись перед дальнейшими изменениями. Не подменяй наблюдение ожидаемым текстом.

Прогноз и опыт с поддержкой

Предскажи отличие ненулевого кода от отсутствующего stdout. Подготовь shell-failure, сначала проверь $? вручную, затем сохрани обработку в solution.sh: предел ожидания приходит первым аргументом. Следующая команда меняет $?, поэтому код запоминают сразу.

Практическое углубление: Скрипт диагностики должен быть безопасным по умолчанию

У рабочего диагностического инструмента есть требования, которых нет у одноразовой команды из истории оболочки:

  • по умолчанию только чтение;
  • явные ограничения по времени;
  • отсутствие зависания на одном недоступном устройстве;
  • поток ошибок не теряется;
  • код возврата отражает результат;
  • в выводе есть время и имя хоста;
  • чувствительные данные не попадают в отчёт случайно;
  • разрушающий режим, если он вообще существует, включается отдельным флагом.

Поэтому хороший скрипт оболочки начинается не с количества grep, а с контракта: что он читает, что изменяет, какой вывод обещает и как сигнализирует о частичном отказе.
