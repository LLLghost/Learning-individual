Найти ошибку в длине сетевого префикса

Результат: Исправить длину префикса на выделенном интерфейсе и проверить маршрут.

Часть общей системы: Граница локальной подсети и необходимость маршрута.

Что сохранить в инженерном журнале: Проверка принадлежности адресов подсети.

Разберёмся до действия

Префикс /24 оставляет восемь бит для адресов внутри сети, /32 обозначает один IPv4-адрес. Подключённый маршрут зависит от адреса и длины префикса интерфейса. Слишком широкий префикс может заставить узел искать удалённый адрес через ARP вместо шлюза; слишком узкий — лишить маршрута до соседа. Для 10.8.3.190/26 сеть равна 10.8.3.128, broadcast — 10.8.3.191, обычные адреса узлов — .129–.190. Это правило нельзя механически переносить на /31, /32 или IPv6.

Среда и права: В учебном Linux-госте обычным пользователем; sudo требуется только для явно указанных изменений. Данные примера можно разбирать без стенда.

Разобранный пример

Команды примера; переменные WORK и NS задаются в инструкции практики ниже:

sudo ip -n "$NS-a" -br address
sudo ip -n "$NS-a" route get 192.0.2.2

Ожидаемый результат: После подготовки prefix узел a имеет 192.0.2.1/32 и не имеет обычного подключённого маршрута к .2. После замены на /24 появляется прямой путь.

Сопоставь наблюдение с описанным механизмом. Вывод относится к проверенному объекту и условиям опыта.

При отклонении: При несовпадении результата сохрани фактический вывод, проверь предпосылки и остановись перед дальнейшими изменениями. Не подменяй наблюдение ожидаемым текстом.

Прогноз и опыт с поддержкой

Предскажи результат route get при /32. Удали только учебный адрес /32 и добавь тот же адрес /24 внутри namespace a. Повтори маршрут и ping. Не исправляй опыт обходным host route.

M06-2: Адрес и маршрут добавили только командами ip, а постоянную конфигурацию сети не меняли. Почему эти команды сами по себе не обещают сохранение адреса после перезагрузки?

Команды ip меняют текущее состояние, а не файлы. После перезагрузки интерфейс настраивает та служба, которая описана в системе: ifupdown, systemd-networkd, NetworkManager или cloud-init. Проверка настройки — это перезагрузка либо перечитывание конфигурации, а не взгляд на вывод ip addr. Состояние ядра не сохраняется само, его восстанавливает служба по своим файлам.

В данном сценарии слишком широкий подключённый префикс выбрал прямой маршрут. Ядро разрешает соседа после выбора маршрута. В других настройках такой же ARP возможен из-за явно on-link маршрута; один пакет не доказывает единственную причину. Применение к описанным условиям: Потому что адрес попал в собственную подсеть.

Углубление: Префикс — правило выбора пути

Префикс — правило выбора пути

В IPv4 префикс /n оставляет n старших бит адреса для сети. В обычной подсети /24 меняется восемь младших бит. Побитовое AND с маской даёт адрес сети. Broadcast — адрес с единицами в битах хоста. Правило «минус два адреса» не универсально: /31 имеет специальное применение на двухточечных линиях, /32 описывает один адрес.

Одинаковые адреса с разными масками могут дать разное решение о локальности. Более специфичный маршрут выигрывает у default даже при непохожем на ожидание шлюзе. CIDR позволяет описывать диапазоны разной длины; суммирование диапазонов допустимо только при правильном выравнивании и полном охвате.

Другие условия: разобранный случай

Даны наблюдения: Для 192.0.2.130/26 сеть — 192.0.2.128, broadcast — 192.0.2.191.

Разбор: Блок содержит 64 адреса; обычный диапазон хостов — .129–.190. Адрес .126 находится в другом /26, хотя первые три октета совпадают.

Это учебные данные, а не протокол выполненного действия.
