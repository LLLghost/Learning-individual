Понять, кому компьютер отправляет пакет

Результат: Определить следующий узел для конкретного IP-адреса.

Объект: Страница заметок и выделенные ресурсы текущего опыта.

Разберёмся до действия

IP-адрес обозначает сетевой интерфейс в адресном плане. Префикс описывает диапазон адресов. Таблица маршрутов выбирает путь: в выбранной таблице используется наиболее длинный подходящий префикс. Для непосредственного соседа Ethernet нужен его MAC; для адреса за маршрутизатором — MAC следующего узла. ARP находит IPv4-соседа только в своём сегменте. Маршрутизатор создаёт новый кадр для следующего участка. NAT может дополнительно менять IP-адреса, поэтому неизменность адреса назначения нельзя обещать для любого пути.

Среда и права: В учебном Linux-госте обычным пользователем; sudo требуется только для явно указанных изменений. Данные примера можно разбирать без стенда.

Разобранный пример

Команды примера; переменные WORK и NS задаются в инструкции практики ниже:

sudo ip -n "$NS-a" route get 192.0.2.2
sudo ip -n "$NS-a" neigh show

Ожидаемый результат: В опыте address путь к 192.0.2.2 идёт через eth0 без via. После обмена таблица соседей может содержать MAC второго узла.

Сопоставь наблюдение с описанным механизмом. Вывод относится к проверенному объекту и условиям опыта.

При отклонении: При несовпадении результата сохрани фактический вывод, проверь предпосылки и остановись перед дальнейшими изменениями. Не подменяй наблюдение ожидаемым текстом.

Прогноз и опыт с поддержкой

До ping предскажи, чей MAC понадобится. Подготовь address, прочитай маршрут, выполни один ping внутри namespace a и повтори neigh. Сохрани маршрут в route.txt.

Самостоятельная задача

Для клиентского адреса стенда и сервера в другой подсети нарисуй один кадр и один IP-пакет: MAC назначения шлюза и IP назначения сервера. Проверь фактический маршрут, не добавляя маршруты на основной ВМ.

Механизмы для заданий углубления

Прочитай механизм до решения. Вопросы и варианты ответов сверены с этими объяснениями; сохранены идентификаторы прежних заданий. Полная редактура подробных разборов прежнего издания отмечена отдельно.

M06-0: Хост отправляет пакет за пределы локальной подсети через обычный шлюз. Для кого выполняется ARP?

Кадр L2 доставляется соседу, который продолжит IP-маршрутизацию. Кадр адресуется соседу в сегменте, адрес назначения сетевого уровня не меняется.

M06-1: Есть маршруты /16 и /24 в одной применимой таблице; оба совпали. Какой принцип выбора?

Самое длинное совпадение префикса действует внутри выбранной таблицы; policy routing отдельно выбирает таблицу. Из совпавших маршрутов одной таблицы выбирается самый специфичный.

C06-0: В обычной IPv4 Ethernet-сети IP назначения уже известен. Как определяют, нужен MAC адресата или шлюза?

Сначала выбирается маршрут в применимой таблице с учётом policy routing. В обычном прямом маршруте ARP разрешает адрес конечного соседа, в маршруте via — адрес следующего узла. Прокси-ARP и явно on-link маршруты требуют отдельного чтения конфигурации. Применение к описанным условиям: Выбирают маршрут и следующий узел: прямой сосед или шлюз.

C06-0b: От чего зависит, чей адрес второго уровня нужен машине для отправки пакета?

Для локального адресата нужен его собственный адрес второго уровня, для удалённого — адрес следующего узла. Маршрут выбирается по наиболее специфичному префиксу. Применение к описанным условиям: От того, в том же сегменте адресат или за его пределами.

C06-1: Почему неудачный ping до шлюза не указывает на неисправность шлюза?

Успешный ping до соседа требует одновременно поднятой линии, верного VLAN, разрешения адреса второго уровня, совпадающего префикса и отсутствия фильтрации. Неудача не говорит, какое из условий нарушено. Применение к описанным условиям: Он означает лишь, что эхо-ответ не вернулся.

C06-1b: Что должно совпасть одновременно, чтобы ping до соседа прошёл?

Неудача не говорит, какое из условий нарушено, — и уж точно не указывает на неисправность соседа. Применение к описанным условиям: Линия, VLAN, разрешение адреса, префикс и фильтрация.

S4-0: Почему при разборе маршрутизации нужно различать IP назначения и Ethernet-адрес следующего узла?

На маршрутизируемых Ethernet-переходах формируются новые кадры для следующего узла. Обычный L2-коммутатор не заменяет адреса кадра при каждом пересылании. NAT может менять IP-адреса, поэтому неизменность IP относится к пути без такой трансляции. Применение к описанным условиям: IP выбирает сетевое назначение, а кадр доставляется соседу на текущем участке.

S4-0b: Что происходит с адресами назначения на следующем маршрутизируемом Ethernet-участке обычного IP-пути без NAT?

Речь о новом канальном участке после маршрутизатора, не о каждом коммутаторе. Другие поля IP, например TTL/Hop Limit, меняются; условие без NAT ограничивает утверждение об адресах. Применение к описанным условиям: Создаётся кадр к следующему соседу, а IP назначения сохраняется.

S4-1: Зачем в TCP/UDP используется порт, если IP адресата уже известен?

ОС сопоставляет протокол, адреса и порты с сокетами. Порт помогает выбрать службу, но сам по себе не является универсальным идентификатором одного процесса; возможны прокси и совместное обслуживание. Применение к описанным условиям: Чтобы вместе с протоколом и адресами различать транспортные конечные точки служб.

S4-1b: Две службы на одном IP используют разные TCP-порты. Какое поле назначения различает обращения к этим двум конечным точкам?

В заданном случае IP совпадает, а порты различаются. Имя сайта или прикладной заголовок может решать дополнительные задачи уже после доставки к транспортной конечной точке. Применение к описанным условиям: TCP-порт назначения.

L06A#why: Почему ARP спрашивает про 10.10.10.1, хотя пинг идёт на 10.10.20.12?

В обычном маршруте через шлюз ARP разрешает адрес следующего Ethernet-соседа. ARP конечного адреса может следовать из слишком широкого префикса или явно заданного on-link маршрута; для вывода нужно читать route get, а не только пакет ARP. Применение к описанным условиям: Потому что адрес второго уровня нужен для одного шага.

Урок 4. Сеть: как одна машина находит другую

Задача, которую решает сеть

Две машины соединены проводом. Первая хочет отправить второй порцию данных. Кажется, что задача решена самим проводом — но машин не две, а миллиарды, провод между каждой парой не протянуть, и почти всегда между отправителем и получателем стоит десяток чужих устройств.

Отсюда три вопроса, на которые сеть отвечает разными механизмами: как назвать получателя, как найти к нему путь и как понять, какой программе на нём предназначены данные. Дальше — по одному разделу на каждый.

Адрес: почему их два

У машины в сети два разных адреса, и это регулярно сбивает с толку.

Аппаратный адрес (его называют MAC-адрес) намертво привязан к сетевой карте и не меняется при переезде. Он работает только внутри одного участка сети — там, где устройства соединены напрямую и слышат друг друга.

Сетевой адрес (IP-адрес) выдаётся машине по месту подключения и меняется при переезде в другую сеть. Именно он позволяет добраться до машины через весь мир.

Разделение выглядит избыточным, пока не задать вопрос, как доставить данные машине, о которой известен только IP-адрес. Ответ: по дороге адрес пересчитывают. Каждый участок пути использует аппаратные адреса своих соседей, а сетевой адрес остаётся неизменным от начала до конца. Механизм перевода одного в другой — протокол ARP, и в главе 6 он разбирается подробно; сейчас важно запомнить, что аппаратный адрес отвечает за один шаг, а сетевой — за весь маршрут.

Здесь бытовая аналогия ломается, и стоит сказать об этом прямо. Почтовый адрес не меняется, когда письмо переходит из рук в руки; в сети адрес следующего шага пересчитывается на каждом устройстве. Держаться за картинку с конвертом дальше вредно.

Имя вместо адреса

Люди не помнят числа вида 93.184.216.34, поэтому пользуются именами. Служба, которая переводит имя в адрес, называется DNS.

Работает она как справочная: машина спрашивает «какой адрес у этого имени», получает ответ и запоминает его на время. Важное следствие — ответ может устареть. Если адрес поменяли час назад, а машина помнит старый, она будет упорно стучаться не туда. Это одна из самых частых причин ситуаций «у меня не работает, а у коллеги работает».

Практический вывод для диагностики: «сайт не открывается» и «имя не разрешается в адрес» — разные поломки. Проверять их надо по отдельности, и первый же вопрос при разборе — получила ли машина адрес вообще. Глава 7 разбирает это с командами.

Маршрут: почему данные идут шагами

Прямого провода до получателя нет. Данные идут через цепочку устройств, каждое из которых решает одну маленькую задачу: кому передать дальше.

Решение принимается по таблице маршрутизации — списку правил вида «данные для такого-то диапазона адресов отдавать такому-то соседу». Правило по умолчанию («всё остальное — вот туда») называется шлюзом по умолчанию, и в домашней сети это роутер.

Два следствия, полезных сразу.

Во-первых, машина без правильного шлюза видит соседей по своей сети и не видит ничего за её пределами. Симптом характерный: локальные адреса отвечают, всё внешнее — нет.

Во-вторых, путь туда и путь обратно могут различаться. Поэтому «я отправил, но ответа нет» не означает, что проблема на стороне отправителя: сломанным может быть обратный путь. Это одна из причин, по которой в главе 1 так подчёркивается разница между наблюдением и его толкованием.

Порт: одна машина, много служб

На одной машине одновременно работают веб-сервер, почтовая служба и база данных. Данные пришли по её адресу — какой из программ они предназначены?

Для этого к адресу добавляют число — порт. Программа, ожидающая обращений, занимает определённый порт, и данные с этим номером достаются именно ей. Часть номеров закреплена по соглашению: 22 — SSH, 80 — веб без шифрования, 443 — веб с шифрованием, 5432 — PostgreSQL.

Пара «адрес и порт» полностью определяет собеседника. Отсюда точная формулировка того, что обычно называют «не работает сеть»: если адрес отвечает, а порт закрыт — сеть в порядке, не работает программа или её не пускает межсетевой экран.

Четыре разные поломки под одной жалобой

Фраза «нет сети» покрывает как минимум четыре разных состояния, и лечатся они по-разному.

  1. Нет связи на уровне провода. Кабель, порт коммутатора, выключенный интерфейс. Признак: машина не видит вообще никого, даже ближайшего соседа.
  2. Нет адреса или он неверный. Машина подключена, но не получила настроек либо получила чужие. Признак: соседи не отвечают, хотя связь есть.
  3. Нет маршрута наружу. Соседи по своей сети отвечают, всё за её пределами — нет. Признак самый узнаваемый из всех.
  4. Не отвечает конкретная служба. Машина доступна, отвечает на проверки, но нужный порт закрыт. Признак: одно приложение не работает, остальные работают.

Смысл этого списка не в том, чтобы его выучить, а в том, чтобы увидеть приём: жалобу разбирают по слоям и ищут границу между работающим и неработающим. Это главный инструмент всей книги, и глава 1 посвящена ему целиком.

Показать разбор

Разбор. 1) Аппаратный адрес нужен для одного шага между соседями, сетевой — для всего маршрута; на каждом шаге адрес следующего соседа пересчитывается заново. 2) Устаревший ответ службы имён: ваша машина помнит старый адрес. Проверять начинают с того, в какой адрес у вас разрешается имя. 3) Да, сеть работает: адрес достижим. Не работает программа, слушающая нужный порт, либо её закрывает межсетевой экран. 4) Отсутствующий или неверный шлюз по умолчанию — правило «всё остальное отдавать туда».

6.1. Почему «IP настроен» почти ничего не гарантирует

Интерфейс может иметь IP-адрес и при этом не иметь линии связи. Линия может быть поднята, но соседний порт коммутатора находиться в другом VLAN. Второй уровень может работать, но маршрут отсутствовать. Маршрут может быть правильным, но шлюз не разрешается через ARP. Даже после успешной доставки по IP нужный порт TCP может быть закрыт.

Поэтому полезно мыслить слоями:

physical link
   ↓
Ethernet frame
   ↓
VLAN / broadcast domain
   ↓
ARP / neighbor resolution
   ↓
IP addressing
   ↓
routing decision
   ↓
TCP/UDP
   ↓
application

6.2. Кадр Ethernet и MAC-адрес

В локальном сегменте Ethernet доставка происходит кадрами, содержащими MAC-адрес источника и назначения. Коммутатор обучается, на каком порту он видел адрес источника, и использует таблицу пересылки для последующих кадров.

MAC-адрес не заменяет IP. Это адреса разных уровней и областей действия. IP нужен для маршрутизации между сетями; MAC-адрес назначения на каждом маршрутизируемом переходе меняется на адрес следующего получателя второго уровня.

6.4. ARP: как IP превращается в адрес назначения второго уровня

Если адрес назначения считается локальным, хосту нужен MAC-адрес получателя. Для IPv4 он использует ARP.

Схема:

Host A: Who has 192.168.10.50? Tell 192.168.10.34
                ↓ broadcast
Host B: 192.168.10.50 is at 52:54:00:aa:bb:cc
                ↓ unicast reply
Host A stores neighbor entry

Проверка:

ip neigh

Состояния вроде REACHABLE, STALE, DELAY, FAILED, INCOMPLETE дают диагностическую информацию. INCOMPLETE означает, что разрешение ещё не завершено; устойчивый FAILED заставляет искать проблему на втором уровне, в VLAN, линии связи или на удалённом хосте.

Наблюдение:

tcpdump -ni eno1 arp

Если запрос ARP уходит, но ответа нет, маршрут до локального получателя уже не главная проблема.

6.5. Шлюз — следующий узел, а не «сервер интернета»

Для адреса за пределами локальной сети хост выбирает маршрут со следующим узлом. Затем ARP выполняется не для конечного удалённого IP, а для адреса следующего шлюза в локальном сегменте.

Адрес назначения IP сохраняется как 8.8.8.8; получателем Ethernet на первом переходе будет маршрутизатор.

6.6. Таблица маршрутизации и самый длинный совпадающий префикс

Пример:

10.0.0.0/8 via 192.168.1.1
10.20.0.0/16 via 192.168.1.2
10.20.30.0/24 via 192.168.1.3
default via 192.168.1.254

Для 10.20.30.77 подходят первые три и маршрут по умолчанию. Выбирается самый специфичный префикс — /24.

Проверить решение ядра:

ip route get 10.20.30.77

Это часто полезнее визуально искать строку в ip r, особенно при маршрутизации по политикам и множестве таблиц.

Метрика обычно помогает выбирать между маршрутами одинаковой специфичности, но полная модель маршрутизации Linux может включать правила политик и несколько таблиц.

ip rule
ip route show table all

6.7. Адрес источника тоже выбирается

У хоста с несколькими интерфейсами несколько адресов. Для исходящего соединения ядро выбирает маршрут и адрес источника. Это влияет на обратный путь, правила межсетевого экрана и асимметричную маршрутизацию.

ip route get показывает и это:

ip route get 203.0.113.10

При сложных системах полезно задавать источник явно:

ip route get 203.0.113.10 from 192.168.50.20

6.8. Состояние линии связи

Проверка:

ip -br link
ethtool eno1

Административное состояние UP и физическая несущая — не одно и то же. Интерфейс может быть административно поднят, но LOWER_UP отсутствовать из-за физической линии.

6.9. Кто задаёт адрес после перезагрузки

Все команды этой главы — ip addr, ip route, ip neigh — показывают и меняют текущее состояние ядра. Оно живёт до перезагрузки и ни в каком файле не хранится. Отсюда две ошибки, которые делают все по одному разу: настройка, потерянная при перезагрузке, и настройка, вернувшаяся после того, как её убрали.

Постоянную конфигурацию задаёт отдельная служба, и в разных системах она разная:

  • ifupdown — /etc/network/interfaces. Так устроены Debian и Proxmox VE, в том числе гипервизор вашего стенда: мосты vmbr10, vmbr20, vmbr30 описаны именно там. Применение — ifreload -a (Proxmox) или ifup/ifdown по интерфейсу.
  • systemd-networkd — файлы *.network в /etc/systemd/network/. Типичен для минимальных серверных образов и контейнеров. Применение — networkctl reload, состояние — networkctl status.
  • NetworkManager — профили соединений, nmcli connection. Обычен в RHEL-семействе и на рабочих станциях. Применение — nmcli connection up, состояние — nmcli device status.
  • cloud-init — задаёт настройку один раз, при первой загрузке машины, и пишет её в формат той службы, которая в системе есть. Так адреса попали в гостей вашего стенда: qm cloudinit dump 9001 network на гипервизоре покажет источник.

Как узнать, что действует у вас. Не по названию дистрибутива, а по тому, что запущено:

systemctl is-active networking systemd-networkd NetworkManager
ls /etc/network/interfaces /etc/systemd/network/ 2>/dev/null
nmcli device status 2>/dev/null

Ответ «активны две» тоже бывает, и это худший случай: две службы спорят за один интерфейс, адрес то появляется, то исчезает, а причина ищется в кабеле. Одна машина — одна служба управления сетью.

Проверка, которая экономит выезд. Настройку, введённую командой, проверяют перезагрузкой, а не взглядом. На удалённой машине это делают иначе: применяют конфигурацию, не разрывая текущий сеанс, и держат наготове откат. В Proxmox для этого есть ifreload -a, в systemd-networkd — networkctl reload, а самый простой страховочный приём — отложенный откат, поставленный до опасной правки:

sudo sh -c 'sleep 300 && cp /etc/network/interfaces.bak /etc/network/interfaces && ifreload -a' &
# правите и применяете; если связь не потеряна — снимаете откат:
sudo pkill -f 'sleep 300'

Ошибка мышления. «Я же добавил адрес, почему после перезагрузки его нет» — это не отказ сети, а разница между состоянием ядра и конфигурацией службы. И обратная ошибка: «я удалил адрес командой, а он вернулся» — значит команда изменила состояние, а файл остался прежним, и служба восстановила описанное в нём при следующем применении.

6.10. Спросить ядро, а не гадать: ip route get

Решение о следующем узле принимается по таблице маршрутов, и его можно не выводить в уме — ядро отвечает прямо. Два вопроса подряд с одной машины:

ip route get 10.10.20.12
ip route get 1.1.1.1
10.10.20.12 dev eth0 src 10.10.20.30
1.1.1.1 via 10.10.20.1 dev eth0 src 10.10.20.30

В первой строке нет слова via — адрес признан локальным, и кадр уйдёт прямо соседу, чей аппаратный адрес найдёт ARP. Во второй via 10.10.20.1 — пакет пойдёт шлюзу. Ответ включает и третье: src, то есть какой адрес источника будет подставлен. Именно этот вывод отвечает сразу на три вопроса, которые обычно задают по отдельности.

Сама таблица короткая и читается снизу вверх по длине префикса:

ip -4 route show
default via 10.10.20.1 dev eth0 proto static
10.10.20.0/24 dev eth0 proto kernel scope link src 10.10.20.30

Запись с scope link появилась сама при назначении адреса — это и есть «своя» сеть; default — маршрут для всего остального. Поле proto говорит, кто маршрут поставил: kernel — ядро при настройке адреса, static — конфигурация, dhcp — клиент DHCP. При разборе «откуда взялся этот маршрут» это первое, что смотрят.

Состояние соседей — отдельная таблица со своим жизненным циклом:

ip -4 neigh show
10.10.20.1 dev eth0 lladdr bc:24:11:94:8b:a9 STALE

STALE не означает проблему: запись верна, но давно не подтверждалась, и ядро проверит её при следующей отправке. Тревожны два других состояния: INCOMPLETE — запрос ушёл, ответа нет (сосед не отвечает или его нет в этом сегменте), и FAILED — разрешение не удалось. Именно эту разницу и проверяет работа практикума L06B.

6.11. Разобранный пример: шлюз не пингуется

Ситуация

eno1: 192.168.50.20/24
GW:   192.168.50.1

ping 192.168.50.1 не отвечает.

Стратегия

Шлюз находится в том же сегменте. Для первой доставки маршрут прост; ключевая зависимость — разрешение адреса соседа на втором уровне.

Действия

ip addr show eno1
ip route get 192.168.50.1
ip neigh show dev eno1
tcpdump -ni eno1 arp

Получено:

# ip route get 192.168.50.1
192.168.50.1 dev eno1 src 192.168.50.20 uid 0
# ip neigh show dev eno1
192.168.50.1 FAILED
# tcpdump -ni eno1 arp
ARP, Request who-has 192.168.50.1 tell 192.168.50.20, length 28
ARP, Request who-has 192.168.50.1 tell 192.168.50.20, length 28

Запросы повторяются, ответов нет.

Интерпретация

Три наблюдения делят задачу пополам. ip route get показывает, что маршрут выбран верно и следующий узел не нужен: адрес локальный, доставка идёт напрямую через eno1. Состояние соседа FAILED означает, что стек попытался разрешить MAC-адрес и не получил ответа. И перехват это подтверждает: кадры уходят с интерфейса.

Значит, вся часть пути от приложения до провода работает: маршрутизация, ARP-логика, драйвер, передача. Не работает то, что начинается за пределами хоста, — и расследование сужается до VLAN на порту коммутатора, самого порта, кабеля, состояния шлюза или чужого адреса, назначенного не в том сегменте.

Вывод

Дальше идти надо не в /etc/network, а к коммутатору: сравнить VLAN порта доступа с VLAN шлюза, посмотреть счётчики и MAC-таблицу порта, проверить, что шлюз вообще отвечает соседям в этом сегменте:

ip -s link show eno1                  # растут ли RX-пакеты вообще
tcpdump -ni eno1 not arp | head       # виден ли чужой broadcast-трафик сегмента
arping -I eno1 192.168.50.1

Менять маршрут по умолчанию в этот момент бессмысленно: проблема возникает ещё до маршрутизации — на разрешении адреса соседа в собственном сегменте. Правило общее: пока сосед в состоянии FAILED, ни один параметр L3 не может ничего исправить.

6.12. Лаборатория: два маршрутизируемых сегмента

Создайте три VM:

linux1 -- netA -- router -- netB -- linux2

Адреса:

linux1: 10.10.1.10/24, gw 10.10.1.1
router: 10.10.1.1/24 + 10.10.2.1/24
linux2: 10.10.2.10/24, gw 10.10.2.1

На router включите пересылку пакетов:

sysctl -w net.ipv4.ip_forward=1

Убедитесь, что linux1 видит linux2. Затем:

  • удалите маршрут по умолчанию на linux1;
  • поставьте неправильный /16 префикс;
  • отключите пересылку на router;
  • наблюдайте ARP на обеих сторонах.

Для каждой поломки объясните, на каком слое меняется симптом.

Концептуальное углубление: префикс — локальное правило принятия решения

Маска подсети не существует «в сети вообще» как единая магическая таблица. Каждый хост использует собственную конфигурацию интерфейса и таблицу маршрутизации, чтобы решить, какой адрес считать достижимым напрямую, а какой отправлять через следующий узел.

Из-за этого два узла с несовместимыми масками могут иметь асимметричное представление о локальности. Например, один считает адрес соседа локальным и запрашивает его по ARP напрямую, а другой считает первый хост удалённым и отправляет ответ шлюзу. Это создаёт симптомы, которые выглядят очень странно, если подсеть воспринимается только как запись /24 в настройках.

ARP как локальный механизм

ARP нужен для следующего узла IPv4 в локальном домене Ethernet. Маршрутизатор не «передаёт исходный кадр Ethernet дальше». Он принимает пакет, делает новый поиск маршрута и создаёт новый кадр второго уровня для следующего сегмента. Поэтому MAC-адреса меняются на границе маршрутизации, а IP-адреса обычно сохраняются, если не применяется NAT.

Эта модель позже объяснит VLAN, мосты, межсетевой экран и перехваты tcpdump.

Практическое углубление: Пройдём один пакет полностью

Пусть linux1 (10.10.10.11/24) обращается к linux2 (10.10.20.12/24). Это полезнее разобрать медленно один раз, чем запомнить десять сетевых команд.

  1. Приложение формирует данные для 10.10.20.12.
  2. Ядро сравнивает адрес назначения с локальными маршрутами. 10.10.20.12 не принадлежит напрямую подключённой 10.10.10.0/24.
  3. Таблица маршрутизации выбирает маршрут по умолчанию или явный маршрут через 10.10.10.1.
  4. Чтобы отправить кадр Ethernet следующему маршрутизатору, нужен его MAC-адрес. Ядро смотрит таблицу соседей.
  5. Если записи нет, выполняется разрешение по ARP для 10.10.10.1 — не для конечного 10.10.20.12.
  6. Кадр приходит на интерфейс маршрутизатора в CLIENT-NET. Маршрутизатор снимает оболочку второго уровня, выполняет новый поиск маршрута уже для адреса назначения 10.10.20.12.
  7. В SERVER-NET адрес назначения подключён напрямую. Маршрутизатор узнаёт MAC-адрес linux2 через ARP и создаёт новый кадр Ethernet.
  8. Адреса IP источника и назначения при обычной маршрутизации не меняются; адреса второго уровня меняются на каждом маршрутизируемом переходе.

Теперь команда ip neigh получает строгий смысл: она отвечает не «работает ли сеть», а «каким соседям третьего уровня этот хост уже сопоставил адреса второго уровня на конкретном интерфейсе».

Попробуйте без подсказки

Сделайте tcpdump -eni одновременно на интерфейсах router в сетях CLIENT и SERVER. Сравните MAC-адреса одного эхо-запроса ICMP до и после маршрутизации. Затем сравните IP-адреса. Объясните, почему один набор изменился, а второй нет.

Типичная ошибка мышления

Заблуждение. Ping до шлюза не проходит — значит проблема в шлюзе.

Почему это неверно. Успешный ping до соседа в том же сегменте требует одновременно: поднятой линии, корректного VLAN на порту, разрешения ARP, совпадающего префикса у обеих сторон и отсутствия фильтрации ICMP. Неудача означает только «эхо-ответ не вернулся» и не указывает, какое из этих условий нарушено. Кроме того, шлюз — это просто следующий узел, у него нет обязанности отвечать на ICMP.

Что проверить вместо этого.

ip -br link                    # если state DOWN, дальше идти бессмысленно
ip -br addr                    # prefix с обеих сторон должен совпадать
ip route get 10.0.0.1          # какой dev и какой source выбраны
ip neigh show                  # REACHABLE / STALE / FAILED
tcpdump -ni eth0 arp           # уходит ли запрос и приходит ли ответ

ARP в состоянии FAILED — это уже локализация: проблема на L2, а не в маршрутизации.

Лестница самостоятельности

Эту главу не нужно считать завершённой после одной успешной лаборатории. Пройдите три уровня, уменьшая количество подсказок.

  1. С опорой: проследить ARP и маршрут одного ping. На этом уровне разрешено смотреть разобранный пример и сверять ожидаемые результаты.
  2. С частичной опорой: изменить префикс или шлюз и предсказать симптом. Перед каждой командой письменно сформулируйте, что именно она должна подтвердить или опровергнуть.
  3. Инцидент: диагностировать асимметричную адресацию. На этом уровне сначала фиксируются симптом и подтверждающие данные; готового списка команд нет.

Переходите дальше, когда можете объяснить не только что сделали, но и почему следующий шаг был информативнее альтернатив.

Итоги главы

Доставка по IP начинается с определения, находится ли адресат в том же сегменте. Для локального адресата нужен MAC-адрес его самого; для удалённого — MAC-адрес следующего маршрутизатора. Маршрутизация выбирает путь по наиболее специфичному префиксу, а разрешение адреса соседа связывает решение третьего уровня с Ethernet. Эта последовательность позволяет диагностировать сеть снизу вверх без случайного изменения шлюза и межсетевого экрана.

U06. Университетское углубление: Ethernet, IPv4 и маршрутизация

До: 00, 02. После: вычислять подсети, выбирать следующий узел, объяснять ARP и границы перехвата. L06A/B, T06, VLAN.

Теория

Ethernet доставляет кадры внутри канального домена. Кадр содержит адреса MAC назначения и источника, поле типа или длины, данные и контрольную сумму FCS; преамбула и межкадровый интервал также занимают время линии. Коммутатор изучает соответствие MAC-адреса источника и входного порта в таблице FDB. Известный одноадресный кадр пересылается на нужный порт, неизвестный обычно распространяется в пределах соответствующего VLAN. Таблица FDB коммутатора и таблица ARP хоста решают разные задачи.

IPv4-адрес — 32 бита; префикс /p оставляет 32−p бит для адресов внутри сети. Для обычной broadcast-подсети с p ≤ 30 часто доступны 2^(32−p)−2 адреса узлов, но /31 на point-to-point и /32 имеют другую семантику. Сетевой адрес получается побитовым AND адреса и маски. CIDR не опирается на старые классы A/B/C.

Для отправки ядро выбирает маршрут в применимой таблице по правилам маршрутизации на основе политик. Внутри таблицы важен наиболее длинный совпавший префикс; далее учитываются свойства маршрутов. Затем выбираются исходный адрес и следующий узел. Если цель в том же сегменте, соседом может быть сама цель; для удалённой сети — шлюз. ARP связывает следующий узел IPv4 с MAC-адресом в локальном сегменте. MAC-адрес удалённого сервера за маршрутизатором обычно не нужен исходному хосту.

Команды ip addr и ip route меняют текущее состояние ядра, а не сохраняемую конфигурацию сети. Если адрес и маршрут добавлены только ими, после перезагрузки они исчезнут; постоянное состояние задают средствами настройки сети выбранной системы и затем проверяют повторным запуском.

Маршрутизатор удаляет входной заголовок второго уровня, уменьшает TTL, обрабатывает пакет и создаёт новый кадр на выходном интерфейсе. Адрес назначения IP обычно сохраняется, если не применяется NAT. Прямой и обратный пути могут различаться. Поэтому перехват SYN на сервере не доказывает, что SYN-ACK дойдёт до клиента. ICMP сообщает диагностические события; полное блокирование ICMP лишает сеть части механизмов обработки ошибок.

Наблюдение ограничено точкой измерения. Перехват внутри VM показывает представление виртуального интерфейса; разгрузка на сетевую карту может менять видимые размеры и контрольные суммы до аппаратной обработки. Отсутствие пакета в перехвате может означать фильтр захвата, неверное пространство имён, потери при захвате или другую ветвь пути. Чтобы найти границу, задайте ожидаемый пакет и сравните две соседние точки с синхронизированным временем.

Неверный префикс меняет решение о том, является ли цель соседом: клиент с ошибочным /16 может искать ARP для адреса из соседней /24 вместо отправки пакета шлюзу. Для диагностики сравнивают ip route get и соседей до изменения. После возврата согласованного /24 проверяют выбор шлюза, ARP для следующего узла и прикладной запрос; сохраняемую конфигурацию исправляют отдельно от текущего состояния ядра.

Разобранные примеры

E06.2. Маршрут. Для 10.20.8.5 совпадают 0/0, 10/8, 10.20/16 и 10.20.8/24. В выбранной таблице выигрывает /24, даже если у маршрута по умолчанию ниже метрика. Другое правило политики может выбрать другую таблицу раньше.

E06.3. Сериализация. Только 1500 байт данных при 1 Gbit/s занимают 12 мкс. Реальная занятость линии больше из-за заголовков и интервалов. Сериализация — лишь часть задержки, кроме неё есть распространение, обработка и очередь.
