Получить структурированный результат внешней команды

Результат: Получить структурированный результат внешней команды без смешивания каналов.

Часть общей системы: Структурированное наблюдение внешнего процесса.

Что сохранить в инженерном журнале: Код завершения, stdout, stderr и ограничение времени.

Разберёмся до действия

Python может запускать программу через subprocess.run. Список аргументов с shell=False передаёт границы прямо процессу; shell=True добавляет интерпретацию оболочкой и требует другой модели безопасности. capture_output разделяет stdout и stderr, text декодирует байты, timeout ограничивает ожидание. Ненулевой returncode нужно обработать либо явно, либо через check=True и исключение. JSON сериализует поля результата, но не превращает неуспех в успех. Отсутствующее поле, null и ноль имеют разные значения.

Среда и права: В учебном Linux-госте обычным пользователем; sudo требуется только для явно указанных изменений. Данные примера можно разбирать без стенда.

Разобранный пример

Команды примера; переменные WORK и NS задаются в инструкции практики ниже:

python3 -c "import subprocess; r=subprocess.run(['python3','-c','import sys; print(7); sys.exit(3)'],capture_output=True,text=True,timeout=3); print(repr(r.stdout),repr(r.stderr),r.returncode)"

Ожидаемый результат: stdout содержит 7 и перевод строки, stderr пуст, returncode равен 3. Наличие полезного stdout не обнуляет отказ.

Сопоставь наблюдение с описанным механизмом. Вывод относится к проверенному объекту и условиям опыта.

При отклонении: При несовпадении результата сохрани фактический вывод, проверь предпосылки и остановись перед дальнейшими изменениями. Не подменяй наблюдение ожидаемым текстом.

Прогноз и опыт с поддержкой

Предскажи три поля результата программы из задания. Подготовь python-result; запусти дочерний Python, печатающий out в stdout, err в stderr и завершающийся с 7. Сохрани решение в solution.py, принимающей команду как список sys.argv[1:] и печатающей JSON stdout, stderr, code. Исполнитель запустит её от имени ученика с разными командами.

Самостоятельная задача

Измени дочернюю программу так, чтобы stdout был пустым, и обработай TimeoutExpired отдельно от ненулевого кода. Не используй shell=True для склейки пользовательских аргументов.

M22-1: Почему capture_output=True недостаточно для ограниченного сборщика?

Timeout ограничивает время, но не автоматически объём памяти. Ограничение по времени не ограничивает объём.

M22-2: Скрипт на Python запускает системную команду и молча продолжает работу при её отказе. Что изменить?

Returncode проверяют согласно контракту утилиты; stdout может быть пустым или непустым при любом исходе. Успешный код запуска ещё не доказывает предметную полноту: дальше проверяют схему, значения и ожидаемый набор результатов. Повторы допустимы после оценки идемпотентности. Успех команды определяется её кодом возврата, а не содержимым вывода.

R22: API выдаёт 75 объектов на страницу, всего 302. Сколько страниц нужно? POST закончился timeout: сформулируйте безопасную последовательность вместо безусловного повторного создания.

5 страниц: 75+75+75+75+2. При timeout проверить идентификатор операции или созданный ресурс либо повторить запрос по документированному ключу идемпотентности; не выдавать новый независимый запрос на создание. Количество страниц: 5.

C20-0: Какой шаг глава называет ключевым при превращении набора команд в диагностический инструмент?

Это разделение позволяет проверять интерпретацию на сохранённых фактах и менять представление, не трогая сбор. Применение к описанным условиям: Разделить сбор фактов, интерпретацию и представление результата.

C20-0b: Зачем в диагностическом инструменте разделяют сбор фактов и их толкование?

Разделение сбора, интерпретации и представления позволяет менять представление, не трогая сбор, — и наоборот. Применение к описанным условиям: Чтобы проверять толкование на сохранённых фактах.

C20-1: Чем опасна передача недоверенного значения в строку shell=True без корректного контекстного экранирования?

Оболочка может интерпретировать значение как код. Список аргументов с shell=False убирает этот уровень интерпретации, но не отменяет проверку аргументов утилиты и использование -- там, где оно предусмотрено. Применение к описанным условиям: Подставленное значение может выполнить произвольную команду.

C20-1b: Сценарий отработал на вашей машине. Почему это не значит, что он отработает на сервере?

Рабочее окружение сервера может отличаться версией Python, локалью, форматом вывода команд, сетью и правами пользователя. Применение к описанным условиям: Там другая версия, локаль, формат вывода, пользователь.

L22B#why: Почему после таймера клиента нельзя сказать, что POST не выполнился?

Таймер клиента ограничивает ожидание, а не гарантирует откат серверной операции. Результат ищут по идентификатору операции, ресурса или корреляции; простой рост числа объектов ещё не доказывает, что их создал именно этот запрос. Ключ идемпотентности работает только по документированному контракту сервера. Применение к описанным условиям: Потому что таймер обрывает ожидание ответа.

L22A#why: Почему «программы нет» и «программа вернула 1» нельзя записать одним статусом?

Отчёт читают, чтобы принять решение, а «не получилось» решения не подсказывает. Отсутствие ZFS на машине без ZFS — нормальное состояние; ss без прав — повод перезапустить сбор иначе. Обрезка по пределу — третий случай: данные есть, но неполные, и выдавать их за полный вывод нельзя. Применение к описанным условиям: Потому что это разные выводы о системе.

Углубление: Результат инструмента — структура

Результат инструмента — структура

subprocess.run с массивом аргументов передаёт их без интерпретации shell. capture_output собирает stdout и stderr отдельно; returncode обозначает исход процесса. check=True превращает ненулевой код в исключение, timeout ограничивает ожидание. JSON-парсер проверяет синтаксис, а схема и типы — смысл полей. Человеческий вывод может меняться после обновления или смены языка.

argparse задаёт интерфейс команды, logging направляет диагностические сообщения отдельно от машинного результата. Обрабатывай ожидаемые исключения на границе инструмента и сохраняй причину: unavailable, timeout, invalid-data или failed. HTTP имеет транспортный исход и статус ответа; успешный HTTP ещё требует проверки тела. Секреты не должны попадать в argv, отчёт и traceback. Конкурентный опрос сокращает суммарное ожидание независимых узлов, но требует лимита параллельности и отдельного результата каждого.

Другие условия: разобранный случай

Даны наблюдения: Команда завершилась кодом 2, stdout пуст, stderr содержит причину отказа. Старый скрипт пытается разобрать stdout как успешный JSON.

Разбор: Первичная ошибка — отказ процесса; ошибка JSON вторична. Сначала классифицируй исход, затем разбирай ожидаемый формат.

Это учебные данные, а не протокол выполненного действия.

Граница вывода и безопасного действия: Не запускай ученический код от root. Повторные попытки HTTP ограничивай временем и применяй только с учётом идемпотентности операции.
