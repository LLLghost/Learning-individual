Разделить запуск Pod и готовность приложения

Результат: Различить Running Pod и готовность приложения принимать запрос.

Объект: Страница заметок и выделенные ресурсы текущего опыта.

Разберёмся до действия

Pod объединяет контейнеры с общей сетью и связанным жизненным циклом. Фаза Running означает, что Pod назначен узлу и контейнеры созданы; она не равна Ready. Readiness probe управляет готовностью принимать трафик, liveness probe может инициировать перезапуск, startup probe откладывает другие пробы во время старта. Неверная liveness может создать цикл перезапусков исправного, но медленного приложения. Проверка включает условия Pod, события и реальный запрос.

Среда и права: В учебном Linux-госте обычным пользователем; sudo требуется только для явно указанных изменений. Данные примера можно разбирать без стенда.

Разобранный пример

Команды примера; переменные WORK и NS задаются в инструкции практики ниже:

kubectl -n "$NS" get pods
kubectl -n "$NS" describe pod notes

Ожидаемый результат: В подготовленном опыте Pod может быть Running и 0/1 Ready из-за неверного пути readiness. Исправление не должно удалять пробу.

Сопоставь наблюдение с описанным механизмом. Вывод относится к проверенному объекту и условиям опыта.

При отклонении: При несовпадении результата сохрани фактический вывод, проверь предпосылки и остановись перед дальнейшими изменениями. Не подменяй наблюдение ожидаемым текстом.

Прогноз и опыт с поддержкой

Предскажи состояние для работающего HTTP-сервера и readiness на отсутствующем пути. Подготовь kubernetes, прочитай события и исправь путь на доступный. Дождись Ready.

Самостоятельная задача

Повтори вариант с другой ошибкой порта. Подтверди готовность и содержимое приложения, не ограничиваясь успешным apply.

Объясни и вернись позже

Когда рестарт полезен, а когда readiness должна лишь убрать трафик? Через день выбери пробу для медленной инициализации.

Свободное объяснение сохраняется для самопроверки; автоматическая проверка не оценивает его смысл.

M26-1: Какая величина CPU и памяти является основой учёта ёмкости при обычном размещении Pod планировщиком?

Планировщик учитывает requests и правила размещения относительно allocatable. Limits прежде всего задают ограничения исполнения и не заменяют requests в этом расчёте; defaulting может связать значения до планирования. Размещение считается по заявленным requests и доступной allocatable-ёмкости с учётом правил.

M26-2: API Kubernetes принял новое желаемое состояние Deployment. Что можно утверждать сразу после ответа API?

Контроллеры Kubernetes согласуют наблюдаемое состояние с желаемым асинхронно. Принятый объект не означает завершённый развёртывание или готовность приложения. Контроллеры асинхронны; готовность проверяют отдельно..

R26: Узел имеет 7,5 CPU allocatable, Pod request 2 CPU. Сколько таких Pods размещается по CPU? Для работающих Pods Service имеет пустые EndpointSlices: какие три факта проверяются?

3 Pod по CPU, остаётся 1,5 CPU. Проверить namespace, селектор и метки, готовность и согласование EndpointSlice; после появления конечных точек проверить targetPort и слушающий сокет. Количество Pods: 3.

C23-0b: Чем состояние Running отличается от готовности Pod?

Условия готовности могут определяться разными пробами; отсутствие HTTP-пробы не создаёт автоматической проверки страницы. Фаза Running не подменяет Ready или пользовательский запрос. Применение к описанным условиям: Running — фаза жизненного цикла, Ready — выполнение настроенных условий готовности.

L26B#why: Почему работающий под не обязательно попадает в сервис?

Running, labels, namespace и readiness — разные проверки. Читают selector и EndpointSlice с conditions.ready, затем путь запроса и порт. Перезапуск без изменения установленного несовпадения не является исправлением. Применение к описанным условиям: Потому что Running не гарантирует совпадения меток с селектором Service и готовности Pod.

L26A#why: Готовый Pod в том же namespace имеет app=notes-v2, Service с selector app=notes. Почему у этого Service нет соответствующей готовой конечной точки?

В данном случае задано несовпадение меток. Вообще конечные точки зависят также от namespace, IP и готовности; EndpointSlice может содержать неготовые адреса. Один пустой список не доказывает только ошибку selector. Применение к описанным условиям: Указанный selector не совпал с labels этого Pod.

Углубление: Контроллер, планировщик и приложение

Контроллер, планировщик и приложение

API хранит желаемые объекты, контроллеры сравнивают желаемое и фактическое состояние, scheduler выбирает узел, kubelet запускает контейнеры через runtime. Running означает стадию жизни Pod, Ready — допуск к обслуживанию по заданным условиям. Liveness может инициировать restart, readiness снимает готовность, startup probe даёт время запуска. Неправильно выбранная probe способна сама создавать отказ.

Requests участвуют в планировании и распределении ресурсов, limits задают ограничения исполнения. Pending может означать невозможность разместить requests; CPU limit способен вызвать throttling, memory limit — OOMKilled. Сеть, хранилище и конфигурация остаются отдельными зависимостями. Reconciliation заменит потерянный экземпляр, но не восстановит отсутствующий секрет и не исправит неверный selector. Маленькой странице не нужен кластер без соответствующих требований.

Другие условия: разобранный случай

Даны наблюдения: Pod Running, readiness падает; EndpointSlice содержит адрес с ready=false.

Разбор: Процесс существует, но не считается готовым endpoint. Сначала проверяй probe, порт, зависимости и фактический ответ, а не увеличивай число реплик.

Это учебные данные, а не протокол выполненного действия.

Проверь перенос понимания

Различи четыре причины: Pending из-за requests, OOMKilled, Ready=false и selector без совпадений. Для каждой назови следующий наблюдаемый объект.

Граница вывода и безопасного действия: Используй отдельный kind cluster и явный kubeconfig. Контекст рабочего кластера не должен быть неявной целью учебных команд.
