Сохранить объяснимое изменение конфигурации

Результат: Сохранить изменение конфигурации отдельным объяснимым коммитом.

Часть общей системы: История конфигурации и объяснение изменения.

Что сохранить в инженерном журнале: Коммит, причина, проверка и способ возврата.

Разберёмся до действия

Git хранит снимки отслеживаемых файлов и связи между коммитами. Рабочее дерево, индекс и последний коммит — три разных состояния. diff показывает выбранную разницу, а status — незафиксированные изменения. Коммит конфигурации не разворачивает её в сервисе и не проверяет применимость. Секреты нельзя считать удалёнными из истории после простого удаления файла новым коммитом. Безопасный учебный репозиторий содержит только созданную работой конфигурацию и фиктивные данные.

Среда и права: В учебном Linux-госте обычным пользователем; sudo требуется только для явно указанных изменений. Данные примера можно разбирать без стенда.

Разобранный пример

Команды примера; переменные WORK и NS задаются в инструкции практики ниже:

git -C "$WORK/repo" status --short
git -C "$WORK/repo" diff
git -C "$WORK/repo" log -1 --oneline

Ожидаемый результат: В начале есть baseline и port=8080. После задачи нужен второй коммит с port=8081 или 8082 и чистое рабочее дерево.

Сопоставь наблюдение с описанным механизмом. Вывод относится к проверенному объекту и условиям опыта.

При отклонении: При несовпадении результата сохрани фактический вывод, проверь предпосылки и остановись перед дальнейшими изменениями. Не подменяй наблюдение ожидаемым текстом.

Прогноз и опыт с поддержкой

Предскажи, попадёт ли незастейдженный файл в коммит. Подготовь git-change, измени порт, прочитай diff, добавь только service.conf в индекс и закоммить с причиной изменения.

Самостоятельная задача

Повтори второй вариант. Покажи различие baseline и нового коммита и объясни способ возврата отдельного изменения без переписывания чужой истории.

Объясни и вернись позже

Какое испытание нужно сверх чистого git status для проверки работающего сервиса? Через день восстанови три состояния файла.

Свободное объяснение сохраняется для самопроверки; автоматическая проверка не оценивает его смысл.

Первоисточник для сверки поведения и версии: документация. Команды Linux рассчитаны на Debian 12/13; доступность конкретной функции проверяется предпосылками работы.

R23: В идеализированной модели одна одинаковая задача Ansible обрабатывает 30 узлов, forks=5, длительность на каждом узле ровно 12 с, накладных расходов нет. Сколько волн и секунд требуется? Почему changed=0 во втором запуске не доказывает здоровье HTTP-сервиса?

30/5=6 волн по 12 с=72 с без учёта сбора фактов и разброса времени узлов. changed=0 частично подтверждает сходимость выбранных задач, но не здоровье сервиса: playbook описывает только то, что в нём написано. Проверить хеш конфигурации и фактическую привязку, журналы сервиса и зависимостей, сквозной запрос и данные. Количество волн по forks: 6; Время прогона, с: 72.

C21-0: Что означает успешный прогон плейбука?

Недоступный в момент запуска хост, ручное изменение после прогона и задача через оболочку вместо идемпотентного модуля создают расхождение, которого в отчёте не видно. Применение к описанным условиям: Что задачи не завершились ошибкой на доступных хостах из выборки.

C21-0b: Какой счётчик recap Ansible явно отмечает хост, до которого не удалось установить необходимое соединение?

Недоступный хост не получил задачи и не может считаться сошедшимся, даже если changed=0. В отчёте и событиях запуска проверяют unreachable и failed отдельно. Применение к описанным условиям: unreachable: недоступность хоста.

C21-1b: Режим проверки показал три изменённые задачи. Что это?

Check mode моделирует поддержанные действия, а не универсально подтверждает сходимость. Объясни, откуда взялись три changed, проверь поддержку модулей, условия и реальные данные; ноль changed сам по себе также не доказывает здоровье сервиса. Применение к описанным условиям: Предполагаемое изменение или поведение модуля, которое нужно сверить с фактическим состоянием.

S6-0: Чем репозиторий отличается от каталога, где рядом лежат config.bak и config_old?

Причина изменения не возникает автоматически: её записывает автор коммита. История связывает состояния и различия; случайные config.bak без метаданных не дают такой же структуры. Применение к описанным условиям: Git хранит историю снимков отслеживаемых файлов, отличия и записанные автором сообщения.

S6-0b: Что фиксирует обычный Git-коммит и почему это полезно для нескольких связанных файлов?

Коммит создаёт снимок дерева из индекса. Изменения без git add и неотслеживаемые файлы автоматически не включаются. Согласованность сочетания требует осмысленного выбора файлов автором. Применение к описанным условиям: Состояние отслеживаемых файлов из индекса, позволяющее вернуть согласованное сочетание.

S6-1: Обычный репозиторий существовал только на одном сервере; его носитель безвозвратно потерян, клонов и копий нет. Что Git сам по себе может восстановить?

Git не создаёт удалённую копию автоматически. Для обычного репозитория потеря единственного хранилища объектов уничтожает доступную историю; нужны независимые клоны или резервные копии. Применение к описанным условиям: Ничего из потерянной истории: другой копии объектов нет.

S6-1b: В репозиторий случайно записали пароль и следующим коммитом удалили файл. Что делать?

Коммит с файлом никуда не делся, и пароль по-прежнему читается из истории. Удаление файла не отменяет того, что он уже записан. Применение к описанным условиям: Менять сам пароль: записанное остаётся в истории.

L23A#why: Почему успешный отчёт о прогоне не описывает состояние парка?

Отчёт фиксирует конкретную выборку и время прогона. Недоступность видна в unreachable/failed и должна учитываться, а не объявляться невидимой. Сводка не доказывает состояние вне inventory, отсутствие дрейфа после прогона или корректность произвольной shell-задачи. Применение к описанным условиям: Потому что отчёт описывает прогон.

L23B#why: Хост web-03 во всех трёх прогонах имеет changed=0 и unreachable=1. Что это значит?

unreachable явно показывает отсутствие необходимого соединения в этих прогонах. changed=0 такого хоста не подтверждает сходимость. Проверяют доступность, failed и фактическую конфигурацию, отдельно от пользовательского здоровья. Применение к описанным условиям: Что до него ни разу не дошли: unreachable означает отсутствие связи.

Углубление: Версия желаемого состояния

Версия желаемого состояния

Git commit фиксирует снимок подготовленных в index файлов и метаданные. Неотслеживаемые и не добавленные изменения не появляются в нём автоматически. Diff рабочего дерева, index и последнего commit отвечают на разные вопросы. Секрет, попавший в историю, требует отзыва и отдельного удаления из истории: новый commit с удалённым файлом не стирает старые версии.

Ansible описывает состояние через inventory, переменные, facts, modules, templates и roles. Группы inventory выражают роли узлов, а не только адреса. Handler запускается при уведомлении об изменении. Идемпотентность означает повторное достижение того же состояния без лишних изменений, но зависит от модуля и описания задачи. Git хранит намерение и процедуру, а наблюдение реального узла выявляет drift — отклонение от этого намерения.

Другие условия: разобранный случай

Даны наблюдения: После первого применения changed=3, после второго changed=0. Затем администратор вручную поменял конфигурацию на сервере.

Разбор: Второй прогон подтвердил устойчивость того состояния, но не вечное отсутствие drift. Следующее сравнение должно обнаружить отклонение и показать конкретный diff.

Это учебные данные, а не протокол выполненного действия.

Проверь перенос понимания

Раздели в репозитории шаблон, inventory, пример переменных и зашифрованные/внешние секреты. Как доказать, что работающий сервер соответствует конкретному commit?

Граница вывода и безопасного действия: Хеш commit идентифицирует источник, но сам по себе не доказывает его применение. Проверяй фактическое состояние и не сохраняй пароли в открытых примерах.
