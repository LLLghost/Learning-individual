Опубликовать приложение с подходящим адресом прослушивания

Результат урока: Опубликовать приложение с подходящим адресом прослушивания и подтвердить вывод наблюдением.

Сначала разберёмся

У контейнера есть собственное сетевое пространство имён. Адрес 127.0.0.1 внутри него относится к его loopback. Публикация порта связывает внешний вход с адресом контейнера, но не меняет слушающий адрес приложения. EXPOSE описывает метаданные; явная публикация задаётся отдельно.

Разобранный пример

Приложение слушает только внутренний loopback. Правило публикации есть, но обращение к адресу контейнера не попадает в этот сокет.

Где и от чьего имени: На учебной ВМ сравни два наблюдения до изменения контейнера. Проверь политику внешнего доступа перед привязкой на все адреса.

Цель команды: получить наблюдение, описанное ниже. Команды с sudo требуют прав администратора учебной ВМ; остальные выполняются обычным пользователем.

docker port web; docker exec web ss -lntp

Ожидаемый результат: Опубликованный порт и реальный слушающий адрес. Это описание вида результата; имена и значения сверяют со своей машиной.

Если результат отличается: сохрани вывод и код ошибки, проверь имя машины, наличие инструмента и права. До выяснения причины не переходи к изменяющим действиям.

Опыт с поддержкой

На учебной ВМ сравни два наблюдения до изменения контейнера. Проверь политику внешнего доступа перед привязкой на все адреса.

До действия запиши, что ожидаешь увидеть и почему. После сравни результат с прогнозом, сохрани факты и обозначь, что они ещё не доказывают.

22.8. DNS внутри Compose

Compose создаёт обнаружение сервисов по их именам в общей сети.

services:
  app:
    build: .
    depends_on:
      - db
  db:
    image: ${POSTGRES_IMAGE:?Set_POSTGRES_IMAGE_to_a_tested_digest}

Перед запуском задайте POSTGRES_IMAGE как проверенную полную ссылку вида postgres@sha256:<фактический digest> и сохраните её в описании; заполнитель не является исполнимым значением. Это схема обнаружения сервисов, а не полный готовый стек PostgreSQL: учётные данные, том и проверка готовности добавляются по контракту выбранного образа. Приложение обращается к имени db, а не к localhost, потому что localhost внутри контейнера приложения означает сам этот контейнер.

Это одна из наиболее частых ошибок начинающих.

22.9. depends_on не гарантирует готовность приложения

Контейнер может считаться запущенным, пока база данных ещё выполняет инициализацию. Поэтому стек, приближенный к эксплуатации, использует проверки готовности и повторные попытки, а не полагается только на порядок запуска.

Опять проявляется знакомый урок systemd: «процесс запущен» и «сервис готов» — разные состояния.

22.15. Почему free и nproc внутри контейнера врут

Процесс в группе с лимитом 64 МиБ спрашивает систему о памяти и процессорах:

free -m
               total        used        free      shared  buff/cache   available
Mem:            1960         331         782           0        1004        1629

nproc
2

Он видит 1960 МиБ и два процессора — то есть ресурсы хоста, а не свои. Причина простая: free читает /proc/meminfo, а /proc в контейнере — это тот же /proc ядра, и пространства имён для него нет. Ограничения лежат в cgroup, и туда никто не смотрит.

Последствия у этого не косметические. Java, Go и Node по умолчанию выбирают размеры пулов и кучи по числу процессоров и объёму памяти; приложение, увидевшее «два процессора и два гигабайта» в группе на 64 МиБ, запустит слишком много потоков и будет убито. Современные среды выполнения умеют читать cgroup — у JVM это включено по умолчанию с версии 10, — но проверять это приходится каждый раз.

Правильные источники правды внутри контейнера:

cat /sys/fs/cgroup/memory.max      # лимит памяти группы
cat /sys/fs/cgroup/memory.current  # сколько занято сейчас
cat /sys/fs/cgroup/cpu.max         # квота и период
cat /sys/fs/cgroup/memory.events   # упирались ли в потолок

Тот же вывод касается мониторинга: агент, снимающий «свободную память» внутри контейнера, измеряет хост. Полезные метрики контейнера — это memory.current против memory.max и рост max в memory.events.

22.17. Сеть контейнера: veth, мост и публикация порта

Сетевое пространство имён пустое; связь с хостом делает виртуальная пара интерфейсов — один конец внутри, другой снаружи. Соберём её без Docker:

sudo ip netns add lab
sudo ip link add veth-host type veth peer name veth-lab
sudo ip link set veth-lab netns lab
sudo ip addr add 10.99.0.1/24 dev veth-host && sudo ip link set veth-host up
sudo ip netns exec lab ip addr add 10.99.0.2/24 dev veth-lab
sudo ip netns exec lab ip link set veth-lab up
ping -c1 10.99.0.2

Связь есть. А вот что видит «контейнер» изнутри:

sudo ip netns exec lab ip route
10.99.0.0/24 dev veth-lab proto kernel scope link src 10.99.0.2

Маршрута по умолчанию нет — наружу такой контейнер не ходит. Docker делает ровно то же самое, только автоматически: создаёт мост docker0, включает в него один конец каждой пары, раздаёт адреса и прописывает маршрут через мост:

ip -br addr show docker0
docker0          DOWN           172.17.0.1/16

Публикация порта — это правило трансляции, а не свойство контейнера. Слушающий сокет внутри пространства имён недостижим снаружи, пока хост не начнёт переправлять туда пакеты:

sudo iptables -t nat -S DOCKER
-N DOCKER
-A DOCKER -i docker0 -j RETURN

Пока контейнеров с опубликованными портами нет, правил здесь тоже нет; каждый -p 8080:80 добавляет строку DNAT. Отсюда разбор классического симптома «внутри работает, снаружи нет», который подробно разобран в следующем разделе: проверять надо три вещи по очереди — на каком адресе слушает процесс внутри (0.0.0.0 или 127.0.0.1), опубликован ли порт наружу, и не мешает ли правило межсетевого экрана хоста. Все три проверяются командами, и ни одна не требует перезапуска контейнера.
