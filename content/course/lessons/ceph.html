Разобрать распределённое хранение по состоянию объектов

Результат: Определить состояние объектов Ceph по репликам и правилам размещения.

Объект: Страница заметок и выделенные ресурсы текущего опыта.

Разберёмся до действия

Ceph распределяет объекты по OSD через placement groups и правила CRUSH. Число копий само по себе не задаёт независимость: копии должны попадать в разные допустимые домены отказа. size задаёт желаемое число реплик, min_size ограничивает возможность ввода-вывода при их нехватке. Снижение min_size ради исчезновения ошибки меняет риск потери данных. HEALTH_OK не заменяет проверку размещения и чтение нужного объекта.

Среда и права: В учебном Linux-госте обычным пользователем; sudo требуется только для явно указанных изменений. Данные примера можно разбирать без стенда.

Разобранный пример

Данные примера:

pool: size=3, min_size=2
объект A: копии на host1, host2, host3
host3 недоступен

Ожидаемый результат: Осталось две копии, желаемая избыточность не достигнута. Допустимость операции зависит от реального состояния PG и политики, а не только от арифметики.

Сопоставь наблюдение с описанным механизмом. Вывод относится к проверенному объекту и условиям опыта.

При отклонении: При несовпадении результата сохрани фактический вывод, проверь предпосылки и остановись перед дальнейшими изменениями. Не подменяй наблюдение ожидаемым текстом.

Прогноз и опыт с поддержкой

Предскажи отличие между потерей одного OSD и целого host. По данным нарисуй размещение и выбери наблюдение PG, которое подтвердит доступность объекта.

M17-0: Пять голосующих узлов разделились 3+2. Кто может иметь большинство?

Большинство=3; пересечение большинств помогает избежать конфликтующих решений. Решение принимает сторона, набравшая большинство голосов.

M17-1: quorum_status успешно подтвердил кворум трёх MON Ceph. Какое из следующих утверждений этот результат НЕ подтверждает?

Кворум MON и размещение с доступностью данных OSD проверяются отдельно. Кворум плоскости управления и доступность данных проверяются отдельно.

M17-2: Узел Ceph перестал отвечать вовремя. Почему тайм-аут сам по себе не доказывает, что узел погиб?

В распределённой системе отсутствие ответа не отличает смерть узла от задержки или разрыва связи. Решение об отказе принимают по правилам кворума и состоянию системы. Тайм-аут не доказывает смерть: ответ мог задержаться..

R17: 5 хостов по 18 TiB сырой ёмкости, размер реплики 3, плановый предел заполнения 70%. Оцените полезную ёмкость до дополнительных резервов. Сколько голосов нужно для большинства из 5?

90·0,7/3=21 TiB до дополнительных резервов. Большинство=3. Отдельно проверяют размещение после потери хоста, не только нормальную ёмкость. Полезная ёмкость, TiB: 21; Большинство: 3.

L17A#why: Три монитора запущены, а в кворуме два. Что это меняет для данных?

Мониторы держат карту и принимают решения большинством; копии данных задаются size пула, а условие записи — min_size. Смешение этих чисел приводит к выводам вида «у нас три копии, потому что три монитора». Применение к описанным условиям: Кворум большинства сохранён; число копий и доступность данных проверяют отдельно по OSD и пулу.

L17B#why: Для PG осталась одна пригодная реплика, а min_size=2 запрещает нужный I/O. Какой риск меняет снижение порога до 1 при остальных необходимых условиях?

min_size — порог допуска I/O при недостатке реплик, а не полное описание протокола подтверждения и не обещание точного числа копий каждого COMMIT. При одной оставшейся копии снижение порога может вернуть доступ ценой повышенного риска. Состояние PG, size, размещение и восстановление проверяют отдельно. Применение к описанным условиям: Может разрешить I/O при единственной копии без запаса на её отказ.

Углубление: Избыточность зависит от размещения

Избыточность зависит от размещения

Ceph RADOS хранит объекты на OSD. Клиент получает карту кластера и определяет размещение через CRUSH; placement group группирует объекты для управления размещением. MON поддерживают карты и кворум управления; число MON не равно числу копий данных. RBD предоставляет блочный интерфейс, CephFS — файловый с дополнительными метаданными.

В replicated pool size задаёт желаемое число копий, min_size — нижний порог для разрешения I/O, а не полное описание протокола подтверждения долговечности. CRUSH failure domain определяет разнесение по host/rack и другим уровням. Три OSD одного физического сервера не переживают потерю этого сервера как три независимых узла. Recovery/backfill требуют сети, места и времени; HEALTH_OK не описывает пригодность всех пользовательских путей.

Другие условия: разобранный случай

Даны наблюдения: size=3, все копии размещены на дисках одного хоста. Хост обесточен.

Разбор: Количество копий не обеспечило доступность при этом отказе. Нужна политика разнесения по независимым хостам и проверка её фактического выполнения.

Это учебные данные, а не протокол выполненного действия.
