Разобраться, кто может прочитать файл заметки

Результат: Дать владельцу доступ к заметке без предоставления прав всем остальным.

Объект: Личный note.txt в рабочем каталоге попытки permissions.

Разберёмся до действия

Процесс обращается к файлам от имени своей учётной записи. В обычном режиме доступа проверяются владелец, группа и остальные; r разрешает чтение, w — запись, x у каталога — проход к имени внутри. Для открытия файла нужен проход по каждому родительскому каталогу. ACL, политики AppArmor/SELinux и опции монтирования могут дополнительно менять эффективный доступ. Поэтому chmod 777 не является универсальным исправлением. umask снимает биты из запрошенного режима: 0666 при маске 0022 даёт 0644, а не арифметическое вычитание во всех случаях.

Среда и права: Владелец файла — course внутри Linux-гостя. chmod от этого пользователя; проверка от root не подтверждает его доступ.

Разобранный пример

Команды примера; переменные WORK и NS задаются в инструкции практики ниже:

id
stat -c '%U %G %a %n' note.txt
chmod 600 note.txt
cat note.txt

Ожидаемый результат: Файл принадлежит course, режим стал 600, чтение вернуло private note. Группа и остальные не получили прав.

6 означает чтение и запись владельцу; два нуля не дают прав остальным. Успешный cat проверяет доступ конкретного пользователя, а не только красивую запись режима.

При отклонении: Если 600 не помог, проверь владельца, каталоги и дополнительные политики. Не меняй права рекурсивно на системных каталогах.

Прогноз и опыт с поддержкой

Подготовь permissions и перейди в её work. Предскажи отказ cat при режиме 000. Прочитай владельца и режим, исправь только нужные биты, повтори cat и запусти проверку работы.

Самостоятельная задача

После отката повтори опыт. Теперь сначала проверь проход по каталогам пути. Объясни, почему доступный файл внутри закрытого родительского каталога может оставаться недоступным.

Углубление: Как имя файла становится проверкой доступа

Как имя файла становится проверкой доступа

Каталог связывает имя с inode, который описывает объект файловой системы. Жёсткие ссылки дают несколько имён одному inode; символическая ссылка хранит путь, который разрешается отдельно. Удаление имени не прекращает доступ через уже открытый дескриптор. Для прохода по каталогу нужен x, для списка имён — r, для изменения записей — w вместе с x; разрешение на удаление определяется прежде всего родительским каталогом.

Для обычных mode bits выбирается класс владельца, иначе подходящей группы, иначе остальных; это не суммирование всех трёх классов. ACL добавляет именованные записи и маску эффективных прав. setgid на каталоге помогает наследовать группу; sticky ограничивает удаление чужих записей в общем каталоге. setuid у исполняемого файла может менять effective UID. NSS определяет источник учётных записей; /etc/passwd не хранит современные хеши паролей, локальные хеши обычно в /etc/shadow. sudo делегирует конкретные действия. Capabilities и мандатные политики добавляют проверки сверх mode bits.

Другие условия: разобранный случай

Даны наблюдения: У журнала mode 0660 и правильная группа, но родительский каталог 0700 принадлежит другому пользователю.

Разбор: Процесс не может пройти по пути. Изменение режима только конечного файла не исправит доступ к каталогу.

Это учебные данные, а не протокол выполненного действия.

Проверь перенос понимания

Разбери путь к заметке для владельца, участника группы и постороннего. Отдельно предскажи чтение файла, список каталога и удаление имени.

Граница вывода и безопасного действия: Проверяй от имени пользователя службы. chmod 777 не является диагностикой; mount read-only, ACL, SELinux/AppArmor и настройки службы могут запрещать доступ даже при широких mode bits.
