Понять, какие компьютеры есть в лаборатории

Результат: Показать на схеме, где работает ученик, где приложение и через какой узел проходит связь между сегментами.

Объект: router связывает CLIENT-NET, SERVER-NET и STORAGE-NET; linux1 — клиент, linux2 — сервер заметок, storage — учебное хранение.

Разберёмся до действия

Хост Proxmox запускает виртуальные компьютеры — гости. Терминал хоста и терминал гостя управляют разными системами. Linux-мост соединяет виртуальные сетевые интерфейсы в один сегмент, подобно коммутатору. Три отдельных моста стенда создают три сегмента. Для обмена между их IP-подсетями нужен маршрутизатор с подходящими маршрутами; само различие названий мостов маршруты не создаёт. Карта стенда связывает имена машин, адреса, роли и владельцев данных.

Среда и права: Только чтение схемы. Создание ВМ будет отдельным действием.

Разобранный пример

Данные примера:

браузер → linux1 → router → linux2 → файл заметки
CLIENT-NET         SERVER-NET
                    storage → STORAGE-NET

Ожидаемый результат: На рисунке отделены хост, гости, сегменты и маршрут запроса. Доступ к панели Proxmox не означает доступ к HTTP-серверу внутри linux2.

Когда известны узлы пути, можно проверить каждый переход и выбрать место выполнения команды. Без карты успешный ping на хосте легко принять за проверку гостя.

При отклонении: Не подставляй адрес управляющего интерфейса Proxmox вместо адреса гостя. Если фактическая схема отличается, сначала исправь карту и только затем выполняй сетевые опыты.

C00-0: Зачем в учебном стенде отдельные CLIENT-NET, SERVER-NET и STORAGE-NET?

Изолированные мосты создают наблюдаемые сегменты второго уровня. Связь между ними требует маршрутизатора, поэтому путь пакета можно разбирать по слоям. Применение к описанным условиям: Чтобы наблюдать маршрутизацию и отказы между изолированными сегментами.

C00-0b: Две машины подключены к разным изолированным мостам и разным IP-подсетям. Маршрутизатор между ними ещё не настроен. Почему прямой связи нет?

Изолированный мост — отдельный домен второго уровня. Связь между сегментами даёт маршрутизатор, и поэтому путь пакета на стенде разбирается по слоям. Применение к описанным условиям: Сегменты разделены; для обмена IP между подсетями нужна настроенная маршрутизация.

C00-1: Что делает повторение работы со сломанным стендом осмысленным?

Известная исходная точка делает опыт повторяемым и позволяет связать наблюдаемый эффект с конкретным изменением. Применение к описанным условиям: Известная исходная точка: шаблон или снимок плюс зафиксированная конфигурация.

C00-1b: Почему работу на стенде начинают со снимка и записанной конфигурации?

Опыт повторяем только от известной исходной точки: без неё непонятно, что именно вызвало наблюдаемый эффект. Применение к описанным условиям: Чтобы наблюдаемый эффект можно было связать с изменением.

Зачем начинать с железа, если книга в основном про Linux

Представьте две книги. В первой на странице 1 написано: «мост — устройство второго уровня, решение о пересылке принимается по MAC-адресу». Во второй сначала показывают физический компьютер с одним Ethernet-портом, устанавливают на него гипервизор, создают программный мост, подключают к нему две VM и наблюдают, как они начинают видеть друг друга. Только после этого появляется термин bridge.

Формально обе книги сообщили один и тот же факт. Но во втором случае у читателя уже есть объект, к которому можно прикрепить понятие. В дальнейшем, когда появятся VLAN, tap-интерфейсы, виртуальные маршрутизаторы и межсетевые экраны, они будут расширять знакомую систему, а не висеть в воздухе.

Поэтому наш первый учебный объект — не команда Linux. Это маленький ЦОД внутри одного физического компьютера.

К концу Части 0 у нас будет:

На схеме много новых слов. Сейчас их не нужно заучивать. Важно увидеть роли:

  • lab-host предоставляет CPU, RAM, диски и физическую сеть;
  • гипервизор позволяет разделить эти ресурсы между виртуальными машинами;

Критерий выполнения. Показать разбор

Разбор. Доказано: у linux1 есть адрес 10.10.10.11/24 на работающем интерфейсе; шлюз 10.10.10.1 достижим; маршрутизация CLIENT-NET → SERVER-NET работает — ответил linux2; выход в интернет по IP-адресу работает. Опровергнуто: заявление «стенд готов полностью» — пункт «разрешить DNS-имя» из контрольной точки 0.21 не выполняется, и запись в журнале противоречит карточке, на которую ссылается. Вариант A — один существующий компьютер

Подходит, если отдельного железа нет.

Желательно:

  • x86-64 CPU с аппаратной виртуализацией Intel VT-x/AMD-V;
  • 32 ГБ RAM;
  • около 500 ГБ свободного SSD;
  • один сетевой интерфейс;
  • Windows или Linux как основная ОС.

На таком компьютере можно использовать Hyper-V, VMware Workstation или KVM/libvirt. Логика лаборатории остаётся той же: несколько виртуальных L2-сетей и набор VM. В книге основным эталонным вариантом будет Proxmox VE на отдельном хосте, но главы про Linux, сети, службы хранения и автоматизацию не зависят от конкретного графического интерфейса гипервизора.

Ограничение: хост нельзя свободно перезагружать, вытаскивать NIC/HBA или менять прошивку, если это ваша рабочая машина. Аппаратные лаборатории придётся выполнять позже на отдельном сервере.

Вариант B — отдельный лабораторный ПК или сервер — рекомендуемый

Это лучший баланс.

Практически удобная конфигурация:

Компонент Минимально комфортно Рекомендуемо
CPU 4 физических ядра / 8 потоков 8–16 ядер
RAM 32 ГБ 64 ГБ
Системный накопитель 256–512 ГБ SSD 1 ТБ NVMe/SSD
NIC 1×1GbE 2×1/2.5/10GbE
Доп. диски не обязательны 2–4 отдельных SATA/SAS/NVMe

Почему 64 ГБ удобно: учебник иногда требует одновременно держать router, две Linux VM, storage, monitoring и automation. Каждая по отдельности небольшая, но запас памяти позволяет не думать о постоянном выключении соседних узлов. Для мини-Ceph потребуется несколько дополнительных VM, поэтому при 32 ГБ другие машины придётся временно останавливать.

Официальные требования Proxmox для ознакомительной установки намного ниже, но это требования к запуску самого гипервизора, а не к нашей учебной инфраструктуре. Здесь ресурсы выбираются под набор гостей и эксперименты.

0.7. Что такое vmbr0 на физическом уровне

Начнём с моста, которого нет в плане адресов: его завёл сам Proxmox при установке. После стандартной установки он создаёт мост vmbr0, связанный с физическим NIC. Упрощённо:

             physical switch
                   |
                 cable
                   |
                 eno1
                   |
                 vmbr0
              /     |     \
           host    VM-A   VM-B

Физический NIC eno1 больше не является просто «местом, где лежит адрес хоста». Он становится портом моста. Адрес управления системой находится на vmbr0. Когда позже VM подключится к тому же мосту, внешняя сеть увидит MAC-адрес VM как отдельного участника сегмента Ethernet.

Это первый пример важного принципа книги: имя интерфейса, IP-адрес и физический разъём — не одно и то же.

Посмотрите на хосте:

ip -br link
ip -br addr
bridge link
cat /etc/network/interfaces

Найдите в конфигурации связь между физическим NIC и vmbr0. Заодно вы увидите там три моста, которых после установки Proxmox не было, — и ни у одного из них нет ни порта, ни адреса. О них следующий раздел.

У вашего хоста моста может не оказаться вовсе: если управление живёт прямо на физическом интерфейсе, а стенд собран с STAND_WAN_MODE=nat, роль внешнего моста играет vmbr90 с адресом на хосте. Всё сказанное дальше от этого не меняется.

0.8. Три изолированных программных моста

[VM]

Три моста стенда уже подняты. Посмотрите на них:

ip -br link | grep vmbr
bridge link
  • vmbr10 — CLIENT-NET;
  • vmbr20 — SERVER-NET;
  • vmbr30 — STORAGE-NET.

Общего у всех трёх два свойства, и оба нарочные: ни одного физического порта и ни одного адреса.

Почему нет физического порта? Потому что они изображают три отдельных коммутатора Ethernet, которые существуют только внутри хоста-гипервизора. Машины на разных мостах без маршрутизатора не обмениваются IP-пакетами между сегментами. Кадр, попавший в vmbr10, наружу не выйдет — выходить некуда.

Почему нет адреса хоста? Потому что сейчас сам Proxmox не должен быть участником этих сетей. Он только предоставляет среду второго уровня. Позже мы специально добавим мосту адрес и увидим, что это меняет.

Вот как это записано в /etc/network/interfaces — откройте файл и найдите этот кусок у себя:

auto vmbr10
iface vmbr10 inet manual
        bridge-ports none
        bridge-stp off
        bridge-fd 0

auto vmbr20
iface vmbr20 inet manual
        bridge-ports none
        bridge-stp off
        bridge-fd 0

auto vmbr30
iface vmbr30 inet manual
        bridge-ports none
        bridge-stp off
        bridge-fd 0

bridge-ports none — это и есть «коммутатор без единого кабеля». inet manual — «адреса у интерфейса не будет».

Если собираете руками. Создайте в Proxmox три Linux Bridge с теми же именами: Bridge ports оставьте пустым, IPv4/CIDR и Gateway не назначайте, STP пока off, автозапуск on. Не копируйте конфигурацию вслепую поверх своей — безопаснее создать объекты через интерфейс и затем сравнить результат с файлом.

Что у вас теперь есть

Настоящий объект второго уровня. Он виртуальный, но принципы пересылки кадров у него реальные. Когда в главе 8 появится фраза «мост Linux пересылает кадры Ethernet между портами», у вас будет конкретный vmbr20, который можно наблюдать.

0.9. Откуда взялись шесть машин: облачный образ вместо установки с ISO

Систему на эти шесть машин никто не устанавливал. Скрипт скачал один готовый образ Debian — debian-12-genericcloud-amd64.qcow2 — и импортировал его как диск каждой машине. Всё остальное: имя узла, пользователь, адреса на четырёх интерфейсах, установленные пакеты — гость получил при первой загрузке с отдельного маленького диска, который готовит гипервизор. Механизм называется cloud-init.

Отсюда первое наблюдение, которое пригодится всю книгу: диск машины и настройка машины — разные вещи. Образ одинаков у всех шести; различает их то, что лежит на служебном диске рядом. Посмотрите на хосте, из чего он состоит:

qm cloudinit dump 9001 user
qm cloudinit dump 9001 network

Установка шести машин с ISO дала бы тот же результат за шесть одинаковых часов. Облачные образы придуманы ровно для того, чтобы этого не делать; в главе про автоматизацию окажется, что и остальная работа устроена так же.

Сетевой интерфейс у всех машин VirtIO, дисковый контроллер — VirtIO SCSI. Это паравиртуализованные устройства: гость знает, что работает в виртуальной среде, и взаимодействует с хостом эффективнее, чем при полной эмуляции старого железа. В главе про KVM мы разберём это детально.

Набор инструментов на узлах одинаков — qemu-guest-agent, curl, vim, git, tcpdump, traceroute, mtr-tiny, dnsutils. Ставит их не список пакетов cloud-init, а маленький сценарий, который сначала дожидается связи: пять узлов выходят наружу только через router, и в момент их первой загрузки его ещё нет.

Если собираете руками. Загрузите в хранилище Proxmox актуальный образ Debian stable или Ubuntu Server LTS и установите одну машину — linux-base: 2 vCPU, 2048 МиБ, диск 32 ГиБ на шине SCSI/VirtIO SCSI, сетевая карта VirtIO в vmbr20, прошивка UEFI. На этапе установки включите сервер SSH. После первого входа поставьте тот же набор пакетов:

sudo apt update
sudo apt install -y qemu-guest-agent curl vim git tcpdump traceroute mtr-tiny dnsutils
sudo systemctl enable --now qemu-guest-agent

Для всей книги выберите одну базовую серверную ОС и не меняйте её от главы к главе: иначе различия дистрибутивов начнут маскироваться под различия механизмов. И если у гостя ещё нет доступа в интернет, не чините это случайными командами — сначала закончите VM router, пакеты можно поставить после неё.

0.10. Один образ на шесть машин: почему это важнее удобства

Все шесть узлов стенда выросли из одного и того же файла. Собранные руками, они вырастают из шаблона: linux-base выключается, превращается в шаблон, и из него делаются linux1, linux2, storage, monitoring, automation.

Общий исходный образ нужен не ради экономии времени. Он делает лаборатории воспроизводимыми. Если после break/fix система пришла в неизвестное состояние, вы возвращаете известную точку и повторяете эксперимент, а не гадаете, что из вчерашнего осталось. Это тот же принцип, который позже появится в автоматизации: контролируемое исходное состояние снижает число неизвестных переменных.

Ресурсы VM

Скрипт раздаёт их так; собирая руками, держитесь этих же чисел:

VM vCPU RAM Системный диск Дополнительно
router 2 2 ГиБ 16 ГиБ 4 NIC
linux1 2 2 ГиБ 32 ГиБ —
linux2 2 2 ГиБ 32 ГиБ —
storage 4 4 ГиБ 32 ГиБ 4 диска по 8 ГиБ
monitoring 2 4 ГиБ 40 ГиБ —
automation 2 2 ГиБ 32 ГиБ —

RAM не нужно резервировать по максимуму одновременно. На хосте с 32 ГБ включайте только узлы текущей лаборатории — остальные пусть стоят выключенными.

Сумма по таблице — 16 ГиБ памяти и 216 ГиБ дисков, но столько стенд не занимает. Измерено на собранном стенде: все шесть машин запущены и настроены, а процессы виртуальных машин держат около 5 ГиБ, в простое — около 3,5 ГиБ; в хранилище с тонким выделением занято около 11 ГиБ из 216 выделенных. Хост, на котором это измерялось, имеет 12 ГиБ памяти — и шесть машин на нём работают одновременно. Память и место отдаются по мере обращения, а не при создании: это то же свойство, из-за которого «свободно» и «выделено» в отчётах гипервизора расходятся в разы.

0.11. Как машина попадает в свою сеть

Машина оказывается в сети не потому, что у неё такой адрес, а потому, что её виртуальная сетевая карта воткнута в определённый мост. Посмотрите на хосте:

qm config 9001 | grep -E 'net|ipconfig'

Строка net0: virtio=…,bridge=vmbr10 и есть «кабель, воткнутый в коммутатор vmbr10». Целиком раскладка стенда такая:

router:
  net0 -> vmbr0   (WAN/management LAN; в режиме nat — vmbr90)
  net1 -> vmbr10  (CLIENT)
  net2 -> vmbr20  (SERVER)
  net3 -> vmbr30  (STORAGE)

linux1:
  net0 -> vmbr10

linux2:
  net0 -> vmbr20

storage:
  net0 -> vmbr20
  net1 -> vmbr30

monitoring:
  net0 -> vmbr20

automation:
  net0 -> vmbr20

Теперь остановитесь и мысленно проследите один путь:

Если linux1 хочет обратиться к linux2, между ними нет общего моста. Значит, кадр не может просто перейти из vmbr10 в vmbr20. Нужен объект, у которого есть интерфейс в обеих сетях — router.

Мы ещё не изучали маршрутизацию, но необходимость в ней уже стоит перед вами в виде работающей схемы. Убедиться можно прямо сейчас: выключите router и повторите пинг с linux1 на linux2. Потом включите обратно.

Если собираете руками. Назначьте интерфейсы по этой же таблице.

0.12. Маршрутизатор: что он уже умеет и чего у него нет

[VM]

Зайдите на router — через консоль Proxmox или qm terminal 9000 — и посмотрите, что там настроено:

ip -br link
ip -br addr
ip route
sysctl net.ipv4.ip_forward
sudo nft list ruleset

Сначала имена интерфейсов. В машинах, собранных из облачного образа, они называются eth0, eth1, eth2, eth3; в системе, установленной с ISO, — скорее ens18 и дальше по порядку. Ни то ни другое не следует заучивать: смотрите ip -br link и подставляйте своё. Порядок при этом тот же, что в разделе 0.11: первый интерфейс — внешний, дальше три учебные сети по порядку — vmbr10, vmbr20, vmbr30.

Дальше — то, ради чего router существует. Пересылка пакетов включена:

net.ipv4.ip_forward = 1

И есть одно правило трансляции — всё, что уходит наружу, выходит с адресом самого маршрутизатора:

table ip nat {
    chain postrouting {
        type nat hook postrouting priority srcnat; policy accept;
        oifname "eth0" masquerade
    }
}

Этого достаточно, чтобы узлы стенда видели друг друга и выходили в интернет. И это всё, что там есть. Фильтрующих правил нет вовсе — ни одной цепочки forward в выводе вы не найдёте, а значит пересылается всё, что может быть переслано.

Для учебного стенда за вашим же маршрутизатором это приемлемо, но полезно увидеть разницу между «работает» и «настроено». Ниже — та же функция плюс фильтрация: пропускать ответы на установленные соединения, выпускать внутренние сети наружу, разрешать им говорить между собой, остальное отбрасывать. Имена интерфейсов подставьте свои.

#!/usr/sbin/nft -f
# Только выделенная router VM, не гипервизор и не рабочий host.
# Таблицы course_filter/course_nat ещё не должны существовать.
table inet course_filter {
    chain forward {
        type filter hook forward priority 0;
        policy drop;
        ct state established,related accept
        iifname { "eth1", "eth2", "eth3" } oifname "eth0" accept
        iifname { "eth1", "eth2", "eth3" } oifname { "eth1", "eth2", "eth3" } accept
    }
}
table ip course_nat {
    chain postrouting {
        type nat hook postrouting priority 100;
        oifname "eth0" ip saddr { 10.10.10.0/24, 10.10.20.0/24, 10.10.30.0/24 } masquerade
    }
}

Сохраните в /etc/nftables.conf только на router и только имея консоль. Сначала сохраните текущий набор правил и убедитесь, что таблиц course_filter/course_nat ещё нет: этот пример рассчитан на первое применение, а не на дописывание в существующие таблицы. Правило трансляции, которое положил cloud-init, лежит в таблице nat и будет заменено вашей — поэтому применять надо целиком, а не по одной команде.

sudo nft list ruleset > "$HOME/nft-before-course.txt"
sudo nft -c -f /etc/nftables.conf
sudo nft -f /etc/nftables.conf
sudo systemctl enable nftables
sudo nft list ruleset

После применения проверьте доступ в интернет и связь между сегментами, затем перезагрузите машину и проверьте ещё раз: правило, работающее до перезагрузки и исчезающее после неё, — самая частая ошибка этого места. Чужие базовые цепочки могут дополнительно фильтровать трафик: эта конфигурация не предназначена для совмещения с UFW, firewalld или действующим межсетевым экраном. Правила входящей цепочки для защиты самого router изучаются отдельно; это не законченный межсетевой экран для промышленной среды.

Не нужно сейчас запоминать hook, priority или masquerade. Глава 8 разложит этот файл на путь пакета. Пока важен результат: router пересылает пакеты между внутренними сетями и транслирует их адреса наружу.

Если собираете руками. Адреса внутренним интерфейсам — 10.10.10.1/24, 10.10.20.1/24, 10.10.30.1/24; внешнему — DHCP или статика по вашей LAN. В Ubuntu это Netplan:

network:
  version: 2
  ethernets:
    ens18:
      dhcp4: true
    ens19:
      addresses: [10.10.10.1/24]
    ens20:
      addresses: [10.10.20.1/24]
    ens21:
      addresses: [10.10.30.1/24]

Применяйте из консоли гипервизора, а не через единственный сеанс SSH: sudo netplan try, затем sudo netplan apply. Пересылку включите файлом в /etc/sysctl.d, а не командой на лету — иначе она не переживёт перезагрузку:

cat <<'EOF' | sudo tee /etc/sysctl.d/99-lab-router.conf
net.ipv4.ip_forward=1
EOF
sudo sysctl --system

0.13. Где на самом деле заданы адреса узлов

Зайдите на linux1 и посмотрите его адрес:

ip -br addr
ip route

А теперь посмотрите на хосте, откуда он взялся:

qm config 9001 | grep ipconfig

Адрес гостя записан вне гостя — в конфигурации виртуальной машины, и cloud-init переносит его внутрь при загрузке. Для книги это важное наблюдение: у одной и той же настройки бывает несколько мест хранения, и вопрос «где это на самом деле задано» будет возвращаться в главах про сеть, службы и автоматизацию.

Адресный план стенда целиком:

linux1       10.10.10.11/24   GW 10.10.10.1
linux2       10.10.20.12/24   GW 10.10.20.1
storage      10.10.20.20/24   GW 10.10.20.1
             10.10.30.20/24   без шлюза
monitoring   10.10.20.30/24   GW 10.10.20.1
automation   10.10.20.40/24   GW 10.10.20.1

Разрешение имён у всех узлов — 1.1.1.1; замените на DNS вашей сети, если он есть.

На втором интерфейсе storage нет второго шлюза по умолчанию, и это не упущение. Причину подробно разберём в главе 6; пока воспринимайте как ограничение исходной схемы и не «чините» его.

Если собираете руками. Задайте те же адреса в самих системах.

0.14. Первая проверка связности: не «пинговать всё подряд», а идти по пути

Это первая настоящая проверка стенда — и первый раз, когда вы пользуетесь диагностической моделью, которую книга будет применять до последней главы.

Зайдите на linux1. Напрямую с хоста он недоступен: его сеть живёт внутри vmbr10, и у гипервизора там нет адреса. Значит — консоль Proxmox или ssh course@10.10.10.11 с маршрутизатора, у которого интерфейс в этой сети есть. То, что вход приходится искать, — само по себе следствие схемы, а не неудобство.

ip -br addr
ip route
ping -c 2 10.10.10.1
ping -c 2 10.10.20.12
ping -c 2 1.1.1.1
getent hosts example.com

Порядок важен:

  1. есть ли локальная конфигурация интерфейса;
  2. достижим ли ближайший маршрутизатор;
  3. работает ли маршрутизация между учебными сетями;
  4. работает ли выход наружу;
  5. работает ли разрешение имён.

Вы уже используете будущую диагностическую модель, хотя ещё не знаете деталей ARP, поиска маршрута и DNS.

Если шаг 2 не работает, нет смысла начинать с DNS. Если шаг 4 работает, а шаг 5 нет, менять VLAN тоже бессмысленно. Это первое знакомство с локализацией границы отказа.

0.15. Диски узла storage: сопоставьте три уровня

[VM]

У узла storage кроме системного диска есть ещё четыре, по 8 ГиБ, и у каждого своё имя: серийный номер COURSE-DISK-1 … COURSE-DISK-4 и собственный WWN. Зайдите на него и найдите их:

lsblk -o NAME,SIZE,TYPE,FSTYPE,MODEL,SERIAL,WWN
ls -l /dev/disk/by-id/

Размечать их сейчас не нужно. Задача ровно одна — сопоставить три уровня:

объект в интерфейсе гипервизора (scsi1 … scsi4)
        ↓
виртуальный контроллер и устройство
        ↓
объект, который увидел Linux guest (/dev/sdb … /dev/sde)

Связывают первый уровень с третьим не буквы. Имя /dev/sdb за диском не закреплено и после перезагрузки может достаться другому — на этом стенде так и происходит. А вот в /dev/disk/by-id/ каждый из четырёх лежит под своим WWN, вида wwn-0x5000c0de00000001, и серийный номер виден в lsblk: и то и другое принадлежит самому диску, а не порядку, в котором ядро их нашло. Убедитесь, что находите нужный диск с обеих сторон именно так. В главах про хранение это станет отдельной темой — и там адресовать диск по by-id будет уже привычкой.

Если собираете руками. Выключите storage и добавьте четыре диска. Серийный номер задаётся полем Serial, а WWN — только из командной строки: qm set 9003 --scsi1 local-lvm:8,ssd=1,serial=COURSE-DISK-1,wwn=0x5000c0de00000001. Без WWN в by-id окажется не имя диска, а номер слота, в который он воткнут, — то самое, от чего это упражнение отучает. Размер можно взять и больше, 20 ГиБ; важнее, чтобы дисков было четыре и они различались по имени.

Ограничение виртуальных дисков

Виртуальный диск хорошо подходит, чтобы изучить блочный слой, разметку, метаданные RAID, LVM и файловую систему. Но он не воспроизводит честно:

  • физическую линию SATA/SAS;
  • SMART конкретного накопителя;
  • отказ объединительной платы или экспандера;
  • потерю питания;
  • реальные характеристики задержек;
  • прошивку диска.

Когда книга перейдёт к этим темам, лаборатория будет помечена [ЖЕЛЕЗО].

0.16. Снимок — не резервная копия, но идеальная учебная перемотка

Перед первой поломкой создайте снимок baseline-00 для router и базовых узлов.

Снимок нужен, чтобы быстро вернуться к известному состоянию. Но не приучайтесь считать снимок резервной копией. Если погибнет хранилище, где лежат и снимок, и сама VM, они исчезнут вместе.

Для книги действует правило:

baseline snapshot -> лаборатория -> break/fix -> фиксация результата -> revert/новый baseline

А для ценных файлов учебного проекта:

Git repository + отдельная backup-копия

0.17. Создаём инженерный репозиторий ещё до написания скриптов

Слово «репозиторий» уже встречалось в этой главе дважды, и оба раза без объяснения. Исправим это здесь, потому что дальше он понадобится в каждой главе.

Репозиторий — это обычный каталог с файлами плюс сохранённая история его состояний. Разница с каталогом без истории простая: там правка затирает прежнее содержимое, здесь — нет. Каждое сохранённое состояние остаётся доступным, и к нему можно вернуться.

Единица истории называется коммитом, и это не копия одного файла, а снимок всех файлов сразу, с отметкой, кто его сделал, когда и зачем. Сразу всех — важная часть: план адресов, схема топологии и скрипт, который по ним собирает стенд, осмысленны только вместе. Вернуться нужно к их согласованному сочетанию, а не к трём файлам по отдельности, каждый из своего дня.

Отсюда три вещи, которые репозиторий даёт инженеру, и ни одна из них не про «хранить файлы».

  • Возврат к известному состоянию. То же, что снимок виртуальной машины из раздела 0.16, только для того, что вы написали сами, — и, в отличие от снимка, его можно унести с машины.
  • Ответ на вопрос «что изменилось». Две точки истории сравниваются построчно. Через месяц это единственный способ узнать, что именно вы правили в тот вечер, когда всё заработало.
  • Доказательство. Отметка времени и текст о причине превращают «кажется, это было после обновления» в проверяемое утверждение. Этой мыслью книга пользуется дальше постоянно, а в главе 21 доводит её до рабочего цикла изменений.

Заводить его до написания скриптов — не педантизм. Первое, что стоит записи, — не автоматизация, а решения: адресный план из раздела 0.5 и схема, которую вы нарисуете сейчас. Скрипты появятся позже и лягут рядом.

В lab-topology.md вручную нарисуйте ASCII-схему стенда и подпишите интерфейсы. Не копируйте готовую схему из книги без проверки: ваши имена физических NIC и сеть управления могут отличаться.

Первый коммит:

git add .
git commit -m "Document initial lab topology"

Четыре команды, которыми вы будете пользоваться постоянно, делают вот что. git status отвечает, чем текущее состояние каталога отличается от последнего записанного. git add выбирает, что войдёт в следующую запись, — выбирает, а не сохраняет: изменить можно было пять файлов, а записать один. git commit делает саму запись. git log показывает список записей.

git status
git log --oneline
git diff

Разделение add и commit кажется лишним ровно до первого раза, когда вы одновременно чинили одно и пробовали другое: в историю должно уехать почини́вшее, а не всё подряд. git diff показывает, что изменилось с последней записи, и читать его перед каждой записью — привычка того же рода, что читать план перед сборкой стенда.

И граница, которую стоит понимать сразу. Репозиторий на automation живёт ровно до тех пор, пока жив automation: история изменений лежит в том же каталоге, что и файлы, и исчезнет вместе с машиной. Это не изъян, а следствие того, что он пока в одном месте. Копия в другом — на рабочем компьютере или на внешней службе — делается одной командой, и раздел 0.18 о восстановлении требует именно её. Как устроена такая копия и почему она же служит рабочим механизмом, разбирается в главе 21.

Позже Git станет инструментом автоматизации. Сейчас он выполняет более фундаментальную функцию: фиксирует эволюцию инфраструктуры и вашего понимания.

0.18. Первый break/fix: неправильный шлюз

[VM]

На linux1 запишите текущее состояние:

ip -br addr
ip route

Теперь временно замените шлюз по умолчанию на несуществующий адрес из своей подсети, например 10.10.10.254.

Не пытайтесь сразу исправлять. Сначала наблюдайте:

ping -c 2 10.10.10.1
ping -c 2 10.10.20.12
ping -c 2 1.1.1.1
ip route
ip neigh

Задайте себе вопросы:

  1. Работает ли связь внутри локальной подсети?
  2. Что перестало работать только после выхода за её пределы?
  3. Какой объект должен получить кадр Ethernet для удалённой сети?
  4. Что в текущей конфигурации заставляет хост выбрать неправильный объект?

Исправьте шлюз и повторите те же измерения.

Сейчас вы, возможно, ещё не сможете точно объяснить ARP и выбор самого длинного совпадающего префикса. Это нормально. Запишите наблюдение. В главе 6 мы вернёмся к этому инциденту и разберём его уже на уровне пути пакета.

0.19. Как подключать настоящее серверное железо позже

Когда появится свободный сервер, не нужно переносить на него всю лабораторию. Лучше добавить его как ещё один объект.

Пример:

                     management LAN
                     /            \
              pve-lab01          srv-lab01
                  |                  |
             virtual lab        BMC/IPMI + OS
                                     |
                           HBA/RAID/backplane/disks

automation сможет подключаться к физическому серверу по SSH. monitoring — собирать метрики узла и IPMI. Вы получите связь между уже изученными логическими слоями и реальным железом.

Для главы про VLAN можно добавить управляемый коммутатор:

pve-lab01 NIC1 ---- trunk ---- switch ---- access VLAN 110 ---- srv-lab01 NIC1
                                  |
                                  +---- access VLAN 120 ---- laptop/test host

Для главы про хранение — HBA и свободные диски. Для прошивок — BMC, UEFI Shell и физическое устройство PCIe.

Так лаборатория растёт вместе с книгой, вместо того чтобы требовать купить маленький ЦОД на первой странице.

0.20. Что нельзя безопасно эмулировать

Очень важно понимать границу стенда.

Тема VM достаточно? Что теряется
systemd, права, пакеты да почти ничего существенного
маршрутизация, межсетевой экран, DNS, идея VLAN да отказы физического коммутатора и NIC
LVM, mdraid, файловые системы да поведение при отказе носителя и контроллера
iSCSI, логика multipath да поведение физической фабрики и HBA
методика замеров fio частично реальные свойства задержек, кеша и устройств
планирование времени CPU да для основы топология NUMA может быть искусственной
перечисление устройств PCIe частично реальное согласование линии, райзеры, питание
BMC/IPMI нет полноценно отдельный контроллер управления
экспандер SAS и объединительная плата нет оборудование PHY, топология, SES
обновление прошивки нет полноценно риски восстановления, специфичные для платформы

Не делайте вывод «на VM работает — значит рабочее железо исправно». Виртуальная лаборатория обучает модели. Физическая — добавляет реальные сценарии отказа.

0.20A. Если основной компьютер нельзя отдать под голое железо

Не каждый ученик может выделить отдельный сервер. Тогда главное — сохранить топологию, а не название программы.

Хост с Windows

В Hyper-V создайте несколько виртуальных коммутаторов типа Internal или Private, соответствующих CLIENT-NET, SERVER-NET и STORAGE-NET, и один External для VM router с выходом в WAN. Список машин и адресный план оставьте такими же. Не создавайте случайно несколько шлюзов по умолчанию на интерфейсах управления.

VMware Workstation позволяет использовать сети host-only и пользовательские виртуальные сети аналогичным образом. Сеть с NAT можно использовать для первоначального выхода в WAN, а внутренние сегменты — как изолированные сети.

Настольный Linux

KVM/libvirt — наиболее близкая к Proxmox внутренняя модель. Можно создать:

  • сеть с NAT для WAN;
  • три изолированные сети;
  • гости QEMU/KVM через virt-install/virt-manager.

Libvirt сам создаёт программные мосты для управляемых изолированных и NAT-сетей. Позже в главе 17 полезно сравнить их с Proxmox vmbr*.

Что нельзя делать на рабочем компьютере

Не экспериментируйте с основным межсетевым экраном, загрузчиком, пробросом через IOMMU или мостом поверх единственного подключения Wi-Fi либо Ethernet, если потеря доступа мешает работе. Разрушающие задания выполняйте внутри клонов VM.

0.20C. Управляемый коммутатор: когда он действительно нужен

Для первых восьми глав программных мостов полностью достаточно. Управляемый коммутатор нужен, когда хотите перейти от «VLAN как метка в виртуальном тракте» к реальной настройке портов trunk и access.

Минимальные полезные свойства:

  • 802.1Q VLAN;
  • настраиваемые порты access и trunk;
  • желательно счётчики портов и статистика ошибок;
  • желательно LACP для работ по объединению интерфейсов;
  • зеркалирующий порт (SPAN) полезен для перехвата пакетов.

Начальная физическая схема может быть простой:

Proxmox NIC1 ---- trunk ---- managed switch
                         |-- access VLAN 110 -- test server
                         |-- access VLAN 120 -- laptop/test host

Сначала создайте VLAN только на изолированном учебном коммутаторе. Не экспериментируйте с рабочим VLAN управления.

Физический уровень

  • какой компьютер является lab-host;
  • где его NIC управления;
  • где лежат системный диск и диски VM;
  • включена ли аппаратная виртуализация.

Гипервизор

  • Proxmox/KVM запускается;
  • есть доступ к управлению;
  • созданы vmbr10, vmbr20, vmbr30 или функциональные аналоги.

VM

  • router;
  • linux1;
  • linux2;
  • storage;
  • monitoring;
  • automation.

Необязательно держать их все включёнными.

Сеть

разрешить DNS-имя

0.22. Что вы уже узнали, хотя «теория» ещё не начиналась

Мы намеренно не открывали лекцию словами «L2, L3, гипервизор, блочное устройство». Но после сборки у вас уже есть наблюдаемые объекты:

physical NIC -> software bridge -> virtual NIC -> guest OS
virtual disk -> guest block device
CLIENT subnet -> router -> SERVER subnet
host -> hypervisor -> VM
configuration -> break -> observation -> recovery

Теперь термины следующих глав будут отвечать на вопросы, которые уже возникли у вас в руках.

Это и есть точка входа в основную книгу.
