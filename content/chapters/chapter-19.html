Часть VI. Автоматизация

Автоматизируем уже понятые действия

Слишком ранняя автоматизация закрепляет непонимание быстрее, чем ручная работа. Поэтому Bash, Python и Ansible появляются после того, как основные диагностические операции уже выполнялись руками.

Теперь повторяющиеся инвентаризация, сбор данных, настройка и проверка превращаются в воспроизводимые инструменты. Цель — не синтаксис ради синтаксиса, а безопасный контракт автоматизации.

19. Bash как инженерный инструмент

Академическое продолжение этой главы: U21.

Цели главы

После главы вы должны уметь:

  • уверенно использовать конвейер, код возврата и перенаправление;
  • писать безопасные небольшие скрипты на Bash;
  • понимать set -euo pipefail и его ограничения;
  • применять grep, awk, sed, cut, sort, uniq, xargs, jq осмысленно;
  • избегать разбора вывода, рассчитанного на человека, там, где есть структурированный интерфейс;
  • создать диагностический сборщик, не изменяющий состояние сервера.

Перед началом: повторяемые наблюдения становятся кодом

Во многих прошлых главах набор первых команд без изменения состояния повторялся. Bash нужен не потому, что администратор должен писать большие программы в оболочке, а потому что короткий воспроизводимый сбор фактов лучше ручного копирования команд из истории.

Где это в стенде: automation хранит скрипты, целевые узлы — остальные VM. Начнём локально, затем будем собирать данные по SSH.

Критерий хорошего первого скрипта: он ничего не чинит. Он собирает одинаковые факты, корректно сообщает ошибки и не уничтожает исходное состояние.

Прежде чем читать. Скрипт завершился без сообщений об ошибках. Что это доказывает про то, что он сделал?

Ответьте до чтения — одной фразой, вслух или письменно. Неверный ответ здесь полезен не меньше верного: значение имеет сама попытка ответить прежде, чем прочитано объяснение. Разбор — в разделе «Типичная ошибка мышления»: перейти.

19.1. Оболочка — язык связывания инструментов

Сила Bash не в сложных алгоритмах, а в управлении процессами и потоками текста.

command A stdout
      |
      v
command B stdin
      |
      v
command C

Конвейер:

journalctl -k --since '-1 hour' | grep -Ei 'error|fail|timeout'

Но конвейер нужно понимать как несколько процессов, у каждого свой код возврата.

19.2. Код возврата

Команда Unix возвращает целочисленный статус. По соглашению 0 — успех, ненулевое значение — отказ или иной исход в зависимости от команды.

command
rc=$?
printf 'rc=%d\n' "$rc"

В скрипте лучше явно проверять операции, где отказ имеет смысловые последствия.

if ! mountpoint -q /data; then
    echo 'ERROR: /data is not mounted' >&2
    exit 1
fi

19.3. stdout и stderr

Разделяйте машинный вывод и канал ошибок или журналирования.

collect_info >report.txt 2>collector.err

Это особенно важно для автоматизации: если скрипт печатает предупреждения в стандартный вывод вместе с JSON, разбор на следующем шаге сломается.

19.4. Кавычки

Одна из главных причин ошибок в Bash — разбиение на слова и раскрытие шаблонов имён.

Предпочитайте:

rm -- "$file"
printf '%s\n' "$value"

а не:

rm $file

Если $file содержит пробелы, символ подстановки или начинается с -, последствия отличаются.

19.5. set -euo pipefail

Часто используемый строгий режим:

set -euo pipefail
  • -e — оболочка может завершиться на необработанной неуспешной команде;
  • -u — обращение к неустановленной переменной становится ошибкой;
  • pipefail — статус конвейера учитывает отказ не только последней команды.

Но -e имеет контекстные исключения (if, &&, ||, конвейеры и т. п.) и не заменяет продуманную обработку ошибок. Его нужно понимать, а не воспринимать как «сделать скрипт безопасным» одной строкой.

19.6. grep

grep отвечает на вопрос «какие строки соответствуют шаблону».

grep -Ei 'timeout|reset|failed' logfile

Для поиска подстроки без регулярных выражений:

grep -F 'exact[text]' file

Не используйте сложные регулярные выражения, если задача проще решается инструментом со структурированным выводом.

19.7. awk

awk удобен для текста, разбитого на поля.

ps -eo pid,%cpu,comm --no-headers | awk '$2 > 50 {print $1, $2, $3}'

Здесь есть допущение: поля вывода предсказуемы. Если утилита поддерживает JSON, CSV или собственный разделитель полей, структурированный вывод обычно устойчивее.

19.8. sed

sed хорош для построчных преобразований, но не является универсальным разборщиком форматов конфигурации.

Например:

sed 's/^[[:space:]]*//' file

Для YAML, JSON и XML лучше специализированные разборщики.

19.9. jq

Современная автоматизация часто работает с интерфейсами, отдающими JSON:

curl -sS https://example/api/status | jq '.health'

jq сохраняет структуру, в отличие от grep 'health', который может случайно найти нужное слово в другом поле.

19.10. Массивы и циклы

Безопаснее:

hosts=(server1 server2 server3)
for host in "${hosts[@]}"; do
    printf 'Checking %s\n' "$host"
done

чем хранить список с пробелами в одной строке и надеяться на разбиение по умолчанию.

19.11. Диагностический сборщик

Хороший сборщик, ничего не меняющий в системе, должен:

  • проставлять время и имя хоста;
  • ограничивать время выполнения команд;
  • сохранять поток ошибок;
  • не зависать на недоступных ресурсах;
  • не раскрывать секреты;
  • не менять состояние;
  • отмечать начало и конец каждого раздела.

Пример каркаса:

#!/usr/bin/env bash
set -u -o pipefail

section() { printf '\n===== %s =====\n' "$1"; }
run() {
    local rc=0
    printf '$'
    printf ' %q' "$@"
    printf '\n'
    timeout 15 "$@" 2>&1 || rc=$?
    printf '[exit=%d]\n' "$rc"
    return "$rc"
}

section SYSTEM
run hostnamectl
run uptime

section BLOCK
run lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,FSTYPE,MOUNTPOINTS

section PCI
run lspci -nnk

Функция сохраняет исходные аргументы и возвращает код команды. Скрипт намеренно не использует errexit, чтобы сохранить частичный отчёт при неудаче отдельной проверки. Timeout ограничивает время, но этот короткий пример на Bash ещё не ограничивает объём вывода; вариант с лимитом байтов и структурой JSON находится в университетском практикуме.

19.12. Защита в действии: три строки и что они ловят

Про set -euo pipefail легко согласиться, не увидев разницы. Вот она, тремя запусками на стенде.

Код возврата конвейера.

false | true; echo "код: $?"
set -o pipefail; false | true; echo "код: $?"
код: 0
код: 1

Конвейер сборка | tee журнал без pipefail отчитается об успехе провалившейся сборки: последним отработал tee, и он справился.

Необъявленная переменная. Без set -u опечатка в имени или несработавший export оставляют вместо пути пустоту, и команда получает совсем не тот аргумент:

rm -rf "$LOGDIR/old"       # LOGDIR не задана: команда получает /old
set -u; echo "${LOGDIR}/old"
LOGDIR: parameter not set

Разница принципиальная: в первом случае скрипт удаляет каталог в корне и не печатает ни слова, во втором — останавливается на месте. Это тот самый случай, ради которого в первой строке стоит set -u.

Чего set -e не делает. Он молчит там, где отказ уже обработан синтаксически:

set -e
false || true
echo "эта строка выполнится"

Команда слева от || не считается провалом — её результат используется. То же в условиях if, в while и в функции, вызванной внутри условия: там set -e выключен по стандарту оболочки. Поэтому строка set -euo pipefail — разумный минимум, а не гарантия; шаг, отказ которого меняет смысл дальнейшего, проверяется явно, как в разделе 19.2.

19.13. Разделение слов: почему for f in $(ls) ломается

Раздел 19.4 требовал кавычек вокруг подстановок. Посмотрим, во что обходится их отсутствие: в каталоге лежит один файл с пробелами в имени.

for f in $(ls /tmp/wtest); do echo "аргумент: $f"; done
аргумент: файл
аргумент: с
аргумент: пробелом.txt

Результат подстановки прошёл разделение на слова уже после того, как ls его вернул, — и один файл стал тремя аргументами. Кавычки вокруг $(ls …) здесь не спасут: они склеят все имена в одну строку. Правильный обход не использует ls вовсе, потому что раскрытие шаблона выполняет сама оболочка и его результат разделению не подвергается:

for f in /tmp/wtest/*; do echo "аргумент: $f"; done
аргумент: /tmp/wtest/файл с пробелом.txt

Для рекурсивного обхода и произвольных имён — find с нулевым разделителем, единственным байтом, который в имени файла встретиться не может:

find /srv -name '*.log' -print0 | while IFS= read -r -d '' file; do
  gzip -- "$file"
done

Здесь существенна каждая деталь: -print0 и -d '' разделяют нулевым байтом, IFS= отключает обрезку пробелов по краям, read -r запрещает толковать обратную косую черту как экранирование, а -- не даёт принять за ключ имя, начинающееся с дефиса. Пропущенная деталь ломает обработку не всех файлов, а редких — и потому обнаруживается позже всего.

19.14. Разобранный пример: grep выдаёт неправильную температуру

Ситуация

Скрипт:

sensors | grep 'Package' | awk '{print $4}'

на новом сервере выдаёт пустую строку.

Стратегия

Скрипт опирается сразу на три необъявленных допущения: что нужная строка содержит слово Package, что искомое число стоит в четвёртом поле и что разделителем полей является пробел. Любое из них может не выполниться на другой машине. Проверяем их по одному — вместо того чтобы подбирать индекс.

Действия

sensors                                   # что вообще печатается
sensors | grep -n 'Package'               # есть ли такая строка
sensors | grep 'Package' | cat -A | head  # где реальные границы полей
LC_ALL=C sensors | grep 'Package'         # зависит ли вывод от локали
ls /sys/class/hwmon/hwmon*/name           # машиночитаемый источник

Получено:

# старый сервер
Package id 0:  +41.0°C  (high = +80.0°C, crit = +100.0°C)
          ↑ $1  $2 $3    $4 = +41.0°C

# новый сервер
Tccd1:         +38.2°C
Tctl:          +44.0°C
# grep 'Package' — ни одной строки

Интерпретация

Скрипт не «выдаёт неправильную температуру» — он не выдаёт ничего, и это разные неисправности. На новом сервере другой процессор, у него другой драйвер hwmon, и датчики называются Tctl и Tccd1 вместо Package id 0. Строки, которую ищет grep, не существует; конвейер отрабатывает без ошибки и печатает пустоту.

Хуже того, что скрипт сломался, — то, как он сломался. Код возврата остался нулевым, сообщения об ошибке нет, в мониторинг ушло пустое значение. Такая поломка не видна: график просто перестаёт рисоваться, и это замечают через недели.

Разбор полей показывает и вторую мину: даже на старом сервере $4 — это результат случайного совпадения расположения слов. Достаточно другого названия датчика с иным числом слов, и та же команда начнёт печатать не температуру, а порог high — уже без всякого предупреждения.

Вывод

Правильное исправление — сменить источник, а не индекс поля. У sensors есть машиночитаемый режим, а ниже него — sysfs, где значение лежит отдельно от оформления:

sensors -j | jq -r '.[] | to_entries[] | select(.key|test("Package|Tctl")) |
  .value | to_entries[] | select(.key|endswith("_input")) | .value'

# или напрямую, без разбора текста вообще:
cat /sys/class/hwmon/hwmon2/temp1_input     # 41000 → милиградусы

Если машиночитаемого интерфейса нет и разбирать текст всё-таки приходится, парсер обязан объявлять свои допущения и падать при их нарушении: проверять, что строка найдена, что поле похоже на число, и возвращать ненулевой код возврата, когда это не так. Молчаливый пустой ответ — самый дорогой из возможных вариантов поведения.

19.15. Лаборатория

Создайте server-diagnostics-toolkit/bash/collect.sh, который собирает:

  • имя хоста, версия ядра, время работы;
  • процессор и память;
  • отказавшие юниты;
  • недавние предупреждения ядра;
  • диски и файловые системы;
  • устройства PCI;
  • сетевые адреса, маршруты, соседи;
  • слушающие порты.

Требования:

  • скрипт ничего не изменяет;
  • каждая команда имеет разумное ограничение по времени;
  • неизвестная команда не ломает весь отчёт;
  • отчёт содержит время и коды возврата проблемных разделов.

Концептуальное углубление: конвейер оболочки — поток байтов с соглашениями между программами

Сила оболочки Unix появляется из композиции небольших инструментов через стандартные потоки и коды возврата. Но эта же гибкость создаёт риск: пробелы, кавычки, раскрытие шаблонов и непроверенный код возврата легко превращают диагностический скрипт в источник ложных результатов.

set -euo pipefail полезен как строгое значение по умолчанию, но его тоже надо понимать. -e имеет исключения и не заменяет явную обработку ошибок; -u ловит неустановленные переменные; pipefail делает конвейер неуспешным, если один из компонентов завершился с ошибкой.

Кавычки

Разница между "$var" и $var — не вопрос стиля. Без кавычек оболочка выполняет разбиение на слова и раскрытие шаблонов. Пути с пробелами или данные, похожие на шаблон, могут изменить команду.

Машиночитаемый вывод

Если скрипт предназначен для дальнейшего разбора, лучше выводить TSV, JSON или пары «ключ — значение» последовательно, а оформление для человека делать отдельным слоем.

Это подготавливает переход к Python: когда модель данных сложнее строкового конвейера, нужен язык с нормальными структурами данных.

Практическое углубление: Скрипт диагностики должен быть безопасным по умолчанию

У рабочего диагностического инструмента есть требования, которых нет у одноразовой команды из истории оболочки:

  • по умолчанию только чтение;
  • явные ограничения по времени;
  • отсутствие зависания на одном недоступном устройстве;
  • поток ошибок не теряется;
  • код возврата отражает результат;
  • в выводе есть время и имя хоста;
  • чувствительные данные не попадают в отчёт случайно;
  • разрушающий режим, если он вообще существует, включается отдельным флагом.

Поэтому хороший скрипт оболочки начинается не с количества grep, а с контракта: что он читает, что изменяет, какой вывод обещает и как сигнализирует о частичном отказе.

Типичная ошибка мышления

Заблуждение. Скрипт отработал без сообщений об ошибках — значит всё выполнилось.

Почему это неверно. По умолчанию оболочка продолжает работу после неуспешной команды, а код возврата конвейера — это код последней команды в нём. cmd | grep x вернёт 0, даже если cmd вообще не запустилась. Неэкранированное раскрытие переменной с пробелом или с пустым значением молча превращается в другой набор аргументов — и команда выполняется, просто не та.

Что проверить вместо этого.

set -euo pipefail                 # первая строка любого рабочего скрипта
cmd | grep x; echo "${PIPESTATUS[@]}"   # код каждой части конвейера
shellcheck ./collect.sh           # находит большинство ошибок quoting

Для машинного разбора берите структурированный вывод источника (--json, -o json, -J) и jq, а не grep+awk по человекочитаемому формату: он не является контрактом и меняется между версиями утилиты.

Лестница самостоятельности

Эту главу не нужно считать завершённой после одной успешной лаборатории. Пройдите три уровня, уменьшая количество подсказок.

  1. С опорой: написать сборщик, ничего не меняющий в системе. На этом уровне разрешено смотреть разобранный пример и сверять ожидаемые результаты.
  2. С частичной опорой: добавить ограничение по времени и обработку ошибок. Перед каждой командой письменно сформулируйте, что именно она должна подтвердить или опровергнуть.
  3. Инцидент: собрать отчёт с нескольких хостов и корректно пережить частичный отказ. На этом уровне сначала фиксируются симптом и подтверждающие данные; готового списка команд нет.

Итоги главы

Bash идеален для короткого связывания утилит Unix и сбора диагностических данных. Надёжность возникает из понимания кодов возврата, потоков, кавычек и форматов данных. Теория

Оболочка разбирает текст как программу. Раскрытия, разбиение на слова, шаблоны имён и кавычки определяют, какие аргументы получит команда. Переменная со строкой file name.txt без кавычек может стать двумя аргументами. Двойные кавычки сохраняют значение как один аргумент с допустимыми раскрытиями; одинарные предотвращают интерпретацию содержимого. Для набора аргументов используют массивы Bash, а не склеенную строку с последующим eval.

Код возврата 0 обычно означает успех по контракту команды, ненулевой — иной результат. grep возвращает 1 при отсутствии совпадений, что может быть нормальной ветвью, а 2 — ошибку. GNU coreutils timeout возвращает 124 при истечении лимита без --preserve-status; неверную команду после сдвига аргументов нельзя принять за тайм-аут. Код 137 соответствует завершению по SIGKILL. См. GNU Coreutils 9.11: timeout. set -euo pipefail ловит часть дефектов, но не является доказательством корректности: -e имеет исключения в условных конструкциях и конвейерах, -u требует учёта необязательных переменных, pipefail меняет статус конвейера. Ожидаемые отказы обрабатывают явно.

Конвейеры Unix хорошо подходят для потоковой фильтрации текста, но вывод утилит для человека нестабилен между локалями и версиями. Предпочитают JSON и jq, явные поля и формат времени. Имена файлов могут содержать пробелы, переводы строк и начальный дефис: нужны интерфейсы с разделителем NUL там, где они поддержаны, и -- для окончания опций. for f in $(ls) — ненадёжная конструкция.

Сборщик, работающий только на чтение, не должен менять конфигурацию исследуемого объекта, но он пишет свой отчёт и создаёт нагрузку чтения. Ему нужны ограниченный набор команд, ограничения по времени, отдельные потоки вывода и ошибок, коды завершения и время каждого шага. Журналы могут содержать секреты и персональные данные; сбор ограничивают диапазоном и назначением, права на отчёт сужают. Ошибка одной команды не должна превращать пустой файл в «здоровую систему».

Временные каталоги создают через mktemp, связывают с текущим запуском и очищают только проверенную область. Для записи конфигурации используют проверенный временный файл и атомарное переименование в пределах файловой системы, учитывая права, сброс на диск и наблюдателей. Блокировка помогает предотвратить одновременные запуски, но не защищает от всех внешних изменений. Проверки должны включать имена с пробелами, отказ команды, отсутствие прав и прерывание.

Если обёртка команды делает shift перед timeout "$@", имя исполняемой программы исчезает из аргументов. До изменения выводят аргументы с сохранением границ, затем передают исходный "$@" без удаления первого элемента. Проверяют успешный и ненулевой код, имя с пробелами и реальное истечение лимита на безобидной пробе.

Предел времени выполнения не ограничивает размер вывода: команда способна напечатать гигабайты за секунды и заполнить память сборщика. Вывод читают порциями с ограничением байтов, сохраняя признак превышения вместо пустого «успешного» результата.

Разобранные примеры

E21.1. Аргументы. args=(--output "$report_path" --format json) и tool "${args[@]}" сохраняют границы. tool $args не эквивалентен этому.

E21.2. grep. if grep -q 'ERROR' "$log"; then ...; else rc=$?; ...; fi позволяет различить отсутствие строки и ошибку чтения. Автоматически объявлять противоположную ветвь состоянием «ошибок нет» неверно.

E21.3. Сборщик. ip -j route show не меняет маршруты и даёт структурированные данные. Ненулевой код возврата сохраняют рядом с потоком ошибок; отсутствие команды обозначают как «недоступно», а не пустой таблицей.
