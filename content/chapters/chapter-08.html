Академическое продолжение этой главы: U08.

Цели главы

После главы вы должны уметь:

  • объяснить тегированный и нетегированный трафик Ethernet;
  • различать интерфейс VLAN, мост Linux и маршрутизируемый интерфейс;
  • понимать поведение моста как программного коммутатора;
  • объяснить назначение объединения интерфейсов и основные режимы на концептуальном уровне;
  • различать пересылку пакетов и NAT;
  • читать базовый набор правил nftables;
  • использовать сетевое пространство имён для лабораторий и диагностики.

Перед началом: превращаем виртуальную схему в объект исследования

С момента установки Proxmox мы пользовались vmbr10/20/30, но мост был для нас готовой коробкой. Теперь мы разберём, чем он отличается от маршрутизатора, как VLAN добавляет метку к кадру Ethernet, зачем нужны несколько физических и виртуальных линий и на каком этапе пакет встречает межсетевой экран.

Где это в стенде: хост Proxmox плюс VM router. Это первая глава, где полезно одновременно смотреть на гостя и хост. Перед изменением сетевой конфигурации убедитесь, что доступ к управлению vmbr0 не является объектом эксперимента.

Правило безопасности: никогда не учись VLAN и DHCP, подключая экспериментальный мост к рабочей сети без изоляции.

Прежде чем читать. Между двумя VLAN нет связности. Перечислите места, где может быть причина, помимо настройки самих VLAN.

Ответьте до чтения — одной фразой, вслух или письменно. Неверный ответ здесь полезен не меньше верного: значение имеет сама попытка ответить прежде, чем прочитано объяснение. Разбор — в разделе «Типичная ошибка мышления»: перейти.

8.1. VLAN — разделение широковещательных доменов второго уровня

Тегирование 802.1Q позволяет передавать несколько логических доменов второго уровня по одной физической линии. Метка VLAN содержит идентификатор VLAN и служебные поля.

Упрощённо магистральный порт (trunk):

eno1 physical link
  ├── VLAN 10 → servers
  ├── VLAN 20 → storage
  └── VLAN 30 → management

Linux может создать subinterface:

ip link add link eno1 name eno1.20 type vlan id 20
ip link set eno1 up
ip link set eno1.20 up
ip addr add 10.20.0.10/24 dev eno1.20

Но эта конфигурация сработает, только если сторона коммутатора ожидает соответствующий тегированный трафик.

8.2. Тегированный и нетегированный — свойство передачи кадра на конкретной линии

Фраза «порт находится в VLAN 20» недостаточна без уточнения поведения коммутатора. Порт доступа обычно принимает и отправляет нетегированные кадры и связывает их с одним VLAN внутри коммутатора. Магистральный порт способен передавать тегированные кадры нескольких VLAN.

Одна из распространённых причин отказа: хост отправляет трафик с меткой VLAN, а порт коммутатора ожидает нетегированный, или наоборот.

Перехват может показать метку:

tcpdump -eni eno1 vlan

8.3. Мост Linux

Мост работает на втором уровне и концептуально похож на программный коммутатор. Он связывает порты в один широковещательный домен и обучается MAC-адресам.

VM за мостом может получить адрес из той же сети второго уровня, что и физический NIC, без маршрутизации на хосте.

Проверки:

bridge link
bridge fdb show
ip link show master br0

8.4. Мост и маршрутизатор — принципиально разные роли

Мост пересылает кадры Ethernet между портами внутри домена второго уровня. Маршрутизатор принимает решение третьего уровня между сетями IP.

Если две сети должны быть изолированы и общаться по правилам, часто нужны маршрутизация и межсетевой экран. Если VM должна логически сидеть в том же сегменте Ethernet, нужен мост.

Путаница этих моделей приводит к странным схемам, где адреса навешиваются одновременно на физический NIC и на мост без ясной причины.

8.5. Объединение интерфейсов

Объединение соединяет несколько физических линий в один логический интерфейс ради резервирования и распределения трафика.

Режимы отличаются. Два часто обсуждаемых подхода:

  • active-backup — одна линия активна, другая в резерве;
  • 802.3ad/LACP — агрегирование при поддержке со стороны коммутатора.

Нельзя просто включить LACP только на сервере и ожидать корректной работы: это согласованная настройка с коммутатором.

Проверка классического объединения:

cat /proc/net/bonding/bond0

Важно понимать и хеширование: один поток TCP обычно не превращается автоматически в сумму полос всех линий.

8.6. Пересылка и NAT

Маршрутизация не равна NAT.

Если маршрутизатор на Linux имеет маршруты между 10.0.1.0/24 и 10.0.2.0/24, он может пересылать трафик без изменения адресов. NAT меняет заголовки и состояние пакета и решает другую задачу.

Для пересылки IPv4:

sysctl net.ipv4.ip_forward

NAT часто нужен для приватной учебной сети при выходе через один внешний адрес, но внутри центра обработки данных маршрутизируемые сети могут обходиться без него.

8.7. Межсетевой экран как набор точек подключения и правил

Современный Linux обычно использует nftables, хотя совместимость с iptables всё ещё встречается.

Посмотреть набор правил:

nft list ruleset

При диагностике важно понимать направление пакета:

packet to local host       → input path
packet created locally     → output path
packet routed through host → forward path

Если правило межсетевого экрана находится в forward, оно не обязательно влияет на сервис, слушающий на самом маршрутизаторе.

8.8. Межсетевой экран с состоянием и conntrack

Межсетевой экран может учитывать состояние соединения. Упрощённая политика:

allow established/related
allow explicitly permitted new traffic
drop остальное

Conntrack хранит состояние потоков. Это важно при NAT и асимметричной маршрутизации: если запрос и ответ проходят через разные устройства с состоянием, одно из них может не видеть ожидаемого состояния соединения.

8.9. Сетевые пространства имён

Сетевое пространство имён создаёт отдельный набор сетевых интерфейсов, маршрутов, таблиц соседей и сокетов. Контейнеры используют похожую изоляцию.

Лабораторно можно построить сеть без VM:

ip netns add ns1
ip netns add ns2
ip link add veth1 type veth peer name veth2
ip link set veth1 netns ns1
ip link set veth2 netns ns2

Затем назначить адреса внутри пространств имён.

Пару veth можно представить как виртуальный кабель: пакет, вошедший в один конец, появляется на другом.

8.10. Тег на стенде: как он выглядит в кадре

Подинтерфейс VLAN заводится одной командой и живёт поверх физического:

sudo ip link add link eth0 name eth0.100 type vlan id 100
sudo ip addr add 192.168.100.12/24 dev eth0.100
sudo ip link set eth0.100 up
ip -d link show eth0.100
3: eth0.100@eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    link/ether bc:24:11:14:88:65 brd ff:ff:ff:ff:ff:ff
    vlan protocol 802.1Q id 100 <REORDER_HDR>

Три вещи здесь стоит заметить. Запись eth0.100@eth0 называет родителя: подинтерфейс не имеет своего провода и своей очереди, он лишь помечает то, что уходит через eth0. Адрес канального уровня тот же самый, что у родителя, — тег не создаёт нового узла сети, он различает кадры одного узла. И ключ -d обязателен: без него ip link show не покажет ни протокол, ни номер, и подинтерфейс будет выглядеть обычным интерфейсом со странным именем.

Теперь перехват на физическом интерфейсе, пока через подинтерфейс идёт обмен:

sudo tcpdump -e -n -i eth0 vlan 100
bc:24:11:14:88:65 > bc:24:11:bd:16:33, ethertype 802.1Q (0x8100), length 102:
  vlan 100, p 0, ethertype IPv4 (0x0800),
  192.168.100.12 > 192.168.100.30: ICMP echo reply, id 12994, seq 1, length 64

Кадр читается ровно так, как устроен: адреса, затем ethertype 0x8100 — признак того, что дальше идёт тег, затем сам тег (vlan 100) и приоритет (p 0, то самое поле 802.1p), и только потом настоящий тип протокола 0x0800. Отсюда и четыре лишних байта: тег вставлен внутрь кадра, между адресами и типом, а не приписан к нему снаружи.

Практическое следствие этих четырёх байт видно в MTU:

cat /sys/class/net/eth0/mtu /sys/class/net/eth0.100/mtu
1500
1500

У обоих 1500 — то есть полный кадр с тегом занимает на проводе на четыре байта больше обычного. Коммутатор, который этого не ожидает, отбрасывает такие кадры как слишком длинные, и отказ выглядит знакомо по главе 7: мелкие пакеты ходят, крупные — нет. У производителей эта настройка называется по-разному (jumbo, baby giant), но требуется одинаково.

8.11. Тег не изолирует — изолирует коммутатор

Опыт на трёх машинах одного моста vmbr20: у двух заведён подинтерфейс VLAN 100, у третьей нет ничего. Мост стенда создан без фильтрации тегов — как обычный неуправляемый коммутатор.

Сначала связь внутри VLAN:

5 packets transmitted, 5 received, 0% packet loss, time 4097ms
rtt min/avg/max/mdev = 0.370/0.450/0.506/0.046 ms

Работает — и это ожидаемо. А теперь перехват на третьей машине, у которой подинтерфейса VLAN 100 нет вовсе:

sudo tcpdump -e -n -c 3 -i eth0 vlan 100
bc:24:11:bd:16:33 > ff:ff:ff:ff:ff:ff, ethertype 802.1Q (0x8100), length 46:
  vlan 100, p 0, ethertype ARP (0x0806),
  Request who-has 192.168.100.12 tell 192.168.100.30

Чужой широковещательный запрос пришёл на порт, который в этот VLAN не входит. Ничего не сломалось: мост без фильтрации тегов не знает, что такое VLAN. Для него тег — четыре байта в середине кадра, и рассылает он кадр по тем же правилам, что и любой другой: широковещательный — во все порты, одноадресный — в порт, где выучен адрес получателя. Поэтому одноадресный обмен третья машина не увидела, а весь ARP увидела.

Отсюда главное утверждение этого раздела, и оно противоречит бытовому пониманию слова VLAN: метка сама по себе не разделяет ничего. Разделение появляется там, где есть устройство, которое помнит, какие теги разрешены на каком порту, и снимает или отбрасывает остальные. В Linux это включается явно:

sudo ip link set vmbr20 type bridge vlan_filtering 1
bridge vlan show

До этой команды хост со своим тегом может отправлять и слушать что угодно; после неё правила появляются и становятся частью настройки, которую надо задать и проверить. В Proxmox ту же роль играет отметка «VLAN aware» у моста, а номер VLAN, указанный в настройках сетевого адаптера машины, — это уже правило порта.

И вывод для проектирования, к которому раздел 8.1 подводил словами: VLAN — механизм разделения широковещательных доменов, а не средство защиты. Он не мешает соседу по порту слушать эфир и не заменяет правил межсетевого экрана из раздела 8.7; он лишь делает так, что по умолчанию машины из разных доменов друг друга не находят.

8.12. Разобранный пример: VM видит хост, но не шлюз

Ситуация

VM подключена к br0, хост имеет доступ к шлюзу, VM — нет.

Стратегия

Если VM видит хост на втором и третьем уровне, виртуальный NIC и часть моста работают. Нужно сравнить кадры от VM к шлюзу и от хоста к шлюзу, обработку VLAN и пересылку по MAC-адресам.

Действия

Два tcpdump одновременно, в двух точках одного пути — это и есть измерение, разделяющее гипотезы:

bridge link
bridge vlan show
bridge fdb show br0
tcpdump -eni br0 arp     # терминал 1: кадр вошёл в bridge
tcpdump -eni eno1 arp    # терминал 2: кадр вышел наружу

Получено:

# tcpdump -eni br0 arp
52:54:00:aa:bb:cc > ff:ff:ff:ff:ff:ff, ARP, Request who-has 10.20.30.1 tell 10.20.30.55

# tcpdump -eni eno1 arp
(пусто)

# bridge vlan show
port    vlan-id
vnet0    30 PVID Egress Untagged
eno1     10 PVID Egress Untagged

Интерпретация

Кадр от VM дошёл до моста и не вышел на физический интерфейс — граница локализована с точностью до одного устройства: она внутри br0. Это исключает и гостевой стек, и коммутатор, и кабель, хотя симптом «нет сети» указывал на них в первую очередь.

Причину показывает bridge vlan show: порт VM находится в VLAN 30, аплинк — в VLAN 10. При включённой фильтрации VLAN мост — это не «виртуальный провод», а коммутатор с собственной таблицей VLAN, и кадр между портами разных VLAN он не передаёт. Тот же механизм объясняет, почему VM видит хост: адрес самого моста принадлежит внутреннему порту и доступен из любого VLAN, к которому этот порт приписан.

Вывод

Исправление — привести VLAN порта VM в соответствие с проектом сети, а не отключать фильтрацию:

sudo bridge vlan del dev vnet0 vid 30 pvid untagged
sudo bridge vlan add dev vnet0 vid 10 pvid untagged
sudo tcpdump -eni eno1 arp    # проверка: кадр теперь выходит

И главное наблюдение о методе: ping host из VM ничего не доказывает — он проверяет только первый отрезок пути, до внутреннего порта моста, и остаётся успешным ровно в той конфигурации, которая сломана. Проверять надо ту точку, где путь может обрываться, а не ту, до которой он заведомо доходит.

8.13. Лаборатория

Постройте в VM или namespaces:

client -- bridge -- router -- server

Затем:

  1. включите пересылку пакетов;
  2. разрешите только TCP/8080 через nftables;
  3. добавьте NAT для выхода во внешнюю сеть;
  4. создайте VLAN 20 между двумя узлами;
  5. намеренно сделайте несовпадение VLAN;
  6. исследуйте трафик одновременно на физическом интерфейсе и интерфейсе VLAN;
  7. если среда поддерживает, создайте объединение в режиме active-backup.

Концептуальное углубление: разделение на втором уровне, маршрутизация и политика — три разные задачи

VLAN, маршрутизатор и межсетевой экран часто настраиваются рядом и из-за этого смешиваются концептуально.

VLAN и мост отвечают за организацию доменов второго уровня: какие кадры Ethernet могут оказаться в одном широковещательном домене и через какие порты.

Маршрутизация соединяет сети IP и выбирает следующий узел.

Межсетевой экран применяет политику к трафику в определённых точках пути.

Можно иметь два VLAN, которые прекрасно маршрутизируются между собой. Можно иметь один VLAN и межсетевой экран, блокирующий часть трафика. Можно иметь мост вообще без адреса. Разделение этих ролей существенно упрощает диагностику.

Тегированный и нетегированный

Из раздела 8.2 следует практическое: вопрос «VLAN 100 тегированный или нет?» неполон без уточнения на каком участке линии и в каком направлении. Один и тот же кадр идёт с меткой между коммутаторами и без метки на последнем отрезке к конечному устройству — и оба ответа верны, просто про разные точки.

Это меняет и чтение перехвата. Если сетевая карта снимает метку аппаратно, tcpdump на физическом интерфейсе покажет кадр без неё, хотя порт коммутатора магистральный. Отсутствие метки в перехвате доказывает не отсутствие VLAN, а только то, что до точки перехвата метка не дошла; сравнивать нужно перехват на физическом интерфейсе и на интерфейсе VLAN.

NAT — изменение адресов, а не разновидность маршрутизации

Маршрутизатор может передавать пакет без NAT. NAT нужен, когда мы намеренно переписываем адреса и порты источника или назначения. В нашей лаборатории маскарадинг используется на WAN, чтобы приватные учебные подсети выходили через адрес VM router в физическую сеть.

Практическое углубление: как виртуальный мост связан с физическим коммутатором

Мост Linux и обычный коммутатор Ethernet решают одну базовую задачу: получить кадр на одном порту и решить, на какие другие порты его отправить. Отличаются реализация и набор дополнительных функций, но полезная ментальная модель одна.

В нашем стенде портами vmbr20 являются TAP-интерфейсы VM. Если позже vmbr20 будет связан с физическим NIC, ещё одним портом станет физический путь в сеть. Мост с поддержкой VLAN добавляет правило, какие VLAN могут существовать на каких портах и как трактовать тегированные и нетегированные кадры.

Важно не превращать слово «виртуальный» в синоним «ненастоящий». Кадр Ethernet, обучение MAC-адресам, широковещание и метка VLAN в программном тракте следуют тем же протокольным правилам. Зато отказы физического уровня — потеря сигнала, плохой кабель, автосогласование, ошибки PHY — в чистой VM отсутствуют.

Наблюдение на хосте

Во время ping между двумя VM на одном мосту выполните:

bridge link
bridge fdb show br vmbr20
ip -s link

Сначала найдите, какие интерфейсы на стороне хоста соответствуют сетевым картам конкретных VM. Затем проследите, как в таблице пересылки появляются MAC-адреса. Только после этого переходите к фильтрации VLAN: будет понятно, что фильтруется и где.

Типичная ошибка мышления

Заблуждение. Между двумя VLAN нет связности — значит VLAN настроены неправильно.

Почему это неверно. VLAN по определению разделяет широковещательные домены. Отсутствие прямой связности между разными VLAN — это корректная работа механизма, а не дефект. Связь между ними обеспечивает маршрутизатор, и её отсутствие может быть вызвано отсутствующим маршрутом, выключенной пересылкой, политикой межсетевого экрана или NAT — четырьмя разными причинами, ни одна из которых не «неправильный VLAN».

Что проверить вместо этого.

bridge vlan show                       # какие VID разрешены на каждом порту
ip -d link show vlan20                 # тип интерфейса и VID
sysctl net.ipv4.ip_forward             # включён ли форвардинг на маршрутизаторе
nft list ruleset                       # политика и counters
conntrack -L | head                    # видит ли stateful firewall поток
cat /proc/net/bonding/bond0            # режим и состояние линков

Для объединения интерфейсов помните: LACP работает только парно — режим 802.3ad на сервере без соответствующей настройки агрегата на коммутаторе даёт худшую связность, чем одна линия.

Итоги главы

VLAN, мост, объединение интерфейсов, межсетевой экран и пространства имён — разные механизмы, которые часто встречаются в одной схеме. VLAN делит домены второго уровня, мост соединяет порты второго уровня, маршрутизатор связывает сети IP, объединение соединяет линии, межсетевой экран применяет политику, а пространство имён создаёт отдельный сетевой стек. Чёткое разделение ролей устраняет значительную часть путаницы при виртуализации и серверной сетевой диагностике.

U08. Университетское углубление: VLAN, мост, LACP, межсетевой экран и NAT

До: 05–06. После: строить путь пакета через мост и маршрутизатор, различать фильтрацию и трансляцию, оценивать резервирование каналов. L08A/B, контейнерные сети.

Теория

VLAN разделяет канальные домены на общей физической инфраструктуре. Порт доступа обычно принимает и выдаёт нетегированный трафик определённого VLAN; магистральный порт переносит несколько VLAN с согласованной политикой меток. PVID определяет классификацию входного нетегированного кадра. Метка на VM, мосту и аплинке должна соответствовать общей модели: двойное тегирование по ошибке и ожидание метки на порту доступа создают разные неисправности.

Мост Linux пересылает кадры второго уровня между портами по таблице FDB. Адрес хоста может быть назначен самому мосту, но не требуется для пересылки каждого кадра. Маршрутизация между подсетями IP — другая функция. Петля на втором уровне способна размножать широковещательный трафик; STP и RSTP выбирают топологию без активных циклов, блокируя часть путей. Поэтому «два кабеля для надёжности» без модели управления петлёй могут ухудшить сеть.

Объединение соединяет интерфейсы на хосте. Режим active-backup даёт переключение, но не суммирует скорость обычного потока. LACP согласует агрегат с партнёром; хеширование распределяет потоки, чтобы обычно сохранять порядок пакетов одного потока. Один поток TCP чаще ограничен одним физическим участником. Два порта в одном коммутаторе не устраняют отказ этого коммутатора; многокорпусный агрегат требует поддержки и согласованной архитектуры.

Межсетевой экран с состоянием классифицирует пакеты с учётом conntrack. В nftables семейства и точки подключения определяют, где проходит пакет: локальный вход и выход, транзитная пересылка, мост и другие пути. Политика запрета по умолчанию требует явного разрешения необходимых потоков, включая обратный и управляющий трафик. Правило established,related не открывает произвольную новую сессию, но его смысл зависит от правильной классификации.

NAT изменяет адреса/порты и сохраняет соответствия для обратного направления. Он не является самостоятельной моделью авторизации. DNAT может поменять маршрут после изменения назначения; SNAT нужен, когда обратный путь иначе не соответствует дизайну. Ошибки маршрутизации нельзя надёжно исправлять добавлением NAT без понимания топологии: это может скрыть исходную проблему.

Безопасное изменение сети имеет две плоскости: проверяемый путь данных и сохранённый путь управления. Консоль гипервизора, резервный канал и ограниченная область эксперимента позволяют проверить межсетевой экран без потери доступа. В этой книге сетевые поломки вносятся в пространстве имён или отдельной VM, а не на интерфейсе, по которому управляют физическим сервером.

Для исправления ошибки VLAN сверяют разрешённые метки на VM, мосту и аплинке, затем добавляют недостающую метку только в требуемый путь. Проверка должна подтвердить ARP и полезную передачу в новом VLAN, а также сохранение изоляции от другого VLAN: широкое разрешение всех меток может скрыть исходную ошибку и нарушить границу сети.

Для Linux nftables локально адресованный пакет обычно проходит hook input, а транзитный через маршрутизатор — forward; успешная проверка input ничего не доказывает о правилах forward. Конкретную цепочку сверяют с семейством таблицы, типом hook и реальным путём пакета, сохраняя путь управления.

Разобранные примеры

E08.1. Агрегация. 2×10GbE в режиме LACP допускают суммарную полезную скорость множества потоков, близкую к 20 Gbit/s с учётом накладных расходов, но один хешированный поток обычно остаётся в пределах 10 Gbit/s. Неравномерный хеш снижает суммарный результат.

E08.2. Несовпадение VLAN. VM отправляет метку 30, аплинк разрешает только 10 и 20. Поднятая линия не доказывает связность VLAN 30. Перехват у VM и на аплинке вместе с таблицей VLAN локализует границу.

E08.3. NAT и ответ. Клиент приходит через DNAT на серверную часть, которая отвечает через другой шлюз. SYN виден на сервере, клиент получает тайм-аут. Проверяют маршрут ответа и conntrack, прежде чем объявлять отказ приложения.
