Инфраструктура начинает обслуживать жизненный цикл приложения

До этой точки приложение было тестовым сервисом или источником симптома. Теперь оно становится рабочей нагрузкой: образ, конфигурация, сеть, хранилище, процесс развёртывания и модель здоровья.

22. Docker, namespaces, cgroups и Compose

Академическое продолжение этой главы: U24.

Цели главы

После главы вы должны уметь:

  • объяснить, чем контейнер отличается от виртуальной машины;
  • понимать namespaces и cgroups на концептуальном уровне;
  • объяснить образ, слой, записываемый слой контейнера и том;
  • читать Dockerfile и понимать кеш сборки;
  • диагностировать проблемы сети, файловой системы и процессов контейнера;
  • использовать Docker Compose для учебного сервиса из нескольких частей;
  • понимать ограничения контейнеризации с точки зрения безопасности и приложений с состоянием.

Перед началом: приложение изолируется без отдельного ядра гостя

Виртуальные машины уже научили нас разделять хост и гостя. Контейнер требует более тонкой модели: процессы могут иметь отдельные пространства имён и cgroups, но использовать то же ядро хоста. Поэтому Docker нельзя изучать только через команды docker run; важно видеть процесс, сетевое пространство имён, пространство имён монтирования и управление ресурсами.

Где это в стенде: отдельная VM app в SERVER-NET. Docker запускается внутри VM, а не прямо на хосте Proxmox, чтобы экспериментальная платформа приложений не смешивалась с гипервизором.

Прежде чем читать. Контейнер запущен, порт объявлен в образе. Что ещё нужно, чтобы сервис был доступен снаружи?

Ответьте до чтения — одной фразой, вслух или письменно. Неверный ответ здесь полезен не меньше верного: значение имеет сама попытка ответить прежде, чем прочитано объяснение. Разбор — в разделе «Типичная ошибка мышления»: перейти.

22.1. Контейнер не является маленькой виртуальной машиной

Виртуальная машина запускает отдельное ядро гостя. Контейнер обычно использует ядро хоста и изолирует процессы и ресурсы механизмами ядра.

VM:
app → guest userspace → guest kernel → hypervisor → host/hardware

Container:
app → container view of userspace
        ↓
      host kernel
        ↓
      hardware

Это различие объясняет и скорость запуска, и ограничения. Контейнер Linux не приносит собственное независимое ядро в обычной модели Docker.

22.2. Пространства имён

Пространство имён даёт процессу отдельное представление части системных ресурсов. Важные виды:

  • PID — идентификаторы и дерево процессов;
  • сетевое — интерфейсы, маршруты, сокеты;
  • монтирования — дерево точек монтирования;
  • UTS — имя хоста и домена;
  • IPC;
  • пространство имён пользователей и другие.

Когда внутри контейнера выполняется:

ip a

он видит интерфейсы своего сетевого пространства имён, а не обязательно интерфейсы хоста.

22.3. Cgroups

Control groups организуют учёт и ограничение ресурсов: процессорного времени, памяти, ввода-вывода и т. д. Среда выполнения контейнеров помещает процессы в cgroups.

Поэтому контейнер может получить лимит памяти, хотя у хоста её намного больше. Нехватка памяти внутри cgroup и общая нехватка на хосте — разные события и требуют разных доказательств.

22.4. Образ и контейнер

Образ — практически неизменяемый набор слоёв и метаданных, используемый как шаблон. Контейнер добавляет состояние выполнения и записываемый слой.

base layer
  ↓
dependencies layer
  ↓
application layer
  ↓
read-only image
  ↓
container writable layer

Если важные данные существуют только в записываемом слое и контейнер удалён, данные могут быть потеряны. Данные, которые должны сохраняться, обычно выносят в тома, привязанные каталоги или внешнее хранилище.

22.5. Dockerfile

Пример:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 10001
CMD ["python", "app.py"]

Порядок инструкций влияет на кеш сборки. Если зависимости меняются редко, их удобно устанавливать до копирования часто меняющегося исходного кода.

CMD задаёт команду по умолчанию, а ENTRYPOINT — другую часть правил запуска; важно читать контракт конкретного образа.

22.6. Контекст сборки

docker build отправляет контекст сборки сборщику. Нельзя бездумно включать .git, резервные копии, учётные данные и большие артефакты. Используйте .dockerignore.

Это вопрос и скорости, и безопасности.

22.7. Сеть контейнеров

Сеть через мост по умолчанию концептуально:

container eth0
   |
 veth pair
   |
docker bridge
   |
host routing/NAT
   |
external network

Опубликованный порт:

docker run -p 8080:80 image

означает отображение порта 8080 на хосте в порт 80 контейнера согласно правилам среды выполнения. Это не означает, что приложение внутри контейнера автоматически слушает нужный адрес. Если оно привязано только к 127.0.0.1 внутри контейнера, опубликованный порт может оставаться недоступным.

22.8. DNS внутри Compose

Compose создаёт обнаружение сервисов по их именам в общей сети.

services:
  app:
    build: .
    depends_on:
      - db
  db:
    image: ${POSTGRES_IMAGE:?Set_POSTGRES_IMAGE_to_a_tested_digest}

Перед запуском задайте POSTGRES_IMAGE как проверенную полную ссылку вида postgres@sha256:<фактический digest> и сохраните её в описании; заполнитель не является исполнимым значением. Это схема обнаружения сервисов, а не полный готовый стек PostgreSQL: учётные данные, том и проверка готовности добавляются по контракту выбранного образа. Приложение обращается к имени db, а не к localhost, потому что localhost внутри контейнера приложения означает сам этот контейнер.

Это одна из наиболее частых ошибок начинающих.

22.9. depends_on не гарантирует готовность приложения

Контейнер может считаться запущенным, пока база данных ещё выполняет инициализацию. Поэтому стек, приближенный к эксплуатации, использует проверки готовности и повторные попытки, а не полагается только на порядок запуска.

Опять проявляется знакомый урок systemd: «процесс запущен» и «сервис готов» — разные состояния.

22.10. Тома и права

Привязанный каталог связывает путь на хосте с пространством имён контейнера. Идентификаторы пользователя и группы остаются важны. Если процесс контейнера работает от UID 10001, каталог на хосте должен допускать нужные операции для этого идентификатора или соответствующей модели отображения.

Проблема:

Permission denied /data

в контейнере часто диагностируется теми же понятиями, что и обычная проблема прав в Linux, плюс контекст пространств имён и монтирования.

22.11. Журналы

docker logs <container>
docker inspect <container>
docker stats

docker logs показывает стандартный вывод и поток ошибок согласно драйверу журналирования, но приложение может писать в собственный файл внутри файловой системы. Лучше проектировать контейнерный сервис так, чтобы у эксплуатационных журналов был понятный путь сбора.

22.12. Модель безопасности

Изоляция контейнера не равна изоляции виртуальной машины. Ядро хоста общее. Запуск привилегированных контейнеров, монтирование сокета Docker, выдача широких возможностей или путей файловой системы хоста существенно расширяют привилегии.

--privileged не должен быть стандартным способом «починить отказ в доступе».

22.13. Пространства имён можно потрогать руками

Пространство имён — не абстракция среды выполнения, а свойство процесса, и у него есть номер. Ядро показывает их через /proc:

ls -l /proc/self/ns/
mnt  -> mnt:[4026531841]
net  -> net:[4026531840]
pid  -> pid:[4026531836]
user -> user:[4026531837]
uts  -> uts:[4026531838]

Два процесса с одинаковыми номерами живут в одном пространстве имён, с разными — в разных. Это и есть весь механизм: контейнер — это процесс, у которого часть номеров своя. Проверяется без Docker:

sudo unshare --pid --fork --mount-proc sh -c 'echo "внутри: $"; ps -e | head -4'
внутри: 1
    PID TTY          TIME CMD
      1 ?        00:00:00 sh
      2 ?        00:00:00 ps

Процесс видит себя первым и не видит ничего из системы — при том что на хосте он обычный процесс с обычным номером. Отсюда следствие, которое объясняет половину вопросов про контейнеры: «PID 1» внутри и «PID 1» снаружи — разные процессы, а сигнал, посланный внутри, до хостовых процессов не доходит.

То же с сетью:

sudo unshare --net ip -br link
lo               DOWN           00:00:00:00:00:00 <LOOPBACK>

В новом сетевом пространстве имён нет ничего, кроме выключенного loopback: ни интерфейсов хоста, ни маршрутов, ни правил межсетевого экрана. Всё, что появляется у контейнера, кладёт туда среда выполнения.

Три команды, которые стоит помнить при разборе: lsns показывает все пространства имён системы и их процессы, nsenter -t PID -n ip a выполняет команду в чужом сетевом пространстве имён, а readlink /proc/PID/ns/net отвечает на вопрос «этот процесс и тот — в одной сети или нет».

22.14. Cgroup v2: где лежит лимит и что происходит при его достижении

Ограничения тоже видны файлами. Текущая группа процесса:

cat /proc/self/cgroup
0::/system.slice/qemu-guest-agent.service

Путь читается от корня иерархии /sys/fs/cgroup. Создадим свою группу с лимитом в 64 МиБ и запустим в ней процесс, которому нужно 200:

sudo mkdir /sys/fs/cgroup/lab
echo 67108864 | sudo tee /sys/fs/cgroup/lab/memory.max
sudo sh -c 'echo $ > /sys/fs/cgroup/lab/cgroup.procs; exec python3 -c "…выделить 200 МиБ…"'

Процесс убит, и об этом сказано в трёх местах. В счётчиках группы:

cat /sys/fs/cgroup/lab/memory.events
low 0
high 0
max 35
oom 1
oom_kill 1

В журнале ядра:

oom-kill:constraint=CONSTRAINT_MEMCG,oom_memcg=/lab,task_memcg=/lab,task=python3
Memory cgroup out of memory: Killed process 9365 (python3) anon-rss:65052kB

Ключевое слово здесь — CONSTRAINT_MEMCG: память кончилась в группе, а не на хосте. Это разные события с разными доказательствами, и путать их дорого: на хосте в этот момент было свободно больше гигабайта. Счётчик max говорит, сколько раз группа упиралась в потолок и тормозилась, не будучи убитой, — если он растёт, приложение живо, но работает медленнее, чем могло бы.

Так же устроены остальные ограничения: cpu.max задаёт квоту в микросекундах на период (200000 100000 — два процессора), pids.max ограничивает число процессов, io.max — скорость устройства. Все они читаются и пишутся файлами, поэтому «лимит контейнера» всегда можно проверить, не спрашивая среду выполнения.

22.15. Почему free и nproc внутри контейнера врут

Процесс в группе с лимитом 64 МиБ спрашивает систему о памяти и процессорах:

free -m
               total        used        free      shared  buff/cache   available
Mem:            1960         331         782           0        1004        1629

nproc
2

Он видит 1960 МиБ и два процессора — то есть ресурсы хоста, а не свои. Причина простая: free читает /proc/meminfo, а /proc в контейнере — это тот же /proc ядра, и пространства имён для него нет. Ограничения лежат в cgroup, и туда никто не смотрит.

Последствия у этого не косметические. Java, Go и Node по умолчанию выбирают размеры пулов и кучи по числу процессоров и объёму памяти; приложение, увидевшее «два процессора и два гигабайта» в группе на 64 МиБ, запустит слишком много потоков и будет убито. Современные среды выполнения умеют читать cgroup — у JVM это включено по умолчанию с версии 10, — но проверять это приходится каждый раз.

Правильные источники правды внутри контейнера:

cat /sys/fs/cgroup/memory.max      # лимит памяти группы
cat /sys/fs/cgroup/memory.current  # сколько занято сейчас
cat /sys/fs/cgroup/cpu.max         # квота и период
cat /sys/fs/cgroup/memory.events   # упирались ли в потолок

Тот же вывод касается мониторинга: агент, снимающий «свободную память» внутри контейнера, измеряет хост. Полезные метрики контейнера — это memory.current против memory.max и рост max в memory.events.

22.16. Слои: overlayfs своими руками

Образ, записываемый слой и том проще понять, собрав их вручную. Overlayfs берёт три каталога — нижний (только чтение), верхний (запись) и рабочий — и показывает их как один:

mkdir -p /tmp/ovl/{lower,upper,work,merged}
echo "из образа" > /tmp/ovl/lower/file.txt
sudo mount -t overlay overlay \
  -o lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work \
  /tmp/ovl/merged
cat /tmp/ovl/merged/file.txt
из образа

Теперь запишем в объединённый каталог и посмотрим, что где оказалось:

echo "изменено в контейнере" > /tmp/ovl/merged/file.txt

lower: из образа
upper: изменено в контейнере

Это и есть копирование при записи: нижний слой не тронут, изменённая копия легла в верхний. Точно так же работает образ: слои образа — нижние и общие для всех контейнеров, записываемый слой контейнера — верхний и свой.

Удаление ещё интереснее. Нижний слой изменить нельзя, поэтому удаление файла записывается пометкой:

rm /tmp/ovl/merged/file.txt
ls -l /tmp/ovl/upper/
c--------- 2 root root 0, 0 file.txt

В верхнем слое появился whiteout — символьное устройство с нулевыми номерами. Файл «удалён» в объединённом виде, но данные в нижнем слое остались. Отсюда правило, которое стоит знать до первой утечки: секрет, попавший в слой образа, не удаляется следующей командой rm в Dockerfile — он остаётся в нижнем слое и достаётся из образа кем угодно. Убирают его пересборкой без этого слоя или многоступенчатой сборкой.

И третий вывод, самый практический: записываемый слой живёт ровно столько, сколько контейнер. Всё, что должно пережить пересоздание, кладут в том или монтируют с хоста — это не совет по надёжности, а следствие устройства overlayfs.

22.17. Сеть контейнера: veth, мост и публикация порта

Сетевое пространство имён пустое; связь с хостом делает виртуальная пара интерфейсов — один конец внутри, другой снаружи. Соберём её без Docker:

sudo ip netns add lab
sudo ip link add veth-host type veth peer name veth-lab
sudo ip link set veth-lab netns lab
sudo ip addr add 10.99.0.1/24 dev veth-host && sudo ip link set veth-host up
sudo ip netns exec lab ip addr add 10.99.0.2/24 dev veth-lab
sudo ip netns exec lab ip link set veth-lab up
ping -c1 10.99.0.2

Связь есть. А вот что видит «контейнер» изнутри:

sudo ip netns exec lab ip route
10.99.0.0/24 dev veth-lab proto kernel scope link src 10.99.0.2

Маршрута по умолчанию нет — наружу такой контейнер не ходит. Docker делает ровно то же самое, только автоматически: создаёт мост docker0, включает в него один конец каждой пары, раздаёт адреса и прописывает маршрут через мост:

ip -br addr show docker0
docker0          DOWN           172.17.0.1/16

Публикация порта — это правило трансляции, а не свойство контейнера. Слушающий сокет внутри пространства имён недостижим снаружи, пока хост не начнёт переправлять туда пакеты:

sudo iptables -t nat -S DOCKER
-N DOCKER
-A DOCKER -i docker0 -j RETURN

Пока контейнеров с опубликованными портами нет, правил здесь тоже нет; каждый -p 8080:80 добавляет строку DNAT. Отсюда разбор классического симптома «внутри работает, снаружи нет», который подробно разобран в следующем разделе: проверять надо три вещи по очереди — на каком адресе слушает процесс внутри (0.0.0.0 или 127.0.0.1), опубликован ли порт наружу, и не мешает ли правило межсетевого экрана хоста. Все три проверяются командами, и ни одна не требует перезапуска контейнера.

22.18. Разобранный пример: веб-контейнер доступен внутри, но не из сети хоста

Ситуация

curl localhost:8080 внутри контейнера работает. docker ps показывает 0.0.0.0:8080->8080/tcp. Снаружи соединение отклоняется.

Стратегия

Строка 0.0.0.0:8080->8080/tcp описывает намерение Docker, а не факт работы приложения. Проверять надо слушающий сокет внутри сетевого пространства имён контейнера — это единственное место, где видно, к какому адресу приложение на самом деле привязалось.

Действия

docker exec app ss -lntp
docker port app
sudo iptables -t nat -L DOCKER -n | grep 8080
curl -sv http://127.0.0.1:8080/ 2>&1 | head -3

Получено:

# docker exec app ss -lntp
State  Local Address:Port   Process
LISTEN 127.0.0.1:8080       users:(("gunicorn",pid=1,fd=5))

# iptables -t nat -L DOCKER
DNAT tcp dpt:8080 to:172.17.0.2:8080

# curl -sv http://127.0.0.1:8080/
* Connected ... Recv failure: Connection reset by peer

Интерпретация

Три наблюдения складываются в одну цепочку. Правило DNAT существует и переписывает адрес назначения на 172.17.0.2:8080 — то есть до сетевого стека контейнера пакет доходит. А слушающий сокет привязан к 127.0.0.1, и для ядра это означает: принимать соединения только с интерфейса loopback. Пакет, пришедший на eth0 контейнера с адресом 172.17.0.2, не соответствует ни одному слушающему сокету — ядро отвечает RST, и снаружи это выглядит как connection refused.

Проверка «curl localhost:8080 внутри контейнера работает» вводила в заблуждение ровно потому, что шла через loopback — единственный интерфейс, на котором сокет и правда доступен. Она подтверждала не работоспособность сервиса, а сам дефект.

Ключевая деталь: 127.0.0.1 внутри контейнера — это не адрес хоста. У каждого сетевого пространства имён свой собственный loopback, изолированный от хостового. Привязка к нему в контейнере означает «доступен только процессам этого же контейнера», а не «доступен локально на сервере».

Вывод

Публикация порта не может исправить привязку приложения — это разные слои. Менять надо конфигурацию самого приложения:

# было:  gunicorn --bind 127.0.0.1:8080 app:wsgi
# стало:
gunicorn --bind 0.0.0.0:8080 app:wsgi
docker exec app ss -lntp | grep 8080     # проверка: 0.0.0.0:8080
curl -s http://localhost:8080/health

Опасение «0.0.0.0 открывает сервис всему миру» здесь не оправдано: наружу контейнер доступен ровно настолько, насколько его порт опубликован в docker run -p, и ограничивать доступ следует именно там — например, -p 127.0.0.1:8080:8080 публикует порт только на loopback хоста. Внутри контейнера привязка к 0.0.0.0 означает «на все интерфейсы контейнера», а их у него один.

22.19. Лаборатория

Соберите стек Compose:

nginx/reverse proxy
       ↓
Python API
       ↓
PostgreSQL

Требования:

  • DB не публикуется наружу;
  • приложение и база данных общаются по имени сервиса;
  • данные базы лежат в томе;
  • для API настроена проверка готовности;
  • для теста задан лимит памяти;
  • журналы доступны через стандартный путь среды выполнения.

Break/fix:

  1. привяжите API к loopback;
  2. сломайте имя хоста базы данных;
  3. измените права на томе;
  4. поставьте слишком маленький лимит памяти;
  5. диагностируйте каждый отказ, не пересоздавая весь стек вслепую.

Концептуальное углубление: образ и работающий контейнер — разные сущности

Разделение из раздела 22.4 нужно не ради удобства сборки. Слои образа адресуются по содержимому: одинаковый слой лежит на диске в одном экземпляре, сколько бы контейнеров его ни использовало, а запуск не копирует данные — поверх готовых слоёв добавляется один записываемый, работающий по копированию при записи.

Отсюда то, что обычно называют лёгкостью контейнеров: запуск за доли секунды, тот же образ на стенде и в промышленной среде, заменяемый экземпляр. Записываемый слой дёшев именно потому, что его не собираются хранить. Поэтому «данные исчезли после пересоздания контейнера» — не сбой, а прямое следствие этого решения, и вопрос звучит иначе: что в этой системе обязано пережить удаление контейнера и где оно на самом деле лежит.

Сетевой путь Docker

При обычном режиме моста контейнер получает пару veth и отдельное сетевое пространство имён. Конец veth на стороне хоста подключается к мосту, а трансляция адресов и публикация порта позволяют внешнему клиенту обращаться к контейнеру. Это почти миниатюрное повторение сетевой части книги.

Команда docker -p 8080:80 скрывает несколько сетевых правил. Для диагностики полезно снова задавать вопрос: есть ли слушающий сокет внутри контейнера? работает ли путь до адреса контейнера? опубликован ли порт хоста? существует ли правило экрана или трансляции?

Управление ресурсами

Cgroups ограничивают процессор и память и учитывают потребление. Нехватка памяти внутри ограниченного контейнера может произойти при свободной памяти на хосте — потому что значимая граница задана лимитом cgroup.

Практическое углубление: Один процесс — три разных точки зрения

После запуска контейнера найдите процесс приложения:

  1. через docker ps;
  2. внутри контейнера через ps;
  3. на хостовой VM через обычный ps.

Процесс не является «маленькой виртуальной машиной». Это процесс хоста, который видит изменённое представление ресурсов благодаря пространствам имён и cgroups. Идентификатор процесса внутри пространства имён может отличаться от идентификатора на хосте; сетевые интерфейсы тоже принадлежат пространству имён; вид файловой системы собирается из слоёв и монтирований.

Эта модель объясняет, почему паника ядра контейнера как отдельного гостя в обычном Docker невозможна: отдельного ядра там нет. И наоборот, уязвимость ядра хоста потенциально затрагивает все контейнеры сильнее, чем изолированные виртуальные машины с собственными ядрами.

Типичная ошибка мышления

Заблуждение. Контейнер запущен, порт объявлен в Dockerfile — значит сервис доступен.

Почему это неверно. EXPOSE — это документация к образу, а не публикация порта. Явная публикация -p не зависит от этой метки; автоматическая публикация -P использует объявленные порты. См. документацию Docker EXPOSE. Кроме того, приложение, слушающее внутри контейнера 127.0.0.1, недоступно снаружи даже при опубликованном порте, потому что у контейнера собственное сетевое пространство имён и его loopback — это не loopback хоста. И статус Up в docker ps говорит только о том, что процесс с PID 1 жив.

Что проверить вместо этого.

docker port web                                   # что реально опубликовано
docker exec web ss -lntp                          # адрес прослушивания внутри
docker inspect -f '{{json .NetworkSettings}}' web | jq

Приложение должно слушать 0.0.0.0 (или ::), порт — публиковаться через -p, а готовность — проверяться отдельной пробой, а не статусом Up. И помните границу: контейнер разделяет ядро с хостом, это изоляция ресурсов и видимости, а не периметр безопасности уровня виртуальной машины.

Итоги главы

Контейнеры используют обычные механизмы Linux: процессы, пространства имён, cgroups, файловые системы и сеть. Docker добавляет порядок работы с образами и средой выполнения, но диагностика снова сводится к знакомым слоям. Чем лучше вы знаете Linux, тем меньше Docker выглядит отдельной магией.

U24. Университетское углубление: Контейнеры, namespaces, cgroups и Compose

До: 02–04, 07, 21. После: объяснять изоляцию процессов и ресурсов, строить путь сети и томов, отличать образ от состояния. L24A/B.

Теория

Контейнер — это обычные процессы с настроенными механизмами изоляции и управления ресурсами. Пространства имён дают отдельные представления процессов, монтирований, сети, пользователей и других сущностей; cgroups учитывают и ограничивают потребление. Контейнеры обычно разделяют ядро хоста, поэтому это иная граница безопасности, чем отдельная виртуальная машина. Пространство имён пользователей меняет отображение идентификаторов, но не делает любое привилегированное действие безопасным.

В cgroup v2 контроллеры задают квоты, веса и пределы ресурсов. cpu.max ограничивает CPU-время за период; это не выделение отдельных физических ядер. memory.max задаёт жёсткий предел, а показатели давления отражают задержки из-за нехватки ресурса. Процесс может испытывать ограничение или нехватку памяти при свободных ресурсах вне своей группы. Механизмы описаны в Linux cgroup v2.

Образ состоит из слоёв и метаданных запуска; тег — изменяемое имя, дайджест связывает конкретное содержимое. Записываемый слой контейнера не предназначен для роли единственной долговечной копии данных. Тома и привязанные каталоги выносят состояние, но требуют прав, резервных копий и корректной согласованности приложения. Привязанный каталог может открыть контейнеру чувствительные файлы хоста; сокет управления средой выполнения даёт особенно широкие возможности.

У сетевого пространства имён собственные интерфейсы, маршруты и loopback. Адрес 127.0.0.1 внутри контейнера обычно относится к нему самому, а не к хосту. Несколько контейнеров могут специально разделять пространство имён, поэтому модель проверяют по конфигурации. Публикация порта связывает внешний адрес и порт с внутренним путём; она не запускает слушающий сокет и не исправляет привязку только к loopback внутри контейнера.

Compose описывает совместно запускаемые сервисы, сети, тома и зависимости. Порядок запуска не обязательно означает готовность базы данных: нужны проверка готовности и повторные попытки приложения в соответствии с поддерживаемым поведением. Для воспроизводимости фиксируют образы, конфигурацию, миграции схемы и данные. Политика перезапуска помогает пережить падение, но бесконечные перезапуски не лечат ошибочную конфигурацию. Секреты предоставляют ограниченно и исключают из слоёв образа и журналов.

При недоступности опубликованного порта смотрят слушающий сокет в сетевом пространстве имён контейнера. Привязка приложения только к 127.0.0.1 не охватывает адрес контейнера; исправление должно задать нужную достижимую привязку без открытия запрещённых путей. Подтверждают запрос с разрешённого клиента и отказ с запрещённого направления.

Разобранные примеры

E24.1. Квота процессора. cpu.max = 50000 100000 даёт до 50 мс процессорного времени на 100 мс периода, примерно половину одного процессора в среднем. Это не жёсткая привязка к единственному конкретному ядру.

E24.2. Loopback. API в контейнере слушает 127.0.0.1:8080. Проброс порта хоста на адрес контейнера не делает этот слушающий сокет доступным по адресу контейнера. Проверяют привязку в его пространстве имён.

E24.3. Данные. Удаление контейнера с базой данных и пересоздание из того же образа не восстанавливает записи, если они жили только в записываемом слое. Дайджест фиксирует программу, а не состояние базы.
