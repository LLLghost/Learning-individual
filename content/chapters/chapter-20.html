20. Python для диагностики и автоматизации

Академическое продолжение этой главы: U22.

Цели главы

После главы вы должны уметь:

  • строить небольшую утилиту командной строки с argparse;
  • безопасно запускать команды через subprocess;
  • различать стандартный вывод, поток ошибок, код возврата и превышение времени;
  • использовать журналирование вместо хаотичных print;
  • читать и писать JSON/YAML;
  • обращаться к HTTP API;
  • строить структурированный диагностический отчёт;
  • понимать, когда не следует использовать shell=True;
  • ограничивать утилиту по времени и повторять только то, что безопасно повторить.

Перед началом: когда оболочка перестаёт быть удобной структурой данных

Как только нужно разобрать JSON, сопоставить десятки устройств, построить отчёт или обратиться к REST API, конвейер из grep|awk|sed начинает скрывать смысл. Python вводится здесь как средство моделирования данных и ошибок, а не как самоцель программирования.

Где это в стенде: automation; результаты должны попадать в репозиторий.

Связь: первый проект главы — не абстрактный калькулятор, а развитие server-diagnostics-toolkit: запуск процессов, структурированный разбор, коды возврата, журналирование и подготовка отчёта.

Прежде чем читать. Скрипт работает на вашей машине. Чего ему не хватает, чтобы его можно было запускать в эксплуатации?

Ответьте до чтения — одной фразой, вслух или письменно. Неверный ответ здесь полезен не меньше верного: значение имеет сама попытка ответить прежде, чем прочитано объяснение. Разбор — в разделе «Типичная ошибка мышления»: перейти.

20.1. Когда Python лучше Bash

Если задача требует:

  • вложенные структуры данных;
  • разбор JSON и YAML;
  • переиспользуемые модули;
  • сложная обработка ошибок;
  • тесты;
  • интерфейсы по HTTP и SSH;
  • параллелизм;
  • отчёт в нескольких форматах;

Python обычно проще поддерживать.

20.2. subprocess

Плохая привычка:

subprocess.run(user_input, shell=True)

Если строка содержит недоверенные данные, интерпретация её оболочкой создаёт риск внедрения команд.

Предпочитайте список аргументов:

from subprocess import run

result = run(
    ["lsblk", "-J", "-o", "NAME,SIZE,TYPE,MODEL,SERIAL"],
    text=True,
    capture_output=True,
    timeout=10,
    check=False,
)

Теперь доступны:

result.returncode
result.stdout
result.stderr

20.3. Машиночитаемый вывод

lsblk -J отдаёт JSON. Это намного устойчивее разбора колонок по пробелам.

import json

data = json.loads(result.stdout)
for dev in data["blockdevices"]:
    print(dev["name"], dev.get("model"))

В автоматизации всегда сначала ищите флаг структурированного вывода или программный интерфейс.

20.4. argparse

Утилита командной строки должна объяснять себя:

import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--output", default="report.json")
parser.add_argument("--timeout", type=int, default=10)
args = parser.parse_args()

Это лучше ручного разбора sys.argv по индексам.

20.5. Журналирование

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)
logging.info("Collecting block devices")

Журналирование позволяет менять подробность, добавлять отметки времени и перенаправлять вывод без переписывания всего кода.

20.6. Исключения и модель результата

Не ловить всё через:

except Exception:
    pass

Так скрипт превращает реальные отказы в отсутствующие данные.

Лучше возвращать структурированный результат:

{
  "ok": False,
  "command": ["smartctl", "-a", "/dev/sdb"],
  "returncode": 2,
  "stderr": "...",
  "duration_ms": 143
}

Тогда отчёт сохраняет подтверждающие данные.

20.7. HTTP API

Для Redfish, мониторинга и внутренних сервисов нужен клиент HTTP.

С библиотекой requests:

import requests

r = requests.get(
    "https://bmc.example/redfish/v1/Systems/1",
    auth=(user, password),
    timeout=10,
)
r.raise_for_status()
data = r.json()

В эксплуатации нужно учитывать проверку TLS, обращение с учётными данными, повторы и ограничения частоты. Отключение проверки TLS не должно становиться постоянным «решением».

20.8. Секреты

Не храните пароли и ключи доступа внутри исходного кода или репозитория Git.

Варианты:

  • переменные окружения;
  • защищённые файлы конфигурации;
  • хранилище ключей операционной системы или менеджер секретов;
  • Ansible Vault;
  • хранилище секретов системы сборки.

И всегда проверяйте, что диагностический отчёт случайно не выносит секреты из окружения или конфигурации.

20.10. Диагностика по правилам

Пример правила:

if array_state == "degraded":
    findings.append({
        "severity": "critical",
        "title": "RAID degraded",
        "evidence": array_details,
        "next_step": "Map failed member to physical slot before replacement",
    })

Важно не делать слишком уверенных выводов. Лучше:

Evidence: PCIe link negotiated x4 Gen3, capability x8 Gen4.
Interpretation: link is below device capability.
Possible causes: slot/platform limit, riser, signal integrity, firmware setting.

чем автоматически объявлять «райзер неисправен».

20.11. Тесты

Даже инфраструктурная утилита выигрывает от модульных тестов для разборщиков и правил. Вывод утилит производителя можно сохранить как эталонные данные и проверять разбор без реального сервера.

Например:

tests/fixtures/lspci_good.txt
tests/fixtures/lspci_bad_link.txt
tests/test_pcie_parser.py

20.12. Таймауты, повторные попытки и время

Диагностическая утилита обязана заканчиваться. Любой внешний вызов — запуск команды, запрос по HTTP, чтение сокета — получает предел времени, а вся операция целиком получает второй, общий предел. Иначе сборщик, запущенный на тридцати узлах, однажды повиснет на одном недоступном и не вернёт ничего.

Повтор без разбора причины опаснее отказа. Повторять можно то, что безопасно повторить: чтение, запрос с документированным ключом идемпотентности, проверку состояния. Создание ресурса повторяют только после того, как выяснили, был ли он создан.

предел времени на попытку
+ общий предел на операцию
+ признак «повтор безопасен»
+ пауза 2^n со случайной добавкой
= ограниченная по времени и безопасная повторная попытка

Случайная добавка к паузе нужна не для красоты: без неё тридцать узлов, начавших одновременно, будут повторять запросы тоже одновременно и добьют перегруженную службу.

Длительность измеряют монотонными часами (time.monotonic), а не системными: системные могут прыгнуть при синхронизации времени, и отрицательная длительность в отчёте — типичный след такой ошибки. Отметки времени в самом отчёте, наоборот, записывают в UTC с явным указанием пояса, иначе сопоставить их с журналами другого узла невозможно.

Что доказывает истёкший timeout: только то, что ответ не пришёл вовремя. Была ли операция выполнена на другой стороне, он не сообщает.

20.13. Из скрипта в инструмент

Файл на восемьсот строк, который запускается только на компьютере автора, — это черновик. Инструментом его делают несколько скучных свойств: точка входа отделена от логики сбора; есть версия, которую видно в выводе; зависимости зафиксированы; запуск не требует установки пакетов в систему; код возврата определён контрактом; README показывает пример вызова и ожидаемый вывод.

serverdiag/
  __main__.py      точка входа и разбор аргументов
  collect.py       сбор фактов, только чтение
  report.py        формирование JSON и текста для человека
  tests/           проверки на записанных примерах вывода
  requirements.txt зафиксированные зависимости
  README.md        пример запуска и ожидаемый результат

Чем меньше зависимостей, тем выше шанс, что утилита запустится на аварийном узле, где нет ни интернета, ни свободного места под виртуальное окружение. Для сбора фактов стандартной библиотеки почти всегда достаточно, и это осознанный выбор, а не аскеза.

Простая проверка готовности: скопируйте каталог на чистую виртуальную машину и запустите. Всё, что после этого пришлось доустанавливать руками, — часть инструмента, которую забыли описать.

20.14. Отказ внешней команды: что именно у него видно

Модель результата из раздела 20.6 заполняется данными запуска. Посмотрим, какими именно — команда заведомо провалена:

import subprocess

r = subprocess.run(['ls', '/нет-такого'], capture_output=True, text=True)
print('код возврата:', r.returncode)
print('обычный вывод пуст:', r.stdout == '')
print('поток ошибок:', r.stderr.strip())
код возврата: 2
обычный вывод пуст: True
поток ошибок: ls: cannot access '/нет-такого': No such file or directory

Три вывода отсюда. Код возврата — единственный формальный признак отказа, и он не ноль. Обычный вывод пуст: скрипт, который считает признаком успеха непустой stdout, спутает отказ с отсутствием данных, а скрипт, разбирающий stdout без проверки кода, получит пустой список дисков и запишет в отчёт «дисков нет». Сообщение ушло в поток ошибок — без capture_output вы его не увидите вовсе, оно уйдёт в терминал мимо отчёта.

Отсюда два допустимых способа вызова. Явная проверка, когда отказ ожидаем и обрабатывается:

r = subprocess.run(cmd, capture_output=True, text=True, timeout=30)
if r.returncode != 0:
    return {'ok': False, 'command': cmd, 'returncode': r.returncode,
            'stderr': r.stderr.strip()[:500]}

И check=True, когда отказ означает конец работы: тогда Python сам бросит CalledProcessError с командой и кодом внутри. Недопустим третий вариант — вызов без того и без другого: он не падает и не сообщает, а просто продолжает работу с пустыми данными. Формально код при этом корректен, и обзор кода его пропускает.

Замечание о timeout: он обязателен по причинам из раздела 20.12, но истёкший предел времени не равен отказу операции. subprocess.TimeoutExpired означает ровно одно — ответа не дождались; выполнилась команда или нет, это не сообщает, и в отчёте такой исход честнее отмечать отдельным значением, а не ok: false.

20.15. Разобранный пример: разборщик ломается после обновления пакета

Ситуация

Скрипт извлекает серийный номер из lsblk разбиением по пробелам. После обновления модель диска содержит пробелы, поля сдвигаются.

Стратегия

Соблазн — подобрать новый индекс поля и идти дальше. Но прежде чем чинить, надо доказать, что причина именно в сдвиге полей, и заодно понять, есть ли у этого источника форма, в которой сдвига не бывает.

Действия

lsblk -o NAME,MODEL,SERIAL,SIZE | head        # как выглядит текст
lsblk -J -o NAME,MODEL,SERIAL,SIZE,TYPE       # то же в JSON
python3 - <<'PY'
import subprocess
line = subprocess.run(['lsblk','-o','NAME,MODEL,SERIAL,SIZE'],
                      capture_output=True, text=True).stdout.splitlines()[1]
print(repr(line.split()))
PY

Получено:

# было (модель из одного слова):
sda  SAMSUNG_MZ7 S3Z1NX0M 894.3G
['sda', 'SAMSUNG_MZ7', 'S3Z1NX0M', '894.3G']      # serial = поле [2]

# стало (модель из двух слов):
sda  DELL PERC H740P 00a1b2c3 894.3G
['sda', 'DELL', 'PERC', 'H740P', '00a1b2c3', '894.3G']   # поле [2] = 'PERC'

Интерпретация

Гипотеза подтвердилась буквально: split() разбивает строку по пробелам, а в новой модели диска пробелы есть внутри одного логического поля. Позиция серийного номера сдвинулась с индекса 2 на индекс 4, и скрипт стал возвращать кусок названия модели.

Ошибка при этом не возникает — значение того же типа, той же длины, оно просто не то. Это худший класс дефектов в автоматизации: программа продолжает работать и наполняет инвентарь правдоподобным мусором. Найдётся он не при запуске, а месяцем позже, когда по серийному номеру не удастся оформить гарантийную замену.

Корень не в Python и не в конкретном индексе. Текстовый вывод lsblk предназначен для чтения человеком: количество колонок в нём зависит от данных, и никакого обещания о структуре он не даёт. Разбор по позициям опирается на договорённость, которой никто не заключал.

Вывод

Брать надо тот же источник, но в форме, где структура объявлена явно:

import json, subprocess

out = subprocess.run(['lsblk', '-J', '-o', 'NAME,MODEL,SERIAL,SIZE,TYPE'],
                     capture_output=True, text=True, check=True)
for dev in json.loads(out.stdout)['blockdevices']:
    if dev['type'] != 'disk':
        continue
    if not dev.get('serial'):                      # явная проверка, а не молчание
        raise SystemExit(f"нет серийного номера для {dev['name']}")
    print(dev['name'], dev['serial'], dev['model'])

Здесь пробел внутри модели ничего не ломает: поле названо, а не сосчитано. check=True превращает сбой команды в исключение, а явная проверка на пустое значение — в остановку вместо тихой записи пустоты.

Договор о данных важнее выбора языка. Python не спасает плохой парсер, если источник выбран неправильно; и наоборот — с машиночитаемым источником задача решается на любом языке в несколько строк.

20.16. Лаборатория

Создайте serverdiag:

serverdiag/
├── cli.py
├── collectors/
│   ├── system.py
│   ├── network.py
│   ├── block.py
│   └── pcie.py
├── analyzers/
│   └── basic.py
├── renderers/
│   ├── json.py
│   └── markdown.py
└── tests/

Минимум:

serverdiag collect --output report.json
serverdiag analyze report.json
serverdiag render report.json --format markdown

Концептуальное углубление: утилита на Python должна моделировать ошибки как данные

subprocess.run() возвращает не только стандартный вывод. У процесса есть код возврата, поток ошибок, ограничение по времени и возможность вообще не запуститься. Хорошая автоматизация различает эти случаи.

Например, отсутствие smartctl на хосте и отказ по здоровью SMART у диска — совершенно разные состояния. Если программа сводит оба к пустой строке, отчёт становится опасным.

Структура может быть такой:

class CheckResult:
    name: str
    status: str   # ok, warning, critical, unknown
    evidence: dict
    error: str | None

Тогда каждый сборщик возвращает результат с подтверждающими данными, а оформитель отдельно делает отчёт в Markdown или JSON.

Интерфейс вместо разбора экрана

Redfish в BMC, интерфейсы Prometheus, Proxmox и хостингов Git дают структурированные интерфейсы. requests или клиент HTTP позволяет получать данные напрямую. Но интерфейс добавляет аутентификацию, TLS, постраничную выдачу, ограничения частоты и версионирование — их нужно рассматривать как часть инженерного контракта.

Практическое углубление: не разбирайте человеческий вывод, если существует структурированный интерфейс

Команда, красиво печатающая таблицу для человека, не обязана сохранять формат между версиями. Автоматизация устойчивее, когда использует JSON, sysfs и procfs с понятной семантикой, программный интерфейс или машиночитаемые параметры.

Пример принципа:

плохо:  subprocess + split по количеству пробелов в красивой таблице
лучше: command --json -> json.loads()
лучше: библиотека/API, если она является стабильным interface

Но структурированные данные не отменяют проверку. Поле может отсутствовать, команда может вернуть ненулевой код, устройство исчезнуть между двумя вызовами. Python нужен в том числе для явной обработки таких состояний.

Типичная ошибка мышления

Заблуждение. Скрипт работает у меня — значит он готов к эксплуатации.

Почему это неверно. Диагностический скрипт запускается в чужом окружении: другая версия Python, отсутствующие модули, другая локаль (а с ней другой разделитель дробной части), другой формат вывода команд, отсутствие сети, другой пользователь без прав. Отдельно: subprocess с shell=True и подстановкой имени, полученного извне, — это не стилистическая, а безопасностная ошибка.

Что проверить вместо этого.

r = subprocess.run(["ipmitool", "sel", "elist"],
                   capture_output=True, text=True, timeout=30, check=False)
if r.returncode != 0:
    raise CollectorError(f"ipmitool failed rc={r.returncode}: {r.stderr.strip()}")

Список аргументов вместо строки; явная обработка returncode; вывод в JSON, а не print для человека; argparse с --dry-run; секреты из переменной окружения или файла с правами 600, но никогда не в аргументах командной строки — их видно всей системе через ps.

Лестница самостоятельности

Эту главу не нужно считать завершённой после одной успешной лаборатории. Пройдите три уровня, уменьшая количество подсказок.

  1. С опорой: обернуть команды в структурированный результат. На этом уровне разрешено смотреть разобранный пример и сверять ожидаемые результаты.
  2. С частичной опорой: сделать отчёт в JSON и Markdown. Перед каждой командой письменно сформулируйте, что именно она должна подтвердить или опровергнуть.
  3. Инцидент: получить смешанные отказы и не спутать «неизвестно» с «в порядке». На этом уровне сначала фиксируются симптом и подтверждающие данные; готового списка команд нет.

Теория

Python подходит для структурированной обработки, когда конвейер оболочки становится трудным для проверки. Интерфейс командной строки строят через argparse, данные — через словари и списки с явной схемой, вывод — через JSON с версией формата. Журналирование отделяют от машинного результата; сообщение человеку в стандартном выводе может сломать разбор JSON на следующем шаге. Исключения обрабатывают по ожидаемым категориям и сохраняют контекст.

subprocess.run с массивом аргументов и shell=False исключает интерпретацию метасимволов оболочкой в аргументах, но не проверяет безопасность самой вызываемой утилиты. Нужны список разрешённых команд, ограничение по времени, управление окружением и ограничение объёма вывода. capture_output=True собирает весь вывод дочернего процесса в память и само по себе не задаёт предела размера: ограничение времени не заменяет лимит вывода. Для недоверенного многословного процесса читают потоки по частям с явным пределом и прекращают процесс при его превышении. check=True полезен там, где любая ненулевая команда считается ошибкой; сборщик чаще должен сохранить частичный отчёт и продолжить с явным статусом.

REST связывает ресурсы с операциями HTTP, но конкретный контракт задаёт документация сервиса. GET предназначен для чтения, PUT обычно идемпотентен относительно целевого состояния, POST может создавать новый объект при каждом повторе. Превышение времени после отправки означает неопределённость результата: сервер мог выполнить действие. Повторяют безопасно через ключ идемпотентности, условный запрос или поиск результата операции.

Коды HTTP 401, 403, 404, 409, 429 и 5xx означают разные классы ситуаций. Бесконечный повтор всех ошибок может усилить аварию. Задержка с ростом и случайным разбросом, максимум попыток, заголовок Retry-After и общий срок ограничивают воздействие. TLS требует проверки сертификата и имени; отключение проверки ради успешного ответа уничтожает часть модели доверия. Токены не включают в адрес, журналы и репозиторий.

Списки часто выдаются постранично: первая страница не равна всему набору. Сборщик должен пройти по курсору или ссылкам на следующую страницу, ограничить цикл и учитывать изменение данных во время обхода. Для параллелизма удобен ограниченный пул для задач, упирающихся в ввод-вывод; для кода, упирающегося в процессор, результат зависит от реализации и версии интерпретатора, поэтому нельзя универсально обещать ускорение потоками. Нужны лимит параллельности, обратное давление и согласованная обработка частичного отказа.

Тесты проверяют контракт: JSON остаётся корректным при ошибке команды, превышение времени обозначается отдельно, секрет не попадает в журнал, дубликаты страниц не создают дубликаты объектов. Заглушки не доказывают совместимость с реальным интерфейсом, но позволяют воспроизводимо проверить ветви, которые трудно вызвать на живой системе.

После тайм-аута POST сначала ищут результат по идентификатору операции или ключу корреляции. Если объект уже создан, продолжают работу с подтверждённым идентификатором вместо нового независимого POST. Проверка завершения включает единственность ресурса и соответствие его целевой конфигурации.

Отсутствие исполняемого файла и завершение найденной программы с кодом 1 — разные состояния. Первый случай означает, что команду не удалось запустить; во втором программа работала и вернула собственный код. В отчёте сборщика сохраняют их раздельно вместе с ограниченным stderr.

Разобранные примеры

E22.1. Постраничная выдача. Интерфейс вернул 50 объектов и курсор следующей страницы. Если всего 123 объекта, нужны страницы 50+50+23; подсчёт только первой даёт недостоверный инвентарь.

E22.2. Повтор запроса. Запрос POST на создание VM завершился превышением времени. Новый POST без ключа может создать вторую VM. Сначала проверяют идентификатор операции или используют документированный повтор с тем же ключом идемпотентности.

E22.3. Параллельность. 20 независимых запросов по 0,5 с при параллельности 4 имеют идеальную оценку 2,5 с без накладных расходов. Ограничение частоты, разброс задержек и серверная очередь увеличат время.
